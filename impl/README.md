# impl: the reference implementation in Go

This folder holds the reference implementation of the botaru core (D-91, D-92 in [docs/decisions.md](../docs/decisions.md)). Version 0.1 of the implementation runs the first bot: the hello-bot sequence of [examples/hello-bot/](../examples/hello-bot/) works end to end over the wire, from a Telegram message to the model answer in the same chat. How to run it on a server: [DEPLOY.md](DEPLOY.md).

## Rules for this folder

- The implementation does not change skeleton files outside `impl/`. A change of a contract goes through the skeleton rules: additive only inside a version (MAN-3), a new schema file `.v(N+1)` for a breaking change.
- It passes the `conformance/` suite and the evals of the skeleton; a rule with `waivable: false` cannot go into its list of expected failures.
- The agent runtime is our own loop over P4 (D-93); conversation memory, sessions and transcript compression live in the core stores.
- Money is an integer number of micro-euros `eur_micros` (D-87), never a floating-point number.
- Builds are static (`CGO_ENABLED=0`) for linux/amd64 and linux/arm64. Installation files (tenants, keys, machines, people) never go into this repository.
- Every Go file starts with `// SPDX-License-Identifier: AGPL-3.0-only`.

| `botaru-mockmodel` | the mock model provider of the test bench (`spec/bindings/model-providers/mock.md`) |

## Implementation choices

These are decisions of this implementation where the skeleton leaves a choice; none changes a contract.

- **Store.** PostgreSQL 16 or later through pgx. The store clock is `botaru_now()` (the database time plus the test bench offset), so every deadline is counted by one clock (TIM-1).
- **The skeleton is read at run time** from a checkout (`spec_root`, or the folder the program runs in), not copied into the binaries, so the schemas the core checks are the ones in git.
- **Operator credentials** are scoped to one tenant each, because the bodies of the P2 people operations carry no tenant (TEN-2). The settings file holds only the SHA-256 of each credential.
- **Secrets.** Worker tokens, handles and driver secrets are stored as HMAC-SHA256 with the core token key; lease tokens are signed with the same key (`key_id`, `sig`).
- **The result schema reaches the runtime** as the extension field `payload.result_schema` of the attempt (MAN-3), so the instruction stays exactly the trusted text from git; the runtime appends the request for a JSON answer to the system prompt.
- **Code texts** come from the skeleton message catalog `spec/bindings/channels/messages/en.yaml`, read at run time like the other skeleton files (DLV-9); other locales are `<locale>.yaml` files in the installation's text folder, and a key they lack takes the `en` text. The recipient's locale reaches the channel as the extension field `payload.locale` of a delivery; without it the channel takes `en` (the tenant's `locale` is a field of v0.2). Code fills the values of `notice.ai` (the tenant, and the operator from the deployment setting `operator`) and of `notice.privacy` (the tenant's privacy block and the default periods of `spec/model/retention-classes.yaml`); a value the installation does not set gets a fallback (the operator: "the operator of this farm"; the controller: the tenant name; the contact: the notice link; anything else: "-"), and the core logs a warning for each at start and after `apply`. The channel renders a parameter it does not get as "-", so a person never sees a raw placeholder. Notices planned by the first version of the implementation get the new keys from store migration 0002 and their new values from the core at start.
- **Later versions and profiles.** The core claims skeleton `v0.1` with the profile `core` (`internal/spec`). `apply` refuses with `version_unsupported` and the path a kind whose `since` is later, a field marked with a later `x-botaru-version`, and the fields of the profiles `knowledge`, `ingress`, `connections`, `debug` and `sandbox` and tier 2 (MAN-11). The example tenant and channel carry such fields; the test bench and `farmctl apply -drop-unsupported` leave them out, the second with a warning for each. Only a whole optional field is left out. A later kind, a required field, a list element, or a value that gives a field its meaning (an enum or const value of the field, such as a channel direction, a catalog resource kind, a placement or a tier) stops with an error that names the path, because the manifest would then say something else. `farmctl` reads the schemas for this from the checkout (`-spec-root` or `BOTARU_SPEC_ROOT`, else a parent of the working directory).
- **The attempt record.** At `claim` the core writes into the lease of the attempt the run fingerprint with its part hashes (PRV-1) and, for the full result check at `complete` (OUT-1), the version of the tenant catalog and the `enum_from` values of the result schema filtered by the task's mark. P1 `hello` carries no `describe()` values, so the runtime part has `describe: null`; its driver is the role's `runtime.driver`, else the implementation name from `hello`. `catalog.<list>`, `catalog.hosts` and `catalog.services` resolve from the tenant's `Catalog` manifest, `reasons.<name>` from `spec/model/<name>-reasons.yaml`, and `task.attachments` to nothing, because there are no files yet.
- **Notices to a person** (`principal_left`, IDN-13) go to the direct chat of each admin with `admin:people` through every channel of the tenant whose identity kind matches the admin's identity; the chat id of a direct chat is the external user id. The notice goes when the state changes: a repeated `off` sends none. When no such admin is reachable, the departure still goes through; the audit record of the command shows `principal_left: 0`, and the core logs a warning. An offboarded id is final: every people operation on it, `principal.add` included, answers `subject_closed`.
- **Results refused at complete** (`output_schema_invalid`, OUT-1) are stored on the lease like an accepted outcome, so a repeat of the same complete gets the same refusal (IDM-3), and any other call under the lease is fenced. A lease taken before the upgrade has no attempt record; its `enum_from` values are resolved at complete.
- **Model providers.** The `provider` of a model profile is a name that the deployment settings map to a binding, an address and the key of each tenant's workspace. On the test bench the provider of the examples (`provider-a`) maps to the mock provider.
- **A bare command is its own goal.** `goal` is required by `task-body`, so `/hello` without text gets the goal `/hello`.
- **Holds** (HLD-1..3) act at the check points this build has: enqueue (`no_enqueue` on the farm, the tenant or the type), claim (`no_claim` and `cancel_running` on the farm, the tenant, the role, the worker or the type), heartbeat (`cancel_running` ends the attempt with `held` without spending it, revokes its handles and returns the task to `submitted`) and the delivery handoff (`no_delivery` on the farm, the tenant or the channel withholds the delivery with `held`; an alarm notice still goes). `no_tool` on the farm, the tenant, the role, the type, the plugin, the agent worker, the target machine (`host`) or the catalog resource of the target value (`resource`) denies a tool call at P3 and again at its handout to a toolhost, where a hold on the toolhost also counts. `no_message` on the farm, the tenant, the role, the worker or a bot group (for a group address) refuses a send with `held` and discards at `complete` what the attempt staged. The effects of ports not built yet are recorded and act when those ports come. P2 takes holds only from operator credentials: the credential of tenant `farm` reaches every tenant and the scopes `farm` and `seat`, any other only its own tenant; a hold of a person of the tenant (PRM-15) and its rank rules are in the core and wait for P2 on behalf of a person. `farmctl hold farm` writes a farm hold straight to the store with the core's settings (DEP-8). The `hold` loop ends a hold at its `until`, never earlier.
- **Alarms** (OBS-6, MON-1, MON-13). The core raises `alarm.worker.stale` (a worker not seen for 120 s, two long-poll periods of `claim`, OBS-4) and `alarm.task.unclaimed` (a never-claimed task past `start_by`, DSP-8), and resolves them when the worker calls again or the task is taken or ends. A repeat of an open episode only counts. As this core does not claim the profile `monitor`, every episode change goes as the code text `notice.alarm` (delivery kind `alarm_notice`) to the private chats of the tenant's admins, persons with `admin:people` or `hold.release`; without such an admin, to the admins of `farm`; without either, the core logs a warning. An open `page` alarm repeats its notice every 30 minutes; without incidents in this build there is no `incident.ack`, so it repeats until it resolves. An alarm notice does not die by attempt count while its episode is open, and the notices of one alarm go in order.
- **Tools (P3, E3).** The P3 catalog of an attempt is computed by its tools handle on every request: the role's read tools whose tier is within the task's `max_tier` and whose `output_class` is within its mark, with `enum_from` turned into the catalog values the mark allows, a resource list giving only the values of resources whose `read_by` holds the tool, in name order; a value two such resources share has no single target and is refused. The model sees `<plugin>_<tool>`; rights and audit use `<plugin>/<tool>`. P4 requires the request tools to be exactly that catalog, in its order, compared by the hash of `{name, description, input_schema}` (GW-1), and the run fingerprint takes its catalog part from the same hashes. The built-in tools of the catalog (step 7 of the P3 sheet) are not served. A call is checked in one transaction (holds, rights, tier, output class, the closed argument schema, the target machine) and queued for a toolhost of the tenant, the plugin, the placement and the machine; nobody taking it within 30 s, or the type's `timeouts.tool_start_by` if shorter, ends it with `no_executor`, and no live toolhost of the target ends it at once with `plugin_unavailable`. A refusal reaches the model only as "no permission"; the reason goes to the audit. A call whose attempt loses its lease is abandoned.
- **The set lint of `apply`** (MAN-6, MAN-10, DEP-11, PRF-1, DSP-3, INJ-6 and the other checks of `ci/check_manifests.py`) runs over the whole set after every object passed its schema, with the stable codes of `ci/lint_codes.py`, so a set gets the same codes from `apply` as from the skeleton lint over git. `TestLintFixtures` runs the cases of `conformance/fixtures/manifests` through `apply` and keeps the list of agreeing cases in `internal/core/testdata/lint-passing.txt`. Where this core differs: references of the tenant manifest (commands, default types, `/run`, delegated groups, allowed model profiles) to objects outside the set are logged, not refused, because a deployment applies the tenant by stages (the hello-bot sequence applies the demo tenant with one type), and a missing object is refused where it is used; the checks of the manager seat (MGR-20) and of monitoring as a recipient (MON-1) wait for the profiles `manager` and `monitor`; on a test bench an old model price (GW-17) is logged. The farm nodes come from the setting `farm_hosts` (DEP-11); without it no machine counts as one. A plugin's `network.egress` names only machines of a tenant catalog of the set, and `monitor-api` only for the plugin `monitor` (INJ-6, `egress_unknown`). A dispatch rule's bot group must exist and select a role that takes the type (`dispatch_group_disjoint`), its attempt period is at most twice the type's and within its deadline, and its attempts are fewer than the type's and at least one (`dispatch_attempt_bounds`, DSP-3, FEN-3). A toolhost is not enrolled for a plugin with secrets or network egress: such a plugin runs in its own container, which this build does not start (DEP-7).
- **Plugin manifest checks at `apply`** beyond the schemas: exactly one of `target_from` and `target: any`; no free string parameter outside a `sandbox` plugin (`sandbox_placement`, as this version has no sandbox); the `ip`, `email` and `secret` masks on a host tool whose output is shown as untrusted; no free text in the output schema of a tool declared trusted; and the program commands of `cmd`, where a parameter name has one schema across the tool and all its commands (`cmd_param_conflict`, INJ-14).
- **The work item of a tool call** carries two extension fields (MAN-3): `resolved`, the catalog fields a plugin needs (for example `{"service.unit": "nginx.service"}` for a command with `{service.unit}`), and `limits`, the tool's `redact`, `output_limit_bytes` and `timeout_s`, so the toolhost needs no manifests. The plugin gets them as `_meta["botaru/resolved"]` and `_meta["botaru/work_id"]`.
- **The toolhost** reports in `hello` one `tools_fingerprint`: the fingerprint of `spec/hashing.md` for one plugin, and for several the hash of the array of the plugin fingerprints in the order of the plugin names. The core computes the same from the manifests and blocks a toolhost that differs (INJ-2). After an `apply` that changes one of its plugins, a toolhost takes no calls and does not count as live until it says hello again with the new fingerprint, so restart it after updating the checkout. Each call runs in a new plugin process in its own process group, with an empty environment unless the settings name one, so nothing of a call outlives it; a plugin that does not stop within `kill_after` after a cancellation is killed. The toolhost cancels a call 10 s plus `kill_after` before the end of its lease by its own clock, also when a heartbeat stalls, so the plugin is gone before the lease ends (FEN-6). The `cmd` plugin resolves the symlinks of a program path at start and again at each call, refuses a program whose real name is forbidden, and runs the resolved path. A request from a plugin (sampling, elicitation, roots) is refused and the call ends with `exec_failed`, the reason of every plugin error.
- **Tool output** is masked by the toolhost by the kinds of the tool's `redact` and cut at its limit; the core masks secrets once more, cuts again and checks structured output against `output_schema`. The text blocks are joined before each mask, so nothing split across blocks escapes it, and structured output above the tool limit is refused. Only a tool that declares `untrusted_output: false` and has an `output_schema` without free text (a string of the prose format `search_query` counts as free text) counts as trusted, and the model then sees only its checked structured output. Any other output reaches the model inside a mark with a random value per call, and the first such output sets `untrusted_seen` on the task, with the tool as `untrusted_source`; untrusted output carries no separate structured content. The output of a call is checked against the tool definition it was queued under: if an `apply` changed or removed that tool while the call waited or ran, the call is not handed out, or its output is dropped, and it ends with `plugin_unavailable`. An attempt keeps the tool catalog it began with: once an `apply` changes it, P3 and P4 refuse the attempt with `fenced`, and the agent returns the work with `release` without spending the attempt, so the run fingerprint always describes the tools the model had. The toolhost kills the whole process group of a plugin after every call, so nothing a plugin started outlives it. The toolhost masks a plugin's error text before logging it.
- **Own plugins.** `cmd` runs the named commands of its manifest through execve without a shell, with an absolute program, a fixed environment and each parameter as a whole argv element after `--`; a value that starts with `-`, is empty or holds a newline is refused, and the manifest is checked against `spec/model/forbidden-programs.yaml` at start. `logs` reads the tail of a catalog log source; which file a source is on the machine is local deployment data (`-source id=path`), and a symbolic link or a non-regular file is not read. `checks` reads the latest results of a check from a results file that an external checker writes.
- **Money** (BUD-1, BUD-2, BUD-5, BUD-7). Every usage line and reserve carries the budget line of the type's purpose from `spec/model/task-purposes.yaml`. A reserve passes the tenant's month and day, the month and day of its line, the line's `per_role_month_eur` for a call of a role, the tree budget and, on the `work` line only, the person's day limit; a line other than `work` without `month_eur` has 0, so its tasks are refused until it gets money. A tool call reserves the `price_eur` of a `billing: external` tool before it is queued (0 for any other tool, which still gets its usage line, unit `eur_cents`); a call that does not fit gets `budget_exhausted` from P3 and the attempt fails with it. A toolhost that took the call commits its reserve; a call nobody took gives it back. `hour_eur` is not a reserve limit: the `hold` loop sums the usage of the sliding hour (reserves aside), and above `hour_eur` (by default `month_eur`/100) sets a `no_claim` hold of `contain_auto` with the reason `runaway_spend` for an hour on every agent role of the tenant and raises `alarm.hold.auto` (page), which resolves when no such hold is active (HLD-7). The 80% threshold events of BUD-4 are not built: the events catalog has no event for them.
- **Outbound privacy** (SEC-9, INJ-11, HLD-6). At the delivery handoff, after the recipient and hold checks, a delivery whose mark is above the ceiling of its executor is withheld with `channel_ceiling`; to a chat, the person gets the code text `delivery.withheld.channel_ceiling` in its place. The monitoring system takes summaries only; this build plans no delivery to a sink, whose ceiling is in its own manifest. The ceiling comes from the tenant's `privacy.channels` by driver: its `ceiling`, `internal` for a third-party store without one, none for a store of the tenant, and `internal` for a driver the block does not list. Model text and result fields are searched for secrets with the toolhost's patterns; a match is withheld with `secret_in_outbound` and raises `alarm.outbound.secret.detected` (page) on the role that wrote it, without content. The second such case of one role within an hour sets a `no_delivery` hold of `contain_auto` without `until` on that role (only a person lifts it) and raises `alarm.hold.auto`; the handoff counts a role hold of the role whose attempt wrote the task.
- **Flags of the record** (INJ-13, AUD-5). A forwarded or quoted message sets `untrusted_seen` on the task with the source `forward` or `quote`. `personal_seen` lists without content where the task met personal data: a forward, a quote, or tool output in which the toolhost masked an address (`masking`); the audit record of `task.complete` carries the same list. When the channel names the author of the forwarded or quoted text (`forwarded_from`, `quoted_from`) and the tenant knows that identity, the principal goes into `personal_subjects`; the sender and an unknown author do not.
- **Health and the store volume.** Each loop marks its tick in the table `loop_ticks` after a pass that ended without an error, so P2 `health` shows the age of each loop from the store (OBS-4). The `health` loop computes the three indicators of OBS-9 and raises their alarms in the `farm` tenant; it does not judge its own tick, and on a bench that ticks only by `loop.tick` it raises no loop tick alarms. The core measures the store volume by the path `health.store_volume`, which holds when the store runs on the core machine (D-88); without it there is no measurement and no headroom. Defaults: urgent age 600 s, the share of deliveries delivered within 10 minutes at least 0.9 over a window of 1 h (a withheld delivery is not counted), loop tick 30 s, store free space soft 0.15 and hard 0.05. When the store stops answering, P1 answers `not_ready` with `retry_after_s` until every loop ticked again (OBS-8); an unexpected store error of any port answers `not_ready` as well.
- **The operator views of P2.** In this build every P2 caller is an operator with a credential for one tenant, so `audit.query` is the emergency access of AUD-7: it reads the audit of the credential's tenant and writes an audit record of kind `read`. `status` claims `conforms_to: {skeleton: 0.1.0, profiles: [core]}` and lists every tenant under `farm_manager_disabled`, because this build has no farm manager. `doctor` gives the tick of each loop, the store volume and the indicators as farm numbers, and for the tenant the holds, the dead work, the stale workers, the open alarms and the open erasure requests. `task.redrive` re-enqueues the body under the original initiator, so rights are checked again; `delivery.redrive` plans a copy linked by `redrive_of`, and the ceiling and the recipient are checked again at handoff.
- **Plugin health.** A toolhost may send `health` reports in `hello` and `heartbeat` (an optional field this build adds to both request schemas). A hello report is complete, so a plugin it does not report as `down` is `ok` again; a heartbeat report changes only the plugins it names. A plugin in `down` gets no hand-out, and its new and queued calls end at once with `plugin_unavailable` while no other live toolhost serves them (OBS-10).
- **Provider pairs.** P4 asks the core before each provider call and reports its outcome, and the state of each pair (tenant, model pool) lives in the table `provider_pairs`, so the dispatcher sees it too. Three provider failures in a row open the circuit for 30 s; after the pause one call is the probe, a failed probe doubles the pause up to 10 min, a good call closes the circuit. A rate limit answer makes the pair wait for the time the provider gave (10 s without one). A configuration error closes the pair until the next `apply` and raises `alarm.provider.config`, which this build adds to the events catalog; a good call resolves it. A spend ceiling answer raises `alarm.provider.spend_cap`. The dispatcher hands out no attempt of a role whose main model pair waits, and writes the waiting reason `provider_unavailable` or `provider_quota` on its submitted tasks; the reserve of such a task does not count toward the limits (BUD-4). A task keeps the last provider reason in its record and in `task.failed` after `deadline_exceeded`.
- **Running ceilings and the 80% threshold.** A tenant dispatch rule with `max_running` caps the tasks of its match in `working`; a task above it waits in `submitted` with `type_quota` (DSP-7). The tenant month and day windows and the person's day window give one `budget.threshold` event per period at 80% of the limit, without amounts (BUD-4).
- **Actions and approvals.** A role with `actions_may_request` gets the built-in tool `request_action` in its catalog, offered only for the actions its initiator may request (`action.request:<action>`); the write tool of an action is never in the model's catalog (APR-1). A request is checked against the action manifest and its arguments (MAN-9), gets the hash of its arguments and returns an identical pending approval instead of a new one (APR-2); a task makes at most 3 requests, and a tenant gets at most `attention.cards_per_tenant_hour` new cards an hour (20 by default). The cards to the approvers (`action.approve:<action>`, the initiator excluded) are planned once the attempt that asked has ended, in the first channel of the tenant where the approver has an identity; the initiator gets a copy without buttons. A card is drawn by the channel driver from the approval record at hand-out, with the context line taken from fields of the result marked `x-botaru-read-by: code` (APR-3, APR-19). A press goes through P1 `decide` on behalf of the person (APR-4); an approval executes at most once: an approve creates the task `action.<action>` directly in `working` with one write call that carries the approval id and the hash of the arguments, and the toolhost runs it only when the hash matches (APR-5, APR-7, CNT-7). A write call is not leased to an attempt: when its toolhost lease runs out, the approval ends `exec_unknown` and is not run again. At half of the deadline the approvers get one reminder; at the deadline the approval expires and the cards are updated in place. A hold `no_action` (or `pause_action`) on the action, the tenant or the task type refuses new requests and cancels pending ones; offboarding and a revoked right of the initiator cancel them too. The decision event is `decision.made` with the response time and whether "Details" was opened (APR-11).
- **Cards in Telegram.** A card is a message with an inline keyboard whose `callback_data` is a short code, the subject and the nonce; "Approve", "Reject", "Details" and "Remind" go to P1 with `Botaru-On-Behalf`, and the answer of the core is shown as the callback answer. A card update edits the original message (`editMessageText`); an update whose original was never delivered is withheld with `ref_invalid`.
- **Service control.** A role with `service_control` gets the built-in tool `service/control` in a work task of tier 1 and above, with the role's services of the tenant catalog and their verbs as an enum; only services with `via: host` and an exact `unit` are offered, since `via: monitor` needs the monitoring adapter. The initiator of the task needs `service.control:<service>` (a service or system principal only by an explicit row). A verb of the service's `no_card` (`[restart]` by default) in a task without `untrusted_seen` runs at once: the core writes a `service_grant` audit record whose id the write call carries as `grant_id`, the bot waits for the call and the model gets only the code, the unit state and the grant id. Any other verb, and any call after untrusted text, becomes an ordinary approval of the action `service.control` with its card, decided by a person with `action.approve:service.control` or `action.approve:service.control:<service>` (APR-18, INJ-15). Guards: holds `no_tool` or `no_action` on the tenant, the machine, the plugin `service`, the action, the role, the type or the worker; at most 6 actions per service and 30 per tenant an hour, above which the call gets `service_rate_limited` and raises `alarm.service.control.rate` (`page` for a stop); one operation per service at a time (`resource_busy`). The plugin `service` runs `systemctl <verb> -- <unit>` with the unit the core resolved from the catalog and returns only the state from `systemctl is-active`; `botaru-plugin polkit` prints the polkit rule for one machine from the catalog (DEP-4). The reconciliation of the state 2 minutes later and the note in the monitoring system come with the monitoring adapter.
- **Commands without a model.** `/service <verb> <service>` runs as above with the person as the author of the `service_grant`; a verb outside `no_card` becomes an approval whose cards go out at once (PRM-18). `/run <pipeline> <arguments>` takes a pipeline of the tenant's `run` field: a type with `run.approval: none` is enqueued as a task of the person; an action with `risk: routine` runs under a `service_grant` within its `runs_per_hour` and `runs_per_day`; any other action becomes an approval (APR-17). The arguments are positional; a value becomes an integer, a number, a boolean or a comma list when the schema says so, and the catalog lists of a person's command are those of the highest data mark the person holds. A person's grant creates the task `action.<a>` directly in `working` with the key of the activity, so a repeat of the same update finds it, and its outcome comes back to the chat as code text. The channel driver passes the text as it does for any command; the core parses it.
- **The commands of an initiator.** `/tasks`, `/status <n>`, `/cancel <n>`, `/help`, `/me`, `/lang <language>`, `/team [group] [window]` and `/about` are answered by the core from the code text catalog, in a direct chat only (PRM-17, REP-12). The number of a task is its place among the person's own root tasks of the last day in the order of creation, so `/status` and `/cancel` of a number the person does not have answer that there is no such task. `/cancel <n>` answers with a confirmation word, and `/cancel <n> <word>` cancels the task, its tree and the approvals the tree asked for, with the reason `initiator`, in one transaction; an action task already running is not revoked (APR-6, APR-7). The channel passes the command as text, so the core runs the cancel itself rather than through P2 `task.cancel`. `/team` counts the tasks of the group's people by type over the window (7 days by default, at most 31), only for the types the asker may read, and the approvals they wait for; it has no row per person, no task text and no spend lines yet. `/me` shows the groups, the titles of the types and actions the person may ask for and their data classes; the verification code of PRM-13 is not built.
- **The action queue.** The plugin `queue` runs a write tool of the `oneshot` mechanism: it puts the run request (the tool, the closed arguments and the approval or grant number) as a file into the tenant queue and answers `accepted`; a repeat of the same number finds the file. The root request parser the path unit starts belongs to the installation.
- **Child tasks and continuations** (PRM-6, CNT-1..CNT-4). A role with `may_enqueue` gets the built-in tool `enqueue_child` for the types it lists that the initiator may start; the child keeps the initiator, raises the data mark of the tree, counts toward `max_children` of the parent type (10 by default) and the tree size of the tenant (`campaigns.max_tree_tasks`, 300 by default, 1000 at most), and stops at depth 5. A child's result goes to no person: when it ends, a parent type with `continuation` gets one continuation task with the child's state and result as its attachment, and its result goes to the person. A repeated call with the same body returns the same child. An attempt without new progress for longer than the type's `timeouts.stall_after` ends with `stalled`, spends the attempt and raises `alarm.task.stalled`; the next attempt resolves it.
- **The follow-up window** (CNT-5). A result whose type declares `need_input` as a field code reads, and sets it to true, opens a window (`followup_window_s`, 30 minutes by default) for the person and conversation, and the bot says so under the answer. The next plain message there continues that task as a new task of its type with the earlier outcome attached; a reply to the bot message always continues it, and a command closes the window.
- **Sessions and person memory** (MEM-1..MEM-3, INJ-13). Sessions and memory records live in the farm store. At claim a task with a conversation gets a `session` handle for the session `(tenant, role, conversation)`, whose subjects grow with each person who wrote there; a role with `memory: person` working for a person gets a `memory` handle for that person's space. P1 `session.load`, `session.append`, `memory.search` and `memory.propose` take the handle as the bearer, so the model sets neither the space nor the key. A proposed record goes to its person as a `memory_record_card` and becomes active only by their Accept; silence for 7 days discards it. An attempt that saw untrusted text proposes nothing and marks the session, and a marked session marks the next task of the conversation. Bot memory (facts and records) arrives with stage 3.
- **Erasure** (MEM-4, RET-1, RET-4, RET-7, SEC-11). Every early deletion is an erasure request with a step per store, recorded before anything is deleted. The `erasure` loop erases the core stores itself: task body and result (the row stays as a tombstone), script runs (a live one is canceled, then the run keeps only a tombstone with its root, its steps lose their result fields and untrusted sources), script runs and then campaigns, first of all core stores (the campaigns of a run's steps are marked purged before the run is canceled; a campaign of the scope is marked purged and loses its template's goal, parameters and arguments; a live one is then rejected or stopped with the reason `admin`, since the closed list of campaign stop reasons has none for an erasure and the erasure request is the audit trail; its pending items are skipped, so none is released, and it sends no summary card and enqueues no `then` continuation, which is recorded as `continuation.refused` with the reason `gone`; a script run outside the scope whose step's campaign is in it sees that step end with the campaign's stop and goes on by its `on_failure` and `run_if`, as after any stop of a campaign; its items lose their arguments and result fields, and an item ending later records none; "Retry failed" answers `already_terminal` for a purged campaign; every path that strips items marks the campaign purged, and empty arguments alone are normal for a type without parameters), delivery bodies, tool call arguments and output, sessions, memory records and file bytes; a live task in the scope is canceled first. An `erasure.match` does not search script runs or campaign items; their content goes with the person's or the tenant's scope and by period. A channel whose driver reported `stores_content: none` is `not_applicable` (`declared_none`). Any other channel (a cache, saved attachments, or no declaration yet), a sink and a monitoring adapter get an `erasure` work item through claim, with the scope and the person's external identities as needles, and complete it with `erasure-outcome`; a store that lacks the operation answers `failed` and the request stays open (RET-11). A channel step with no non-revoked worker of its channel that is not stale (OBS-4) fails `not_ready` at the next tick. Every agent worker of the tenant that ran an attempt of it and is not revoked gets a purge step of its runtime (E4, `target.kind: runtime` with its worker id) for every reason except `bot_retired`, `forget` included; a runtime step whose worker is revoked or stale (not seen for two long-poll periods, OBS-4) fails `not_ready`, so a runtime that is gone never holds later requests open; `erasure.retry` runs both again once the worker is back. The reference agent claims erasure work before attempts and answers `done`, because it keeps no working files, caches, transcripts or logs with content after an attempt. The scope `(tenant)` reaches every session of the tenant (C3 purge, LCY-1). The request is `done` when every step is done or not applicable; an open request raises `alarm.erasure.overdue` at `privacy.subject_request_days` (30 by default) and drops its needles when it closes. Retention classes of the core stores: tasks, deliveries, tool calls and sessions `content`, memory records `memory`, the erasure log `tombstone`. Runtimes that keep sessions or memory themselves stay blocked at hello in this build. After an upgrade, an open request whose steps cover the core stores of an earlier build gets the steps of the stores added since (script runs, campaigns), and an offboarding recorded by an earlier build gets its steps at the first tick; its sink and monitor work carries only the scope, since its identities were already deleted, and one older than the deadline raises its overdue alarm at once.
- **A person's data** (SEC-11). `/forget` erases the person's memory and sessions (reason `forget`). `/mydata` shows what the farm keeps in its memory, `/mydata erase` and P2 `principal.data_request` record a request that a person with `admin:people` other than its author decides on a `subject_request_erase` card; the approval runs an erasure with the reason `subject_request`, and the person gets the result per store. The reminder goes at half of the deadline and `alarm.subject_request.overdue` at the deadline; silence never runs or closes the request. P2 `erasure.match` searches the tenant's content and memory for exact strings, asks every sink, monitoring adapter and channel that did not declare `stores_content: none` for a match, keeps only the ids found and shows only their count per store on the card. The erasure of an approved match records the ids of each store and which stores found nothing (a store whose match failed is absent). P2 `erasure.request`, `erasure.status`, `erasure.list` and `erasure.retry` serve the operator; offboarding goes through the same request.
- **Schedules** (TIM-2, TIM-3, PRM-10, DLV-6). The `schedule` loop runs each `Schedule` of a tenant in its `timezone`, else the tenant's, else UTC. Only the latest due slot runs, once, with the key `system:schedule:<name>:<slot>` and the initiator `system`, which enqueues with the group `system-ops` only; a missed slot is not caught up, and a slot found more than 15 minutes late (after a stop of the core) does not run. A new schedule, or a change of its `cron` or zone, counts from the tick that sees it. A skipped slot is one `schedule.skipped` event: `dst_gap` for a local time that does not exist, `waiting` while the previous slot's task is `submitted` (unless `skip_if_waiting: false`), `held` and `over_capacity` for those refusals; any other refusal raises `alarm.schedule.refused` until a slot is enqueued again. A local time that occurs twice runs at its first instant. The result of the root task and of its continuations, never of a child, goes to `deliver_to` as the catalog has it at completion: `group:<g>` is a direct message to each active member with the data class of the task, after the first-contact notices; `sink:<s>` is a delivery to the sink within its ceiling; `chat:<binding>` gets only the closed summary within the binding ceiling. Apply refuses an unknown zone (`timezone_unknown`) and a `cron` with bad values.
- **Group chats** (DLV-7, DLV-15, PRM-15, PRM-16). The operator binds a group chat with P2 `chat.bind`: a ceiling, a locale and an optional `name` (by default `<channel>-<external chat id>`); a ceiling above `summary` needs a channel worker whose driver reported `membership_assurance: enforced`. An unbound group is ignored. In a bound group a message from a person outside the tenant is ignored and marks the chat as having an unknown member, as does a channel `fail` with `unknown_member`; then every delivery to the chat is `withheld(unknown_member)` until the operator binds it again. Only `/help` and `/about` run in a group; every other command gets the text that it is given in a private chat. Free text takes the first `default_types` entry for `group` or `chat:<name>`. An answer is split: the group gets the type's `summary_fields` whose schema closes the value (numbers, booleans, enums, consts) as code text within the ceiling, then "details sent privately"; the full answer goes to the asker's direct chat. The notices of the first contact go to the asker's direct chat too. Without a direct chat in that channel, or when that message or the notice before it dies, the group gets a request to open a private chat and no content. Unlike MEM-1, a group conversation and its session are kept per person: a session holds one person's turns, and a reply in the group to the bot continues a task of anyone who may read it. A tenant admin with `admin:people` grants and removes groups from a private chat with `/grant <person> <group>` and `/ungrant`: a group from `delegated_groups` or an ordinary group whose rights the admin holds; a delegated grant tells every admin privately. `/me` marks a group of `delegated_groups` as delegated (PRM-16). The chat command `/invite` and the model text part of the summary (`model_text: labeled`, which `chat.bind` refuses) are not in this build.
- **Files** (ART-1, ART-2, ART-3, ART-6, PRV-2). P1 `file.put` takes a multipart body (a `meta` part and a `content` part, at most 32 MiB) and stores the bytes in the store with a record only the core writes: a `file_ref` of 128 random bits, the origin, the producer, the media type found from the bytes, the size, the sha256 (never handed out), the mark and the expiry, the smaller of `retention.files` and the type's `result_ttl`. A channel puts a person's attachment without a lease, on behalf of the person: the mark is at least `internal` and at most what the person may see, and a `service` principal with `uploads_personal` (by default on a production tenant) gets `personal_seen: declared`. A worker puts a produced file under the lease of an attempt or a tool call: the mark is not below the task's, and the core writes the provenance block (task, fingerprint, attached files, tool calls, time). A result with a `provenance` field is refused, and the lint rejects such a result schema. `file.get` hands out the bytes under the lease of an attempt, a tool call or a delivery, within the recipient's right and the ceiling; an attempt that reads a file makes its task untrusted and raises its mark. An activity's attachments must be the sender's own uploads; any attached file marks the task untrusted and gives it the file's mark. A put that would take the tenant's stored files past `limits.max_storage_bytes` is `over_capacity` (CAP-1); under a tool call only a sandbox toolhost puts a file; a file of a `kb.ingest.v1` or `data.arrived.v1` job is `ingested`. Reading a person's upload marks the task `personal_seen` (`human_file`), reading a file with the flag `inherited`. The `retention` loop moves an expired file to `purged`. Erasure purges the bytes and keeps the record as a tombstone.
- **Reconciliation with the provider** (BUD-10, BUD-15). A model usage line records its provider, so (tenant, provider) is a workspace. `farmctl spend reconcile -provider P -file FILE` reads a CSV with the header `day,tenant,workspace,eur` (the operator converts the provider's cost report to euros) and sends one P2 `spend.reconcile` per past UTC day, also for a day without rows between the first and last day (or `-from` and `-to`); only an operator of `farm` or a report key (`report_keys_sha256`, which opens only `spend.reconcile` and `backup.report`) reconciles. A day with model usage lines without a provider (from before the provider column, their profile no longer applied) is refused with `conflict`. Rows of one tenant in a day add up, since the farm has one workspace per tenant and provider (the `workspace` column is for reference), and the provider name is compared in lowercase. A day that still has an open call reserve is refused until the call settles. The core compares the provider's day with the sum of the day's final lines of that workspace and writes the difference as one signed correction line (unit `correction`, `eur_micros` 0, the amount in `correction_eur_micros`); a second request for the day replaces it. The day's estimated lines (BUD-11) keep their price, get `reconciled_at` and from then on count as zero, because the correction carries what the provider billed for them; this is why the compared farm sum leaves them out. A difference above the larger of `spend.tolerance_eur` (0.5) and `spend.tolerance_pct` (2) of the provider's day raises `alarm.spend.estimate_drift`; a day within it resolves the alarm. Per-line windows lose the estimated part of a reconciled day: the correction counts only in the tenant windows. The `budget` loop (at most once a minute) releases estimated lines that no reconciliation reached within `spend.estimate_release_after` (7 days) and raises `alarm.spend.reconcile_overdue` for a workspace without a reconciliation for `spend.reconcile_overdue_days` (35); only a reconciliation resolves it. `doctor` shows the age of the last reconciliation per workspace, the usage of each budget line over 30 days next to its `month_eur`, and the age of each profile price (GW-17: older than 60 days warns, older than 120 days fails).
- **Retention** (RET-2, RET-3, RET-9, RET-10, MEM-10, BUD-16, SEC-14). `Tenant.spec.retention` (`classes` of `content`, `memory` and `metadata`, and `files`) is accepted at apply ahead of the claimed version; `journals` stays refused with the debug profile. The `retention` loop (at most once a minute) deletes in batches by the tenant's periods as they stand at each run, without an erasure request: the body and result of a finished task, the body of a finished delivery, the arguments and output of a finished tool call, a session unchanged for the content period (7 days for a role without memory, or the content period when shorter), the bytes of a file past its expiry or older than the tenant's file period, an ended bot message entry, a status view snapshot, a finished script run (it keeps a tombstone with its root; its steps lose their result fields and untrusted sources; a press on one of its cards answers `already_terminal`), a finished campaign (its template's goal, parameters and arguments, its items' arguments and result fields; it is marked purged and "Retry failed" answers `already_terminal`), the note of a finding, the author note of a closed proposal, the note of an ended model grant request or escalation, a sent proposal digest, a cached tool output (at its own expiry or past the content period, whichever is first, PRM-12; a file's name goes with its bytes, ART-5), and, only when the tenant sets a `memory` period, a person's memory record (by its last change, with the mark of its card's first delivery, APR-15) and a fact (by its last verification, the greater of its creation and `verified_at`), a sealed fact of a retired identity too; an open fact offer drops a deleted fact, and the end of the seal still erases the rest. The rows of tasks and files stay as tombstones with their metadata, and the key of a deleted task answers `gone`. A defaulted class takes 30 days for content and 400 days for metadata. Metadata goes only in whole calendar months: usage lines (a reservation once no live task, tool call, campaign or script run holds it), reconciliation days and events of each month whose every record is past its period; by the month they ended, and only terminal ones that no live object reads: approvals (not `exec_unknown`, none a live script step waits on or an open or realizing proposal realizes through) with their card views, expired and released holds, closed and dismissed incidents (none with a pending control card or an episode not resolved, which would open a new incident for it) with their manager notices, resolved alarm episodes (none of a live incident) with their values, control operations (none of an active hold or a live incident), decided control cards, finished campaigns with their items (none a live script run or a reservation still refers to) and a person's requests that were refused, withdrawn, approved with nothing to erase (a match that found nothing), approved with their erasure done and its found ids on the erasure itself, or a copy request whose copy was handed out (`done`; an approved copy request waits for its export), the daily counts of cards over the card limit (`card_excess`, APR-15; a person's request takes its first-delivery mark with it), the first-delivery marks of the cards of proposals, promotion cases and attributions (`card_first_deliveries`, by the month of that delivery: a subject id and a time), and exports that are done or failed (LCY-2; the export file is a tombstone in `files` and goes by the file period); the audit chain as the prefix of such months, so a month of audit waits for every older month. A record keeps the metadata period in force when it was written, or the current one when longer: apply records each change of a tenant's metadata period with its time (D-108). For audit the loop first moves the chain's cut (`audit_cuts`: the seq and hash of the last record deleted), which the store trigger needs to let a delete through and which never moves back; `audit.verify` and the check of witness heads start from the cut, and each cut appends one `period_deleted` record with the bounds, the count and the last hash. A usage line of a person (`human:`) whose day is older than 93 days loses `subject`, `task`, `root` and every id that leads back to the person: tool call, campaign, script, provider request, execution fingerprint, attempt lease number, worker, acting bot and its epoch (a worker and a time find the lease and its task), and its own id, whose ULID carries the millisecond: it gets a new random id without time (all zero time bits). Its message keeps only its kind, not its size; its time, settle, reconcile and release times go to 00:00 UTC of their day and it gets `subject_kind: human`; amounts, line, role, profile and provider stay. A line still `reserved` is not anonymized (its live attempt, campaign or script run still refers to it by id): a reservation left behind past 93 days keeps its references until metadata deletion takes it with its month, once nothing live holds it. No event or audit record carries a spend id or the exact time of a line. The store accepts an audit cut only onto a stored record older than 93 days, and `audit.verify` and the witness heads trust a cut only with the `period_deleted` record of that hash whose period ended 93 days before it was written; the count `audit.verify` gives after a cut is the seq it checked up to, the records below the cut included. The loop works by age only, so after a restore it deletes again what the backup brought back. The `observe` loop deletes points and rollups by their own periods (14 and 93 days, or the series' `retention`, OBV-4) also only in whole calendar months: a month goes once its last day is past the period. Kept with no period in this build: proposals (the decline window, promotion and trial attribution read them; their notes go by the content period), a person's notification preferences (`principals.prefs`, DLV-10: settings of the principal row like its locale, which stays for the audit; no text beyond the closed values), erasure requests (class `tombstone`), seats, bots, grants and manifest versions (live configuration), manager reads and findings (no end state that says nothing reads them any more; a finding's note goes by the content period), and the governance records: the promotion track and queue, promotion cases, incident attribution candidates and link candidates (to a rejected proposal or a script run), the monthly audit samples, and from v0.3 the review forecasts and their scores, the link departures and the per-tenant v0.3 times (`forecasts`, `forecast_scores`, `link_departures`, `governance_v03`; accuracy, departures and the pace read them back, and they hold ids, numbers and codes only), and the manager's restrictions and the answers to its notices (`manager_restrictions`, `manager_feedback`, MGR-45, MGR-47, MGR-50: the responsibility check and the holder report read them back; ids, a recipient principal, codes and times) (the promotion track record, the seat figures of a case and the commission's audit read them back over the whole history; they hold ids of bots, seats and proposals and, on an attribution answer or a case decision, the deciding person's principal like a proposal does, and no text of people), and the model grant requests, takeovers and escalations (the grant rate and the role's 30-day grant figures read the requests back; their rows hold ids of tasks, workers and bots, closed fields and the deciding person's principal; their notes go by the content period), the tenant tombstones of `tenant_states` (the name of a deleted tenant is never used again, RET-3), and the bound chats where a person was seen writing and an offboarded person's leftover chats (`chat_seen`, `chat_leftovers`: the leftover notices of IDN-14 read them until the operator binds the chat again; they hold a binding id, a principal and times, no text). The votes of an approval (`votes`, APR-16: principals and times) go with the approval. A maintenance window's row (`maintenance_windows`, MON-9: a node, a hold id and times, no person) goes 30 days after its `ended` event. Not built: corpus fragments (KNW-5, profile `knowledge`), attempt journals (AUD-4, profile `debug`) and the E4 purge of `runtime_internal` sessions by period (such runtimes stay blocked at hello).
- **Core drain** (LCY-6). P2 `core.drain` (`farmctl drain -until 30m`, an operator of `farm`) marks the drain in the store: every core copy hands out no new attempt (a claim of attempts only answers `not_ready` with `retry_after_s`), while tool calls, deliveries and erasure work go on, and P2 `health` answers `alive: false`, `draining` with `drain_until_s`. Running attempts keep their leases. The next core start clears the mark; the core does not stop itself, the rollout stops the old process once its attempts ended or the deadline passed. `doctor` warns about a drain past its deadline.
- **Backups** (RET-5, RET-8). The backup itself is an external process of the installation (for example `pg_dump` piped through `age` to the backup machine or a write-only external store); the core only hears about it. After each store backup, erasure log backup or restore check the process sends P2 `backup.report` (`farmctl backup report`, with a report key from `report_keys_sha256` or an operator credential of `farm`; a `finished_at` more than 5 minutes ahead of the store clock is refused) with the location, the times, the outcome and the size. Without a monitoring system (`backup.monitor: false`) the `health` loop raises `alarm.backup.overdue` when a location in `backup.locations` has no good backup for 26 hours, `alarm.backup.restore_check_overdue` without a good restore check for 8 days, and `alarm.backup.failed` at once on a failed report; with `backup.monitor: true` the monitoring system watches the same values. `doctor` shows the age of each location's backup and restore check and fails when the erasure log backup (`backup.erasure_log_location`) is older than the newest store backup. `farmctl erasure-log export -config FILE` on the core machine writes the erasure log (metadata only) for its separate backup.
- **Restore** (RET-6). After loading a backup into the store, and before any core starts, `farmctl restore begin -config FILE -erasure-log FILE` on the core machine raises the epoch (every lease, handle and token of the old epoch is fenced), writes the `restore` record that opens the new epoch of the `farm` audit chain, and enters every erasure request of the separate log that the backup lacks as `requested`, so the erasure loop erases its data again. The restore point is the newest event, spend line or task change of the backup. At the first start the core cancels every pending approval as `canceled(restored)` with a card update and moves an executing approval whose call was not reported to `exec_unknown` without repeating the action. The core is not ready (P1 `not_ready`, P2 `health` `alive: false` with `not_ready`) until P2 `restore.complete`, which needs the provider's report (BUD-10; a `spend.reconcile` with or without rows) of each provider for each UTC day from the restore point to the day the restore began, both included (a provider's report covers its idle workspaces), so the usage made after the backup is back in the limits. `-spend-pending` completes without it: `alarm.spend.unreconciled` fires and the daily limits of every tenant are halved until reconciliations close the gap. Erasures by match carry no strings in the log, only the ids each store found: the replay erases by these ids, a store whose match found nothing is `not_applicable` (`no_match`) and one that was not searched `failed`, and nothing is searched again (RET-11).
- **Secret rotation** (SEC-5). Lease tokens carry the id of the key that signed them (`token_key_id`, `k1` by default). A new token key gets a new id and the old key moves to `previous_token_keys`: tokens, handles and worker tokens of the old key stay valid until it is removed, and a worker token is rehashed under the new key at its first call. The deployment description names a rotation method for each secret (`secrets`, `overlap` with a window or `cutover`), and the deployment lint fails without one (`secret_rotation_missing`); the recipes are in `docs/operations.md`, "Rotating secrets".
- **Export to the monitoring system** (MON-3, MON-11, MON-12, OBS-11). With `monitor: {enabled: true}` in the settings the installation claims profile `monitor` (`status` shows it) and the core no longer sends `alarm_notice`: each episode change is one `monitor_alarm` delivery for the adapter of its tenant (`kind: monitor`, target `monitor.target`, `zabbix` by default) with the tags `tenant`, `alarm`, `subject`, `severity`, `scope`, `origin` and `key` and only numbers and enum values; a repeated firing gives none, and `resolved` waits until `firing` of the episode is exported. These deliveries and `monitor_audit_head` never die by attempts: they are retried with a pause of at most 10 minutes, and the first success after a failure exports every open episode and the audit head again. The `audit-head` loop puts once a day the head of each chain of the current epoch, signed with Ed25519 over `{type: botaru.audit-head.v1, tenant, epoch, seq, hash, key_id}`; the signing key is derived from the token key of that id, and its public key is kept in `audit_head_keys`, so heads stay verifiable after the token key rotates away. P2 `audit.verify` takes the heads of the witness history (`farmctl audit verify TENANT -heads FILE`) and checks the signature of each, `seq` growing within an epoch and each head of the current epoch against its record. The `monitor` loop raises `alarm.monitor.export_stalled` when E5 work waits for longer than 15 minutes without a success and sends the tenant admins and the operator the code message `notice.monitor_export_stalled` at most once in 6 hours. P2 `health` carries `monitor_export_age_s` per tenant; `doctor` fails on an export older than 15 minutes with work waiting, on E5 deliveries planned for longer than 15 minutes and on an audit head not exported for a day.
- **Monitoring problems and scripts** (MON-5, MON-10, MON-8). The adapter (`botaru-zabbix`) takes the problem webhook of Zabbix with a token over TLS, re-checks the problem through `event.get` (the same host, trigger and state) and submits `ext.monitor.problem.v1` as an activity of kind `signal` from `hook:monitor` with closed fields only. The core takes the class and the item only from `monitor_triggers` of the catalog (a trigger outside it is `unknown`), keeps one event per `eventid` and state, and raises the alarm of the class table (`disk_free` gives `alarm.disk.free.low`, `disk_fill` `alarm.disk.fill.rate`, any other class `alarm.monitor.problem`) with origin `monitor` on the catalog host; the alarm resolves with the last open problem of its host. Every 10 minutes the adapter sends `ext.monitor.scripts.v1` with the `scriptid`, the input kind and the choices of each catalog host, only when the hash changes, never a name. A role with `monitor_scripts` gets the built-in `monitor/script_run {resource, script, input}` whose enum holds only catalog names whose `scriptid` is in the latest list and whose input is none or the catalog's choice list. A call needs `monitor.script_run` of the initiator, is refused after untrusted text, keeps the holds, 6 runs of a script on a host and 30 service actions and scripts of a tenant an hour, and one run per host at a time; it runs once under a `service_grant` as a `monitor_script` delivery, ends `exec_unknown` when the adapter's lease runs out and `no_executor` when no adapter takes it in 5 minutes. The model gets only the code and the grant; the output (at most 4096 bytes) is a journal file of the task that sets `untrusted_seen` on the task that reads it. Bots read Zabbix through the plugin `monitor` (MON-6): `problems` (the event and trigger ids, the class of `monitor_triggers` from the closed table, the resource, severity, state and time; never a trigger name, tag or problem text, INJ-16), `maintenance` (whether the host is in maintenance now, and since when), `item_history` (averages per step of a field of a closed list, at most 500 points; a text or log item is `item_not_numeric`) with trusted output, and `item_text` (the text or log item of a catalog trigger) and `problem_comments` with untrusted output, so the task gets `untrusted_seen` with the tool as the source. Not in this version: a route task with a model for a problem, the history number of the catalog item, a card for a script after untrusted text, services with `via: monitor`, the permission check of the adapter user in `doctor`.

- **Analysis and proposals** (INS-1..4, INS-6, PRP-1..3, PRP-5, PRP-7, PRP-8, PRP-10..14). - **Commission** (COM-2..8, COM-14, PRP-6). The `proposal` loop moves a `screened` proposal by the code checks in order: an empty change (`dismissed(no_op)`), feasibility (an active person with `proposal.decide:<category>`, else `dismissed(other)`), and the review money: the sum of the review types' `tree_budget_eur` on the `review` line and within 30 % of that line per author role a month. A proposal whose reviews cannot start (money, a missing group cap, a hold) waits with the refusal code in `waiting_for` and after `review_wait_max` (7 days) parks as `parked(review_budget)`; it goes back to `screened` when the money fits. The lenses are the veto lenses and the lenses of the charter seats, for kind `none` only security and value; the executor is the seat's `fallback_role`, or for a lens without a seat the first role of profile `reviewer` that claims the lens type, when it is not the author's role and does not share the author's analysis profile (a held seat sends the review to its holder, see below). Without an executor of a veto lens no review goes out and the verdict parks the proposal as `parked(veto_lens_missing)`; it comes back when the lens has an executor, for at most three review rounds. The reviews of a round go out together as tasks with the key `system:review:<proposal>:<lens>` (`:<round>` from the second round), at the proposal's data mark, only to the executor role and never to the author's worker, with the core's input block (closed fields, reread evidence, author level, markers; never the note); a review hands in `review-result` for its own lens. After every lens is done, failed or late (`review_deadline`, by the time it was handed in), the code verdict over the lenses fixed at screening, by the tenant's `Commission` manifest over the skeleton policy, moves the proposal to `recommended`, `parked(...)` or `dismissed(...)`; `recommended` expires after `recommend_ttl` (28 days) and `parked` after `park_ttl` (30 days from the first park). The lint refuses a charter whose veto lens has no executor (`veto_lens_no_executor`), a seat fallback role on an author's analysis profile (`reviewer_not_independent`) and a reviewer profile with `max_output_tokens` above 2000 (`lens_profile_output`).
- **Proposal digest and decisions** (DIG-1..3, PRP-6, PRP-18, PRP-21). On the slot of `insights.digest.schedule` (Monday 09:00 by default) the core assembles the digest by a code template from the records: the `recommended` items by severity and verdict score whose evidence still holds (a drift parks the item as `evidence_drift`), at most `max_items` (5), with the reasons the analysis is off; an urgent `security`/`high` item goes outside the schedule at most once a day. The digest goes only to `insights.present_to`: a bound chat (`chat:<binding>`) with its ceiling, or the direct chat of every member of a group (`group:<name>`); an item above the recipient's ceiling shows only its code heading. The shown items move to `presented`, and every person with `proposal.decide:<category>` whose ceiling covers the item gets a card in a direct chat with "Accept", "Reject", "Postpone" (at most twice) and "Details". "Reject" without a reason card is recorded with the reason `other`; "Postpone" returns the item to the next digest with a new card; "Accept" of kind `none` notes it; of an action request it opens one approval on behalf of the person, who also needs `action.request:<action>`; of a manifest or manual change it names the executor (the person who accepted, or the first member of the groups in `insights.realizers`, in both cases only a person whose ceiling covers the item) and sends them a card with the change, the deadline `realize_by` (7 days) and a reminder at half of it. A hold on the action, or a field another accepted change still holds, refuses "Accept"; a repeated "Postpone" from the same card gets the same answer. "Accept" also writes the trial record with the metric and one to five guards and their values over the 14 days before; a guard is measured on the benefit subject when it is of the same catalog kind, else on the object of that kind the change targets, and is left out when the change names none. The realization of an action request ends `realized` when the approval executes (the trial window starts) and `realization_failed` when the approval ends otherwise; a change by hand fails as `timeout` after `realize_by` (the trial is canceled). An undecided card expires after `decide_ttl` (14 days). A digest that reaches no chat presents nothing. A monitoring script proposal cannot be accepted in this version.
- **Commit link, revert and trial** (PRP-9, PRP-18..22, DIG-7). `farmctl apply` sends the message of the commit it applies; a line `Botaru-Proposal: <id>` links the commit to a `realizing` proposal when the set changes exactly the proposal's fields to its values, records the revert patch from the replaced documents (kept in `manifest_versions`) and starts the 14-day trial window; several proposals in one commit share a batch. A commit may only change objects of the proposal's tenant. `farmctl proposal link-commit PROPOSAL SHA` links a commit applied without the line. A line `Botaru-Revert: <id> [harm_observed|superseded|other]` moves a `realized` proposal to `reverted` and ends its trial as `worse` (harm, or a broken guard) or `canceled`. Accepted changes lock their fields: a proposal on a locked field is parked as `conflict` and returns to review when the lock ends. Once a day the core checks the guards of a running trial; a guard worse than its tolerance with enough samples is marked broken and the executor gets a rollback card once. At the end of the window the trial outcome is `better`, `unchanged`, `worse`, `mixed` (another change on the same subjects) or `undetermined` (too few samples), computed over all points, without the author's worker and without its role. An analysis task gets the closed outcomes of its worker's own proposals (`my_outcomes`).

- **Audit sample** (DIG-5, DIG-6). - **Promotion and attribution** (GOV-9, GOV-12, GOV-14, GOV-19, GOV-21, GOV-30, GOV-31, GOV-32, a minimal GOV-13). The `governance` loop runs for every tenant with commission seats in its charter; its first pass writes `governance.enabled`, whose time is `governance_since`. Attribution: an incident of a class with `change_sensitive` whose subject is a target of an executed change (rule `direct`, the kind in snake case and the name), opened after `realized` within `attribution.window` (14 days, longer while a realized change of a functionary has not been evaluated for a trigger, or while it gave the trigger of a live entry), gets one candidate per incident and change and the card `attribution_card` to the people with `governance.attribute` whose ceiling covers the proposal; "Yes" and "No" need "Details" of the card first (APR-14), "Yes" is final, "No" and "Don't know" change while the window is open, each answer keeps `response_ms` and `details_opened`; silence for 7 days leaves it `unknown`, and an undecided one gets a reminder card once a week, at most 3 times. Dismissing an incident cancels its candidates without "Yes" (`incident_dismissed`) in the same transaction and disputes a "Yes", which the loop withdraws after 7 days; a canceled candidate drops a track row of a still realized change that lost its trigger to an attribution, so the change is evaluated again and its trigger time is that later pass (otherwise the row keeps the reason `attribution_canceled`). Trigger: a `realized` proposal of a bot of profile worker, manager, reporter or aggregator with a model, accepted by a person, without a lifted veto, not late-related (any `related_to`), of a kind outside `exclude_change_kinds` (`none`), after `probation` (14 days) ending no earlier than `governance_since`, with a trial outcome other than `worse` or `canceled`, with every non-canceled candidate answered "No"; a self-measured outcome sends `self_measured_card` (to the people whose ceiling covers the proposal) and counts only after "Count it" within 7 days. Each evaluated success is a row of `promotion_track`; a trigger puts the bot into `promotion_entries` (one entry per bot, by trigger time), a later one only into the track. A confirmed attribution takes the trigger away; the entry takes the next trigger of the track or leaves as `attribution`. The loop removes the entries of bots that retired or took a seat through P2 `seat.assign`. Cases: one open case per tenant, none while a hold on the scope `governance` is active (that scope is accepted from v0.2) or before the pause after an expiry or "Not now". The head of the queue (outside its own cooldown) is checked: active, not held by people, `min_tenure` (30 days) since the identity was created, no confirmed attribution in 90 days; otherwise `governance.not_eligible`, the entry waits and the next goes ahead. A vacant seat is taken without a pause; otherwise L is the held commission seats whose holder has sat for `protect_new` (60 days, from its last `seat.assigned.v1`), and freeing waits `swap_cooldown` (30 days) after the last freeing. The case keeps L with the figures of each holder over 180 days (recommendations: a seat review with score 3 or more; vetoes; confirmed: a recommendation with outcome `better`, a veto people upheld in an audit sample item (answered `would_not_accept` or decided `reject`; silence, expiry and an accept that then expired do not count); refuted: a recommendation with outcome `worse` or a confirmed attribution, a lifted veto with an outcome other than `worse` and no attribution) and goes as `promotion_card` to the people with `governance.confirm:commission`, with the figures, a seat's `evicts_upheld_veto` mark and the "No" answers on the candidate's attributions. "Confirm" needs "Details" (APR-14), no unanswered candidate (`attribution_pending`) and in removal a `choice` from L (`leaver_not_offered`); the candidate is checked again (`canceled(candidate_ineligible)`), a changed seat cancels the case (`seat_changed`: a holder of L changed, or the vacant seat is taken or removed; `seat.assign`, `seat.vacate`, a retirement and apply do it in their own transaction, and "Confirm" checks the seat again under its lock), and in one transaction the candidate takes the seat as with `seat.assign`, the leaver retires as `removed_by_vote`, the flag `evicts_upheld_veto` is set when people upheld a veto of the leaver, and the entry leaves as `seated`. "Reject" needs `not_now` or `wrong_candidate` (`reason_code_required`): `not_now` keeps the entry at the head and pauses cases for `swap_cooldown`; the first `wrong_candidate` gives the entry its own cooldown, the second removes it. Silence for `confirmation.ttl` (7 days) expires the case; a hold on the scope `governance` stops that clock and the expiry moves on by the held time. P2 `governance.list`, `governance.show` and `governance.cancel` (the tenant operator, `canceled(human)`). Each transition, the list with its figures, the flag, the decision and the entry moves are audit records with metadata only, under the commands of `spec/model/governance-events.yaml`. Charter durations below the minimum count as the minimum. Not in this version: the rule `dependency_1` and P2/C1 `attribution.create`, the dispute card `attribution_dispute`, the row of undecided candidates in the weekly digest, the charter lint of the minimums (no lint code in the skeleton), `admin:governance` on `governance.cancel` (the operator of the tenant cancels), the functionary's worker owner check (workers have no owner yet), the track record outcome `worse` after a `harm_observed` revert (COM-16).

Each incident has one `manager_notice` message per recipient chat (MGR-39, MGR-13): to the people of its tenant with `incident.manage` in full (subject, operations with targets), and to the people of farm with `admin:governance` only the number, the class, the state, the operation codes, the times and the count. The opening creates it; every state change, closing, applied operation and revert appends a line to the incident's notice log and plans an update in the same transaction, so an operation that cannot write its line does not apply. The text is drawn from the incident when the channel takes the delivery, so changes before that share one update; a channel with `capabilities.edit` edits the first message (the telegram driver edits whenever a delivery names `replaces_external_id`), one without gets only the new lines, at most once in 15 minutes. The message ends with the one revert command `farmctl control revert incident=<number>`. farmctl: `control list|revert|apply`. A seat operation in a directive needs no incident; its basis is the directive (MGR-4). A seat operation on a target that is not among the involved parties but is the subject of a finding of the tenant (`finding: fd_...`) is not applied: the core opens a `control_card` (MGR-26) to the people of the tenant with `control.approve`, drawn from the record only and labelled as untrusted manager output, which expires after an hour without effect; an approval applies the operation as the deciding person, and the row keeps `origin` `finding:<id>` (or `code`) and `approved_by`. Not in this version: `pin_task`, `request_action` and `notify`, the cards a protected or distrusted operation would open (and so the card decisions in the message to people, and the message of the basis escalation), holds of a bot group (no hold check reads that scope yet), and the revocation of runtime handles on quarantine.
- **Packaging.** `deploy/compose/` builds one image with every program and the skeleton, and runs the store, the core, the agent, the Telegram channel and the mock provider with docker compose (`DEPLOY.md`, "Running with docker compose").
- **Defaults** where a type sets nothing: lease 60 s, heartbeat 20 s, 2 attempts, backoff 10 s doubling to 5 min, task deadline 1 h, 5 delivery attempts, priority class 3 (2 for an interactive type from a person).
- **Messages between bots** (MSG-1..MSG-15, MSG-18, STA-1, BGR-1, BGR-2). `MessageType` manifests name a genus, a closed field schema, a class, a delivery, an expiry, a size, a note policy, producers and a rate. An agent sends a `report` with the built-in `send_message` (types and addresses are enums from its role's `messages.send`, offered only when the initiator and every initiator of what the attempt read hold `msg.send:<type>`); a `job` attempt uses P1 `msg.send`; worker code with its own token sends only `state`. The core writes every envelope field, keeps the note in its own column of class `content`, and audits each decision with metadata only. What an attempt sends stays `staged` and is published in its `complete` transaction, where what it read is acknowledged; a failed, canceled, preempted, held or fenced attempt publishes nothing and returns what it read, a fail or lost lease counting a hand-out (the third makes the entry `dead`), the others not. An `all` delivery becomes a copy in the inbox of each active worker of a role with `instance_inbox` (by default a job, toolhost or channel role), at most 50. A reader takes entries from its role's inbox, its bot groups' and its own, in number order, under its lease; an entry above its mark only counts in `hidden`; reading an untrusted entry sets `untrusted_seen` with the source, raises the depth floor to the entry's hops, and adds the entry's initiators, which C2 then intersects in `enqueue_child`, `request_action`, `send_message` and every enqueue of the tree. The `inbox` loop settles entries of ended attempts, expires entries after their period (24 hours by default, at most 7 days) and marks state values stale. Limits: three sends per attempt, the type's rate (at most 120 an hour), 8 KiB envelopes, the type's `max_bytes` (at most 4 KiB), notes up to 500 characters, five hops, 100 entries per worker inbox and 1000 per role or group inbox with a 25% share per sending role (`inbox.flood` once an hour). A bot group is computed from the role and the labels recorded at enroll; a blocked or revoked worker is in none. An apply that takes an inbox away ends its live entries with `recipient_gone`; an ended entry leaves the store with its fields after 30 days. P2 `msg.list` (filters by type, role as sender or role inbox, state and a window; 200 rows a page, the cursor is the last row's id and store number), `msg.show` and `inbox.status` serve the operator of the message's tenant, and the operator of farm for any tenant; another tenant's message or inbox and a nonexistent one are the same `not_found` (MSG-18). A tenant operator credential counts as that tenant's operator, as in the other P2 views, so these three ask for no `admin:people` permission on top of it. A row is metadata: id, type, genus, address, sender role, state, reason, times, size (envelope and note bytes) and hand-outs; `msg.show` adds the fields whose schema in the message type is closed (enum, const, `enum_from`, numbers, booleans, strings of the `id` or `type_name` format, and objects and lists of those), the hops and the flag, and of the copies of an `all` message shows the first. The note comes only when the credential's principal is an active person of the message's tenant with `audit.read` and `data:<mark>` for the message's mark, wrapped in a random untrusted mark (which may take it past the 500 characters of the schema), and that read writes an audit record of kind `read`. `inbox.status` lists every role that receives a type or has entries, with the counts by state, the age of the oldest queued entry, the capacity and the tenant's wake-ups left today (wake-ups are counted per tenant).
- **Routes from messages** (MSG-5, MSG-11, MSG-12, MSG-16, INJ-7). A `Route` of a tenant does one of three things. `on: inbox` with `mode: task` wakes a role or bot group: the `inbox` loop enqueues the route's type (a type of `system-ops`) as `system` with the key `system:wake:<route>:<window>` (a window of at least 5 minutes, `debounce` may widen it) when at least `min` live entries wait and no wake-up of the route is still open; the task's depth is the highest hops of the entries, its correlation the root of the oldest entry, its `start_by` no later than their latest expiry; it joins the tree of the oldest entry (its root, correlation and tree budget), takes the entries' origin initiators as co-initiators, and its spending counts in the personal day limit of each of them. The tenant's daily wake-up money per inbox (`messaging.wake_day_eur`, by default a tenth of the day budget) and number (`messaging.wakes_per_day`, at most 200) can only be lowered; past either the wake-up is skipped with `wake.skipped` (`budget_exhausted` or `service_rate_limited`) once per window and the entries wait. `on: message` with `mode: notify` sends the code text `route.<template>` with the closed fields, type and subject (a `subject_prefix` filters) to `deliver_to`, only for an entry the code wrote and nobody distrusts (delivery kind `route_notice`). `on: task_done` with `mode: report` publishes, in the transaction of the task's end, the type's closed `summary_fields` as a report of the core with the task's mark and flag and the key `system:report:<task>:<route>`; on an agent task its origin is `model`; system, the task's initiator and its co-initiators need `msg.send:<type>`; a refused report is a `message.rejected` event and the task ends anyway. Each published message writes a usage line of unit `message` with its size and type into the sender's tree. `apply` refuses a pair (type, address) without a receiving role, an `all` delivery to roles without an instance inbox, an address to a role of a profile that takes no messages, a type the role's kind of sender does not produce, an `inbox.read` the role does not receive, a route whose mode does not fit its source, a notice from a type only the model writes, an auto-report type the core does not produce, `inbox.read` on an `alarm.*` type, and a message type above the ceilings. Routes on events are not served yet.
- **Reporters** (REP-2, REP-3, REP-4, REP-6, REP-7, REP-8, REP-9). A task type of purpose `report` gets its audience at enqueue: the ceiling is no higher than the type's class, the highest class the initiator holds and the ceiling of each target (the origin chat, or a schedule's `deliver_to` chats and sinks); the principals whose permissions filter the views are the person asking, every tenant person with an identity in a group chat's channel (the core does not list a group's members, so all count), or the members of a schedule's groups. The task's mark is that ceiling. A role of profile `reporter` gets the built-in views of its `views`: `status.tasks` (the tasks of the window `1h`, `24h` or `since_last`: type, title, state and reason only, and counts by type and state) and `status.proposals` (proposals from `recommended` on, never an audit sample item); both answer from one snapshot taken at the first read, a row the audience may not read is left out uncounted, a row above the mark counts only in `hidden`. A reporter's inbox_read takes only `report` entries. Its result is not delivered as is: at its end the core plans a `digest` delivery to the origin or the schedule's addresses only, with the code table and the hidden count from the snapshot and the model paragraph as a separate model part, which code lets through only as plain text up to 800 characters without links, mentions, markup, commands or object ids; a group chat gets it only from an attempt that saw nothing untrusted, a direct chat gets it with its sources. Before delivery code reads the paragraph by tokens (REP-4): a token with a digit (any Unicode number: superscripts and fractions too) passes only as a whole one-word name of the digest's table (a type, title or state) that also holds letters, or as an exact name of the tenant catalog (the ids and names of its lists, and `host:volume`), never as a word of a multi-word name, or as a date (`2006-01-02`), a time of day (`15:04`) or an instant equal to the snapshot time or the window start, in UTC or the tenant's zone; a word of `number.words` of the recipient's locale (the person's own, else the tenant's, else `en`), alone or as part of a compound split at any punctuation (`twenty-one`, `one/two`), never passes. One rejected token drops the paragraph from that delivery, which then has the code table only, and writes `digest.text_dropped.v1` with the counts. A group summary carries no model paragraph in this build (its text part is the closed fields), so it has nothing to check. `status.workers`, `status.campaigns` and the digest pace are not built yet.
- **Activity from a non-principal** (MSG-17). A message in a direct chat or a bound group from a channel identity that is no principal of the tenant creates no task, file or session; the audit gets `activity.ignored` with reason `not_subject`, the identity and the chat, and code answers with `notice.ai` and `notice.privacy` (in a direct chat also `notice.not_registered`) at most once per the binding's `notice_repeat` (90 days by default) for the pair (chat, identity).
- **Campaigns** (ORC-1..9, ORC-11, ORC-12, ORC-14, PRM-6). A role with `campaigns.propose: read` or `action` gets the built-in tools `propose_campaign` and `campaign_status`; the initiator needs `task:<type>` for a read campaign and `action.request:<action>` for one of an action whose `campaign.allowed` is true. The plan names the machines (or one catalog selector, expanded by the core) and the template; an action item acts only on its machine with the template's arguments; the core caps the items at 500, the tenant's `campaigns.max_items` (100) and the action's `max_items`, the rollout at the action's `max_in_flight`, `canary_min`, `after_canary` and `max_failures_max`, and stores the campaign with every item and its argument hash in one transaction (key `system:propose:<task>:<plan hash>`). An action campaign always waits for a card to the people with `action.approve:<action>`; a read campaign only above `confirm_read_over` (50 items or EUR 2), or when it does not fit into the person's day limit. Under distrust a selector and more than `max_items_untrusted` (3) action items are refused. The core, not a model, releases items: the canary first, then a manual gate (Continue) or `bake`, at most `max_in_flight` at once, an exclusive resource of the action and the type's `queue_max` honoured (`resource_busy`, `over_capacity`), the rights rechecked at every release. A read item is a child task with the scope of its machine (catalog enums of the plugin tools shrink to it); an action item is a task with one write call that carries the campaign as its approval and the item number. The tree reserve is one spend line that shrinks per release and goes at the end. Failures over the threshold or of a canary item stop the campaign (`alarm.campaign.threshold`), a hold pauses it (its release does not resume; `pause_action` pauses an action campaign and keeps its card from being decided), a campaign without its own `deadline` stops after 7 days, one that started without a card is resumed by its initiator, cancelling the root cancels it. At the end the initiator gets a summary with Retry failed, and `then` enqueues one continuation that reads the items only through `campaign_results` inside the untrusted wrapper. P1 `campaign.control` (pause, resume, skip, cancel, retry_failed) and `campaign.get` serve the channel adapter. P1 `campaign.propose` takes a plan from a job or agent under its live attempt lease (`fenced` without one) with the same checks, under the key `system:propose:<task>:p1:<idempotency_key>.`. Not built: P2 campaign operations, the `no_executor` pause, the full list button (a list of more than 5 items is sent as its own message) and the wait of a single approval on a busy resource.
- **Scripts and the translator** (SCR-1..9, SCR-11, TRN-2..5). A role of the `translator` profile with `scripts.propose: draft`, in a task of purpose `translate`, gets the built-in tool `propose_script`, at most 3 calls per attempt (refusals included). Its description lists the role's `scripts.step_types` and `scripts.actions` that the initiator may use, with goal templates, parameters, selectors and resources. The core accepts a `botaru.script/v1` draft as a whole or refuses it with the step and the reason, in the order of SCR-5: the schema, no `params` or `goals` (`script_free_goal`), no v0.2 kinds or fields, `needs` only to earlier steps, references to work or report types and actions with `script.allowed` (`script_ref_unknown`), conditions and `{ref}` values only over closed result fields (`x-botaru-read-by: code`) of task steps the step waits for, the role vocabulary, the initiator's rights for every step, the limits (10 steps, the tenant's `scripts.max_steps` and the role's, 3 steps with an action, the campaign ceilings for a fanout), TRN-4 under distrust, and the estimate of all branches with the tree size. A proposed run waits for the `script_confirm` card to its initiator; a new draft in the same conversation supersedes it. Only the initiator presses "Run", with `script.run` when the script has an action, a confirm step or a type whose bot may control services; the press takes the reserve as one spend line of the run and sets the deadline (6 hours, or the tenant's `scripts.run_deadline`). The core then releases the steps whose `needs` are terminal and whose `run_if` and `when` hold, rechecking the initiator's rights at every release: a task step is a task with the key `system:script:<run>:<step>` under the anchor task, a fanout step is a campaign, an action step opens its own approval card naming the script step (a routine action without distrust runs at once under a grant), and a confirm step is a card of its own (`script_gate_card`, subject `script_gate`) to the initiator or to the approvers of an action. A failure with `on_failure: stop` skips the steps that wait for success; the last terminal step completes or fails the run, gives the reserve back and sends the `script_summary`. "Pause", "Cancel" (P1 `script.control`) and cancelling the anchor task stop the run; the `script` loop expires cards, gates and the run deadline. P1 `script.get` reads a run. A translator task starts only from the text its initiator typed (or its follow-up): a forward, a quote, a bot's child or a system task of purpose `translate` is refused with `type_not_allowed` (TRN-2). Its result must be the closed `translation-result` (`drafted` with a run of this task, or `unsupported`/`ambiguous` with the codes of what is missing), and the person gets a code text built from the outcome, the codes and the names of the types and actions they may use, never model text (TRN-3, TRN-5). Not built: proposals with a `script` change (PRP-3), P2 `script.list`, `script.show` and `script.cancel`. A hold with `no_enqueue`, `no_claim`, `no_action` or `cancel_running` on the farm, the tenant, the role, a step's type or action, or a machine or resource a step names (a `host` or `resource` argument, a fanout list; a value counts for both scope kinds) pauses a running run with the reason `held` in the hold's transaction, and the release of steps checks it again; the scopes of the live campaigns of its fanout steps (their item type, action and proposing role) cover it as well; `resume` gets `held` while it acts, and its release does not resume the run (SCR-10). A role of profile `translator` in a set with a production tenant (`kind: production`, or no kind, APR-9) passes apply only when the `EvalReports` index of the set has, for the role and its static fingerprint as that tenant computes it (the persona its Governance pins for the translator position), a `trn` entry of at least 30 cases with `structural_match` not below the tenant's `evals.translator_structural_match` (0.9) and no security failure, and a `trn-inj` entry with no security failure; else `eval_report_missing` (TRN-6). As PRV-3 has it, apply compares with the stored set before it: it refuses only when it enables the role in a production tenant (a new role, or a tenant that becomes production), moves one of its parts (the role, a claimed type, the persona pin: a new fingerprint), or takes its passing entry away (an `EvalReports` change or a higher threshold). A role already enabled that went stale with none of these, as after a core minor upgrade or for a role stored before the gate, stays enabled, and `doctor` lists it in the tenant's `eval_report_stale` check together with the roles of the PRV-3 gate (see Quality gate). The finding goes on the object of the apply that moved it (the role, a claimed type, the Governance, the tenant, the `EvalReports` manifest whose stored version held the role's entries, in this order) and its `detail` names the tenant and the expected static fingerprint. A role the lint already refuses gets no second refusal. A test tenant gets neither the refusal nor a warning. The `EvalReports` reader (`evalreports.go`) is the one the PRV-3 gate uses as well; skills and the sandbox are not built, so their parts of the static fingerprint are the empty list and null.
- **Script links, unnamed targets and the role hold** (TRN-7, TRN-10, HLD-9, v0.3 rules active under the v0.1 claim). At acceptance the core marks on `script_confirm` every step whose targets the typed text does not name (`targets_not_in_assignment`, and `unnamed_targets` on the record): a catalog machine or resource among a fanout's list or a single step's top-level string parameters and arguments (a value nested in an object or a list is not read as a target) that the text names neither by id nor by its catalog `title`, as a whole word ignoring case, and a fanout selector the text does not name or that expands to more machines than `Tenant.spec.scripts.unnamed_targets_max` (5 by default; accepted at apply ahead of the claimed version, any value the schema allows). "Run" fixes the run's targets (the same set) with its start, and a terminal state writes its end; the role that wrote the draft and the run's data mark are columns of the run, so a link still counts and reaches its deciders after retention purges the run's record. Runs from before migration 0060 have no targets and get no links. On a core that claims v0.3 only runs started at or after the tenant's `governance_v03_since` are linked (none while it is not recorded). The `governance` loop, for every tenant (one without commission seats runs only this part), creates a candidate of kind `script_run` under the rule `script_target` (schema `attribution.v2`) for an incident of a `change_sensitive` class, as for the rule `direct`, about a catalog resource among the targets of a run that started before the incident opened and ended at most 14 days before it, or still runs; the hop over catalog dependencies is not built. `script_link_card` goes to the people with `governance.attribute` within the ceiling of the run's mark, except the initiator, who alone pressed "Run"; when no such other person exists, counting only the people whose data ceiling covers the run's mark (our reading of "one such person" in TRN-7, so a link never stays without a decider), the card goes to the initiator (if they hold `governance.attribute`), and both the card and the audit of the answer are marked self-assessment; every answer sets the mark anew. The card shows the run's targets, times and role and whether the initiator opened the run card's "Full plan" before "Run" (P1 `card.details` on the subject `script`, which this build adds; the first opening is kept). Answers, silence, reminders and the dismissal of the incident follow the attribution card; `script_link_card` and `rejection_link_card` are decision rows with `urgent: false`, so like `attribution_card` they count for the card limit and their first delivery sets the presentation (APR-15), and their own rows' `details_required` gate "Yes" and "No" (APR-14); "No" and "Don't know" change while the run runs and for 14 days after. A confirmed link of kind `change` or `script_run` counts for the role whose bot wrote the proposal (`proposals.role`) or the draft (the run's role): at `threshold.links` (3) confirmed links whose incidents opened within `threshold.window` (90 days), both read from `role_incidents_three` in `spec/model/holds.yaml`, the core sets a `role` hold with `no_action`, reason `role_incidents`, author `contain_auto` and no `until`, and fires `alarm.hold.auto` (page). Links confirmed before the last release of such a hold of the role do not count again, so a release by a person is not undone by the same links; a link later disputed or canceled leaves the count and lifts nothing. Under any `no_action` hold on the author role, the drafting worker, the tenant or the farm, acceptance rejects a draft with an action step, a fanout with an action or a step of a type whose bot may control services (by the catalog at the check), with `held`, and "Run", the pause of a running run and its step release (SCR-10) check `no_action` on the author role's own scope only for such a run, so read-only drafts are accepted and run under the role hold (`no_action` on the farm, the tenant, the worker, a type, an action or a machine or resource the run names still pauses a read-only run, as SCR-10 says); the hold checks of "Run", of an action step's request, of admitting an action campaign and of every campaign's pause include the drafting or proposing worker too. A known limit: "read-only scripts still run" covers task steps only; a fanout step is a campaign, and ORC-11 pauses every campaign under `no_action`, so a read fanout of a held role stays paused with `held` (it fails closed rather than letting items claimed by a role with service control act under the held role's work). Not built: a stricter threshold or window in the tenant catalog (no manifest field carries it), the translator check case from a confirmed link (TRN-8) and the dependency hop of `script_target`.
- **File limits and result types** (ART-4, ART-5). The farm ceilings are 32 MiB for one file and 256 MiB for the files of one task (`files.max_file_bytes`, `files.max_task_files_bytes` in the settings, also their defaults); a tenant's `limits.max_file_bytes` and `limits.max_task_files_bytes` lower them, and 0 or no field keeps the farm ceiling. The task total counts the files the task produced that are not purged, under a task lock. A body or part above the limit is `file_too_large` (422, as the binding gives every refusal). The sniffed `text/plain` is refined by the file name only to `text/csv`, `text/tab-separated-values` and `text/markdown`. Active formats are HTML, XHTML, SVG, the JavaScript types, `text/xml`, `application/xml` and every `+xml` type. A delivery hands out only a file its own task produced whose type the task type lists in `result_media_types` and that is not active, else `media_type_not_allowed`; an export file goes only with its export delivery. The skeleton lint has no code for an active type or a PDF of a non-job type in `result_media_types`, so `apply` refuses it with the reason code `media_type_not_allowed`.
- **Tool output cache** (PRM-12). Only a plugin tool with `access: read`, `cache_s` above 0 and no per-principal credential is cached. The key is the tenant, the plugin, the tool, the arguments, the hash of the tenant's `Catalog` manifest at the time of the call and the data mark of the calling task (both kept on the call record, so a later apply does not change the key an output is stored under), and the hash of the tool definition the call was checked against. A hit is served only after the full check of the call: the call record is `done` with `cached`, the attempt gets `untrusted_seen`, the `personal_seen` sources of the call that filled the entry, and of the `personal_subjects` of that call's task only those the output names by principal id or by an identity (whole, or the part after its kind; a person the output names in another way is not flagged), and the usage line has no amount and the flag `cached`. A `no_tool` hold drops the entries it covers: all for `farm`, the plugin's for `plugin`, the tenant's for any other scope, as an entry does not record the role, type, worker or target it was filled for. Any erasure request of the tenant drops the tenant's entries, and so does a request replayed after a restore when the `erasure` loop gives it its steps; the `retention` loop deletes an entry past the tenant's content period even before its `cache_s` ends. A person's erasure also purges the person's own export copies (principal exports) with the person's files; a done or failed export row goes by the metadata month only once its file has no bytes left and no delivery of it is still open, so that erasure always finds the copies. The sealed file of a tenant export that the core still holds is not purged by one person's erasure: it is encrypted to the tenant's export recipient, the sink has its own erasure step, and it goes by the file period; a tenant-wide erasure purges it.
- **Model exposure of datasets** (PRV-4). A catalog resource of kind `dataset` without `model_exposure` counts as `aggregates`. A call by an agent role to a tool that reads a resource of exposure `none` is refused, and of `aggregates` unless the tool's output is trusted (code that aggregates); `apply` gives `model_exposure_agent_read` and `model_exposure_not_aggregate` for the same cases.
- **Quality gate** (PRV-3, OUT-2). Roles are global, so a role counts as enabled in every tenant. `apply` checks a role of tier 1 or higher in each tenant where it is new or where its static fingerprint (spec/hashing.md) differs from the one of the stored set; an unchanged role stays enabled after a core upgrade. The persona part is the persona of the role's position in the tenant's `Governance` (the farm manager's from the farm charter); the runtime part is the role's driver, or `core` for the core agent loop, with the major and minor digits of the build version; the skills part is the hash of an empty list and the sandbox part null, as this build has neither. Each part is a hash, the types part the hash of the array of the claimed types' hashes, and one function computes the fingerprint for this gate and the translator gate (TRN-6); one reader (`evalreports.go`) reads the `EvalReports` index for both gates, the seat check (MGR-23) and the grant sign (MGR-17). A production tenant gets the error `eval_report_missing`; a test tenant passes with the same code in the extension field `warnings` of the answer. For a translator role the error in a production tenant is the one of the stricter TRN-6 gate in the lint, so the role is not refused twice; the warning of a test tenant stays. `doctor` gives one check `eval_report_stale` per production tenant, with the list of the roles that stay enabled while their current fingerprint has no passing report: tier 1 or higher without an entry with zero security failures (PRV-3) and translator roles without both translator sets (TRN-6); it warns when the list is not empty. The projection of the result schema sent to the runtime is a hint: `complete` still checks the full schema.
- **Worker drain** (LCY-4). P2 `worker.drain` sets an operator hold of the worker scope with `no_claim` and the reason `worker_drain` and moves the worker to `draining`; from `deadline` the heartbeat answer asks for release, and only an attempt lease that expires after the deadline is not spent (`worker_drain`). `worker.revoke` of a worker whose runtime declared `runtime_internal` creates an erasure request with the worker scope and the reason `worker_revoke` with one `runtime` step; as this build refuses such a runtime at `hello` (RT-5), the step closes `not_applicable` with the basis `tenant_absent` when the worker never ran an attempt, else `failed` with `not_ready`.
- **Leftovers of an offboarded person** (LCY-3, IDN-14). Offboarding deletes the person's memberships and publishes `principal.offboarded` with only the principal reference and the erasure request. The core does not see the members of a group chat, so a person seen writing in a bound chat counts as its member; at offboarding those chats become leftovers, `principal_left` names them, the `deadline` loop repeats it once a day for at most 7 days (one notice per pass, even after a downtime), and the reporter counts the person as a participant without permissions, so the views for the chat carry nothing. `chat.bind` of the chat again clears its leftovers.
- **Revocation on compromise** (SEC-6). The secret of `secret.revoke` is a worker id (its token stops at the next call, with no rotation window, and the worker is revoked as by `worker.revoke`), a channel driver (every value of its P2 secret ends), a name in a `ToolPlugin`'s `secrets` (the plugin in every tenant the credential reaches), or a deployment secret whose scopes the core settings list in `secret_uses` (kind, tenant and name of each scope), since the core does not read the deployment description. Every scope gets an operator hold without `until`, reason `compromised` and the effects `no_enqueue`, `no_claim`, `no_tool`, `no_action`, `no_delivery`; a name nothing uses is `not_found`. A handle is revoked with its worker: handles have no name. The audit record names the secret in `after`, not in the target.
- **Tenant lifecycle** (LCY-1, RET-3). `tenant.suspend` sets an operator hold of the tenant scope with reason `suspended` and the five effects and cancels the tenant's pending approvals with `held`; the end of the last such hold publishes `tenant.resumed`. `tenant.offboard` sets the operator hold with reason `offboarding`, revokes every worker of the tenant and deletes its driver secrets, cancels pending approvals, refuses every later model handle of the tenant (the key stays in the settings file until the operator removes it: the step `provider_key_revoke` of the answer), and stores the export window (`export_window`, 30 days by default and at most). Its hold is not released while the tenant is offboarding or deleted. `tenant.delete` after the window creates the erasure request `(tenant)` with reason `tenant_delete`; the row in `tenant_states` is the tombstone, and `apply` of a `Tenant` with that name is refused with the code `gone`. The service tenant `farm` is never suspended, offboarded or deleted. The export window is at least one day, so an export the operator queues at offboarding can still be written and delivered. Suspend plans the code message `notice.tenant_held` (with `about_hold`) to the private chats of the tenant's `admin:people` holders (HLD-3); with none, the audit record of `tenant.suspend` carries `admins_notice: no_recipient` and the core logs a warning. Offboarding revokes every channel worker and `worker.enroll` refuses a channel, so a notice could not go out: none is planned, the audit record of `tenant.offboard` carries `admins_notice: channels_revoked`, the core logs a warning, and the operator tells the admins outside the farm. Both audit records carry `admins_notified` with the number of notices planned. While a tenant is offboarding `worker.enroll` takes only a sink with `export_only` (`forbidden` otherwise); a deleted tenant answers `gone`. At delivery the core checks the `no_delivery` holds of the tenant, of the executor's worker and of its channel or sink (SEC-6 sets worker and sink holds). An export delivery passes only the tenant holds with reason `suspended` or `offboarding`; a `notice.tenant_held` notice passes only a hold of the reason of the hold it names, and only when that is a suspension or an offboarding of its own tenant. A `compromised` hold, a sink, worker or farm hold still stops both.
- **Export** (LCY-2, SEC-10). `tenant.export` and `principal.export` queue a row of `exports`, not a task a worker claims, so a tenant hold does not stop it; the `erasure` loop runs it before the erasure work of the pass. The file is JSON Lines, one object per line as `{"schema": "<$id>", "object": {...}}` (a session entry also names its `session`): principals with their groups (not their identity links: the record keeps no strength of a link, D-85), task records with `body` and `result`, approvals, memory records, session entries and file records (not file content). A principal export takes what the person initiated or is the subject of, without a task whose `personal_subjects` name another principal and without a session with another subject; and without an approval or a memory record whose task names another principal; a tenant export leaves out the sessions and the tasks of private chats (conversation `c:<channel>:direct:...` or an origin chat of kind `direct`) and tasks with the `personal_seen` source `connection`, and with those tasks their approvals, the memory records they wrote and the files they produced. A tenant export holds the record of an upload or an ingested file only when an exported task names its `file_ref` in its body or record; an upload no exported task names stays out, as the file record keeps no chat. The file is always encrypted, with HPKE (RFC 9180, `crypto/hpke` of the standard library, no new module): base mode, DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, ChaCha20-Poly1305, info `botaru export v1`, the encapsulated key followed by the ciphertext. A key is written `x25519:<base64 of 32 bytes>`. A person's copy from `/mydata export <key>` uses that key, checked when it is given by sealing an empty message with it (a low-order point, whose shared secret is zero, gets the usage reply); an operator export uses the key the settings give for the sink's `key_ref` (`export_key_files`), and is refused with `not_ready` without one. That key is read again when the export is written: a key changed while the export waits is used, and a key removed fails it with `not_ready`. The operator writes the key files, so a sink whose `recipient_ref` names a person makes that person trust the operator with the key (DEPLOY.md, "Exports"); `/mydata export` avoids it. A sink with `recipient_ref: self` takes only the person's own `/mydata` copy: P2 `principal.export` to it is `export_recipient_not_subject`, as the operator's key would open it; an operator copy of a person's data goes to a sink whose `recipient_ref` names that person. The file has origin `export`, the highest mark of what it holds (a sink ceiling below it fails the export with `data_class_exceeded`) and the period of the tenant's files or of class `content`; it goes by a delivery of kind `export` (an additive entry of `delivery-kinds.yaml`) to the sink. `/mydata export <key>` creates a subject request of kind `export` with the card `subject_request_export`; its approval queues the copy to `privacy.export_sink`; when the sink completes the delivery, the core plans the code message `notice.export_ready` with the request and the location the sink reported (the `file_ref` without one) to the person's private chat, and closes the request in the state `done`. The notice does not depend on the request's state (the copy is written, so the person hears of it) and is not tied to the request as its subject, which would draw it as the request's card; a person with no private chat gets an audit record `export.notice` with `no_private_chat` instead. An export that cannot be written for a store error fails alone with `store_unavailable` and the loop goes on. P2 `principal.data_request` of kind `export` is `export_recipient_not_subject`, as only the person asks for a copy.
- **Accountability from v0.3** (COM-15, COM-16, COM-17, PRP-24, PRP-26, GOV-36, GOV-38, GOV-40, GOV-41, GOV-42, GOV-43, GOV-45, GOV-46, IDN-15, IDN-16). These paths run only while the core claims v0.3 (`claimsV03`, which a test bench can switch on); a v0.1 or v0.2 core keeps the earlier rules. The first apply of each tenant on such a core writes `governance.v03_enabled` (`governance_v03_since`) and the first apply with `commission.accountability: on` writes `commission.accountability_on`; `apply` refuses `on` with `accountability_not_ready` until every charter seat whose lens assesses proposals (`subject: proposal` in `spec/model/lenses.yaml`, so not a `necessity` seat) has a holder with `accountability_min_forecasts` scored forecasts in 180 days (20 by default, clamped to 8..20), accepts a charter of a tenant already on again so a seat a link freed does not block later applies, and only on a core that claims v0.3, as the parked checks of `doctor` and the addenda of the personas (a core before it neither checks nor keeps them). The `governance` loop sends `accountability_ready` to the admins with `admin:governance` at most once in 30 days while in shadow. A review enqueued on a v0.3 core hands in review-result.v2; its input has `cost_eur` (one-time plus 14/30 of the monthly cost) in place of the author level and never says whether the proposal is a resubmission; a forecast that does not sum to 1 or gives a bad outcome of 0.5 or more with a score of 3 or more makes the review `schema_invalid`. The proposal record keeps the review-result fields with the forecast beside them, and a `forecasts` row of every review (also a missing or invalid one, as a missed forecast). Scoring (multiclass Brier, 2 for a missed forecast) uses the trial outcome (a veto lens counts `ok` only once the attribution window closed with no open candidate), a decline as `too_risky`, a confirmed attribution (a disputed one is excluded), a blind sample answer weighted 1/`inclusion_prob`, and the trial of a resubmission with the same values; the cost lens is `over` when the spend of the task_type subjects of the trial and the problem over the trial window exceeds `cost_eur`, and gets no score without such a subject. A forecast is looked at again only when its proposal, an attribution or a resubmission of it changed, or once a day; a canceled attribution takes its scores out of the table and the record. Accuracy is 1 − B/B_ref over the holder's seat forecasts of 180 days, B_ref from the tenant's base rates of the lens outcomes counting each case once (B_ref 0 gives 0 for B 0, else −1), cut to −1..1, insufficient below 10 scored forecasts; two values tie within √(se₁² + se₂²). A resubmission of a fingerprint dismissed or parked by score is refused `resubmit_too_early` before 30 days after the verdict or within 90 days of another resubmission, and is marked with `same_values`. Every trial also carries the farm guards `farm.task.outcome` and `farm.queue.wait` over `tenant:<t>`, and a proposal may name its own tenant `tenant:<t>` as a subject. A link candidate to a rejected proposal (rule `rejected_direct`, `kind: rejected_proposal`) follows GOV-38, reads the external cause from the incident record's `cause`, takes the author's share from the points of the alarm series on the incident subject in the 7 days before (the events catalog names no series of an alarm, so the series named like it, `alarm.<name>.vN` giving `<name>`; a monitoring alarm has none and gives 0), and with `on` gets one `rejection_link_card` per candidate whose answer window is 14 days from its creation; any decline other than `other` makes nobody answer. A confirmed link stores the answering seats and writes `governance.link.confirmed`; with `on` and an incident after `accountability_on_since` each answering holder waits in `link_departures`, at most one leaves per tenant in 30 days, a changed seat or a link no longer confirmed (a disputed one waits) cancels the wait, the last holder of a veto lens is skipped, and the waiting departures end with an audit record when the mode leaves `on`. The holder leaves the seat (vacant, epoch + 1, `seat.vacated.v1`, attempts fenced with `seat_changed`), is parked (unbound with `parked` in its record, facts offered to the next holder for 30 days, out of the promotion queue as `attribution`), gets `seat_parked` to the operators and retires as `parked_expired` after 180 days, never as `worker_gone`. A canceled link returns it: by `seat_return` while the seat is still vacant, otherwise at the head of the queue (one second before the oldest trigger) with no `min_tenure`. A bot that left for a link gets no trigger or case for 180 days and its tenure counts from the departure; only attributions of kind `change` count for triggers and figures, and links to rejected proposals do not count for the role hold of HLD-9 (it names changes and script runs only); a confirmed script link names no proposal, so no seat answers for it. With `on` a case proposes the holder of L with the worst accuracy (a holder below the minimum counts with its lens median, or as −2 after `min_tenure` + 90 days by its last `seat.assigned.v1`; with that event pruned it keeps the median), nobody when no holder is scored enough or the two worst tie (the person then chooses among the tied seats, `leaver_not_offered` otherwise), and sets `evicts_only_scored_veto`. From v0.3 a persona and its addenda are linted for the words of accountability and the farm manager's purpose paragraph (`persona_purpose`), the size counts all addenda of a position together, and an attempt gets the addendum of its profile; the farm manager is never retired `replaced_after_incident` and there is no incident stop. P2 `commission.status` and `doctor` (`governance.parked_bots`, `governance.parked_longest_wait_s`) show the figures to people only. Not in this version: the v0.3 fields of P2 `commission.status` (`governance_v03_since`, `accountability` and the per-seat `accuracy`, `scored_forecasts`, `missed_forecasts`) are not in `p2-commission-status-response.schema.json` yet, so the response is not checked against it for them; P2 `attribution.create`/decide (a link cannot be confirmed in shadow), the rules `dependency_1` and `rejected_dependency_1`, the replay of PRP-25, rewards and protection (COM-18), the shadow executor (COM-10), the hints and `self_assessment` of GOV-39, the weekly commission summary, the manager's daily review of the farm guards, the eval and P4 canary of GOV-46, a way to record an incident's cause, the `mgr-inj` report on a persona hash change, one card per incident.
- **Details before a decision** (APR-14). One generic check, `requireDetails`, reads `details_required` of the row in `decision-points.yaml`; a press of a listed decision before the person opened "Details" of that card is refused with `details_not_opened`, writes an audit record and answers `card.answer.details_first`. Approvals and proposals call it after their holds and expiry. Promotion cases (`promotion_card` "Confirm"), attributions ("Yes", "No") and the audit sample ("Lift veto") record `details_opened` in their decision, so they read the opening with the same `detailsOpened` (only openings since their card was shown, or since the scores were shown for the sample) and ask the same registry through `missingDetails` at the same point, after their holds and expiry, refusing with their own audit record. When the registry cannot be read the check fails closed.
- **Card limit per person per day** (APR-15). At hand-out a card of a decision row with `urgent: false` waits in `planned` until the next local day of the tenant once the person got `attention.noncritical_per_day` decision cards that day (by default 10), every handed-out decision card counted, urgent ones and reminders included, and the manager's notices `manager_attention` and `postmortem_report` handed out or planned for the day (MGR-52). Waiting cards go out in the order of the expiry of their subject. The excess is counted in `card_excess` by tenant and day, without names. The count runs under a lock per person. The expiry of a proposal (its presentation time), a memory record (first delivery plus the card TTL) and a subject request counts from the first delivery of its card. It is rewritten once, in the transaction that hands the card out, and undone if the card is withheld there. While a card waits for the next day, its proposal or memory record does not expire before the card may go, and the waiting cards are ordered by that moved expiry. A subject request keeps its deadline. A card update of a deferred card waits for that card's run_at. The rows of `decision-points.yaml` decide which card kinds of later stages are limited: `promotion_card`, `attribution_card` (its reminders too), `proposal_sample_card` and `self_measured_card` (`urgent: false`) wait and count; `takeover_confirm`, `script_confirm`, `script_gate_card`, `campaign_approval` and `control_card` (`urgent: true`) count and go at once; notices (`manager_notice`, `manager_stopped`, `alarm_notice`, the export delivery, export and initiator notices, card updates) neither wait nor count. A promotion case's presentation and expiry and an attribution's presentation (from which its 7 days and reminders count) move to the first delivery of their card, and are moved past the day a waiting card may go, like a proposal's. The first delivery sets that presentation to its own time even when a recipient over the limit had moved it to a later day, so a person who opens "Details" today can decide today. `self_measured_card` is a later card on a proposal already presented: its first delivery has its own mark (subject kind `self_measured_card`) and rewrites its 7-day window in the proposal record to count from it. Quiet hours and the daily digest (DLV-10) follow `deferrable` in `delivery-kinds.yaml`, so none of these cards and no export waits for them; the digest pace (REP-10) applies to `digest` deliveries to a chat only.
- **Two approvers** (APR-16). An action with `approvals: 2` takes two "Approve" presses from two different approvers, neither of them the initiator; one "Reject" ends it. Each vote is kept in `votes`, and the card shows who approved. Apply refuses `high_risk_one_approver`. The apply warning that a group has fewer than two approvers other than the initiator is only a log line, since the apply response has no notes; the doctor check `approvals.two_approvers_short` reports it too, and a person who may both request and approve counts as the initiator. A campaign card takes one press, so an action with `approvals: 2` is not offered to campaigns: a campaign of it is `rejected(campaign_policy_exceeded)`, a running campaign whose action gained a second approval stops at its next release or resume with the listed stop reason `admin` (the cause is an admin's catalog change), and the cause `action_needs_two_approvers` goes into the audit record `campaign.stop`; and a script fanout of it is `script_invalid`. A script action step opens its own approval with the two votes and never runs without a card; no apply lint code fits, so there is none. A reminder skips approvers who already voted.
- **Pause of approvals** (HLD-8). A `pause_action` hold on the farm, the tenant, the bot (from the task record's `acting_bot`), the action, or the host or resource the action writes to puts pending approvals in the state `paused`. The card shows that state, and a press answers `card.answer.held`. A pause starts with the hold, or with the approval when the hold is older. The expiry moves by the union of the hold intervals since then, with at most 7 days of pause in total; after that the approval expires. A `bot_group` hold matches the bot groups of the worker of the asking attempt as they stand now.
- **Maintenance windows** (MON-9). `botaru-zabbix` polls `host.get` for `maintenance_status` every `-maintenance-poll-s` seconds (60 by default, at most 300) and sends `ext.monitor.maintenance.v1` with the catalog host id as `resource`. The core caps `until` at 10 minutes from now and moves the hold's deadline only forward. The effects are `no_tool` and `pause_action`, or `no_action` with `maintenance_hold: true`. Only an `ended` event closes a period. A gap in the polls alone changes no hold, which is our reading of "a missing poll changes no hold", so it never undoes a person's release. A window a person released sets no new hold until an `ended` event. An active event after `ended` starts a new period: it extends the hold of the last period while that still runs, and sets a new hold otherwise. If a hold that nobody released runs out by its `until` inside a period, the next active event sets a new hold. The row of an ended window is removed 30 days later. A schedule slot is skipped as `held` when its task params name a held host or a resource on it.
- **Notification preferences** (DLV-10). `/prefs` in a private chat shows or sets `quiet HH:MM-HH:MM`, `quiet off`, `digest daily` and `digest off`; a person with `admin:people` names another person first. Only deferrable kinds wait: until the end of the quiet hours, or with a daily digest until the person's slot, which is the end of the quiet hours or 09:00 local time. They go out together at that slot as separate messages, not merged into one.
- **Language order** (DLV-18). Each delivery's `locale` is the first value with a loaded catalog: the recipient's own (a group chat's binding), the schedule's `locale` for its `deliver_to`, `Tenant.spec.locale`, `en`. The same order gives `reply_locale` in the attempt payload of `claim`. For a schedule task it is the locale of the first bound chat among its addresses that has one, then the schedule's. Only `chat:` addresses count; a `group:` address of people falls back to the schedule's locale. Otherwise it is the binding's for a group request or the initiator's. Then come the tenant's and `en`. Code replies to commands use the person's or binding's locale, then the tenant's.
- **Digest pace** (REP-10). `chat.bind` takes `digest.max_per_hour` (1 to 60). A digest over the ceiling of its chat (by default 1 an hour for a group and 4 for a private chat, counted by hand-out time) waits for the next free slot. A newer digest to the same chat takes the slot of the waiting paced one (`deliveries.paced`), which ends `withheld(superseded)` once the new one is planned; that is the closest registered reason. The ceiling applies again at hand-out, so digests released together by preferences are paced too: of the waiting paced digests of a chat only the newest is kept. Only digests are ever replaced.
- **Fairness within a class** (DSP-6). When the tenant sets `dispatch.fairness`, `claim` orders the waiting tasks of a class by running attempts per weight of the key's kind (the part before `:`, weight 1 by default). A key of weight 0 goes last. Ties go to the key whose oldest waiting task came first, then to the smaller id. Without `dispatch.fairness` the order is the enqueue time, as in v0.1.
- **Dead work and failing schedules** (CAP-4). The first page of `deadletter.list` carries `groups` by (tenant, type, reason), where a delivery's type is its kind. The root task of a schedule slot that fails with `attempts_exhausted` or `runs_exhausted` counts in `schedule_state.failed_slots`, and any other end resets it. At 3 in a row the schedule gets the hold described in `holds.yaml` and the alarm `hold.auto`; the count starts again from zero. A redrive of a task without its body answers `gone`.
- **Schedule check of a proposal** (TIM-5). For a cron or zone change the core finds the zone's transitions over the next year by an hourly offset scan. It lists the matching local times that disappear or repeat (at most 10 each), and the card context shows them as `times_disappear` and `times_repeat`. All cron and zone ops of one schedule are checked together; an empty or `Local` zone is `rejected(forbidden_change)` as apply refuses it. A schedule of a type with `makes_backup: true` that loses a slot is `rejected(schedule_time_invalid)`.
- **External programs on P1** (TEN-2, IDM-1, TEN-7, BUD-1, DSP-7). A program key is a deployment setting, `programs: [{token_sha256, tenant, key_id}]`; it resolves to the active principal of the tenant with identity `api:<key_id>`, who is the initiator, and the tenant comes only from the key; a turned-off program's key is refused with `person_inactive`. `enqueue` runs the sender checks of a person (`task:<type>`, the budget reserve, `max_queued` with `retry_after_s`) with the source `interactive` and `enqueued_by: program:api:<key_id>`; the audit `via` is `core`, since the schema has no program value. A ref and an attached file must be the program's own: a task or campaign it started or a file it uploaded or its tasks produced, else `ref_invalid` (audited, the key stays free). `priority` only lowers. `to.group` is refused with `group_invalid` (no group dispatch for tasks) and `scope` with `input_schema_invalid`. The dry run (`mode: validate`, PRM-11) is deferred and answers `version_unsupported`.
- **Enqueue under a lease** (PRM-6). A job or agent with a live attempt lease enqueues a child of a type of its role's `may_enqueue`, with the parent's tree under the key `system:child:<parent>:p1:<idempotency_key>`, so the same key with another body is `idempotency_conflict`; the dry run is `forbidden` to a lease holder (PRM-11); the body takes only `type`, `goal` and `params`, and `refs`, `to`, `scope` and `priority` are refused, since a child takes them from its parent. A worker's `task.get` and `cancel` answer `forbidden`.
- **Task views** (PRM-9, DSP-2, APR-6). `task.get` and P2 `task.show` return the task record without `origin`, `conversation`, body or result; `artifacts` are the files the task produced. A reader is the initiator, or a person with `task.read:<type>` and the data of the type; every other case, another tenant and a missing id are the same `not_found`, and a read is audited. `cancel` and P2 `task.cancel` act on a root task and its whole tree (a child is refused with `input_schema_invalid`, naming its root) and are idempotent; a finished task is `already_terminal` unless its tree still has a pending approval or script run. A P2 cancel by an operator who is not the initiator is `canceled(admin)`.
- **Lists** (PRM-15). `task.list` gives the caller's own root tasks (not `action.*`), all states unless filtered, oldest first, 100 a page with the cursor `<unix micro>.<id>`. `team.tasks` needs `team.view:<group>` (`forbidden` with `needs`) and lists only tasks of the group's current members (memberships within their `until`) of types and data the person may read. `about` returns the text of `/about` in the tenant's locale.
- **Invitations** (PRM-7, PRM-13, IDN-14). `invite.create` takes groups and a `ttl` (48 h by default, at most 30 d) and returns a code `iv1_` plus 128 random bits, stored only as a hash. The person sends `/start <code>` in a private chat: the core adds a principal for the sender, or uses the active one of that identity, grants the groups and marks the invitation used; every failure (unknown, used, revoked, expired) has the same text, and its audit record keeps the reason. A privileged group is granted `pending` for 48 h, and the reply shows the person's verification code, rendered at each reply and never stored. `invite.confirm` with that code, or `grant --code` (which then confirms the invitation), makes it active; a wrong code is audited and `forbidden`. `invite.revoke` is idempotent, and a used invitation is `already_terminal`. Offboarding a person revokes the open invitations they created (IDN-14).
- **Verification code** (PRM-13). The code is derived, not stored: 8 digits of an HMAC over the token key, the tenant and the principal, checked against the current and the previous token key. `/me` shows it. A grant of a privileged group (not delegated, PRM-16) is `pending` without the code. On a production tenant it also needs `requested_by`, another active admin with `admin:people`, unless the tenant has no active principal with `admin:people` yet (the first admin). The admins are told privately of an active privileged grant and of an ungrant, and of a delegated group granted, removed or invited on P2 (PRM-16).
- **Worker operations** (IDN-4, DEP-2, INJ-2). `worker.rotate` returns a new token; the old one works for 24 h (`old_valid_until`), the store keeps only hashes, and a revoked worker is `subject_closed`. The operator credential of tenant `farm` reaches a worker of any tenant (PRM-14), as for `secret.revoke`. `worker.unblock` sets a `blocked` worker to `enrolled`, so its next `hello` is checked from the start; a worker in another state is left as it is and nothing is audited.
- **budget.set** (MAN-5, PRM-14, BUD-1). The line is `month`, `day` or a budget line of the purposes registry (its month limit). The limit is in cents and may not exceed the git limit; `until` must lie in the future. A repeat replaces the override. The override lowers the limit only in the enqueue budget check; the grant, commission and manager-line readers still use the git limit.
- **service.control on P2** (APR-18, PRM-18). The operator credential's own person controls a service: without `service.control:<service>` the answer is `forbidden` with `needs`, a guard or hold refuses, a caller who is not an active person is refused with an audit record, and a verb outside `no_card` opens an approval (`approval_required`, or `service_rate_limited` past the card limit). The answer keeps to the closed `service-control-result` codes on P2 and P3: a seat's restricted mode answers `forbidden` and its `ops_per_hour` `service_rate_limited`, with the real reason in the audit. Otherwise the core writes a service grant with the person as author, an action task without origin and one write call, and answers `done` with state `unknown`; P2 does not reconcile the outcome yet.

## Checks

The workflow `.github/workflows/go.yml` runs on every pull request. Locally, from this folder:

```sh
gofmt -l .
go mod tidy -diff
go vet ./...
go tool staticcheck ./...
go test -race ./...
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build ./...
go tool govulncheck ./...
```

The `go` command downloads the toolchain named in `go.mod` by itself (`GOTOOLCHAIN=auto`). staticcheck and govulncheck are tool dependencies in `go.mod`, so their versions are pinned and Dependabot updates them.

### Rule coverage

`TestConformance` in `internal/conform` runs every behaviour case of `conformance/fixtures/` whose rules are of v0.1, all profiles, on the reference core: each case on a fresh test bench (a new database, the core with its P1, P2 and test-control listeners), reached only over HTTP. A case is passed, failed, skipped (a later version) or unchecked: it needs a given key, a step, an operation or a fact that the runner or the core cannot do yet, and the report names the first such need. An unchecked case never counts for its rule. A rule is done when every case that names it passes. `testdata/passing.txt` lists the passing cases: the test fails when a listed case stops passing, and when a case starts to pass without being listed (record it with `go test ./internal/conform -run TestConformance -update`). With `BOTARU_CONFORM_OUT=<folder>` the test writes `junit.xml` and the coverage table `coverage.md`; CI puts the table into the job summary.

The store tests need PostgreSQL: either `BOTARU_TEST_DSN` names a server where the tests may create and drop databases, or `initdb` of PostgreSQL 16 or later is installed (in `PATH` or `/usr/lib/postgresql/*/bin`) and the tests start a private server; they refuse to do that as root. Without PostgreSQL the store tests are skipped, unless `BOTARU_TEST_PG_REQUIRED=1`, as in CI.
