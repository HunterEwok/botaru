# Glossary

## In short

The glossary collects the terms of the bot farm skeleton: what each one means in the model, what it is easily confused with, and where it is described in detail. The terms are split into 14 topics, from the parts of the farm to the skeleton versions; inside a topic the rows are sorted alphabetically by term. A name in backticks is an identifier from manifests, ports and schemas, and the names after a slash are other names for the same concept. The normative text of the rules lives in [conformance/rules.md](../../conformance/rules.md), the rule numbers in the "Details" column lead straight to the rule, and decisions are marked like (D-33) and collected in the [decision log](../decisions.md). After the topics come the reason codes added by the October 8 review, pairs of words that are easy to mix up, and a list of what is not in the model.

## The farm and its parts

| Term | Meaning | Not to be confused with | Details |
|---|---|---|---|
| admin API (P2, `AdminAPI`) | Everything that people change and view: `apply`, stops, workers, erasure requests, viewing. The people's client is `farmctl`; the channel passes some operations on behalf of a verified person, and operator operations come only from `farmctl`. | P1 worker protocol | [P2](../../spec/ports/p2-admin-api.md), [PRM-14](../../conformance/rules.md#PRM-14) |
| agent runtime (E4, `AgentRuntime`) | A replaceable program that runs the model loop inside an agent attempt; the core talks to it through the E4 adapter (`describe()`). It calls the model only through P4 and tools only through P3, and has no provider keys and no worker token. The reference is our own loop in Go over P4 (D-93). | worker; model gateway | [E4](../../spec/ports/e4-agent-runtime.md), [DEP-5](../../conformance/rules.md#DEP-5) |
| architecture decision record (ADR) | A record of an architecture decision of the skeleton in `docs/adr/` in MADR 4.0.0 format. It is needed when the model changes: a new concept, a lifecycle state, a rule, a manifest kind that affects permissions, an issuance condition. | decision from the decision log; port sheet | [Architecture](../architecture.md), [Extending](../extending.md) |
| authorizer (C2, `Authorizer`) | The port behind the core that answers every `authorize` question with "allowed" or "denied" and a reason. The reference is a function in the transition transaction with the permission table as a fixture. | conformance check | [Permissions](../permissions.md), [C2](../../spec/ports/c2-authorizer.md) |
| background loop | A deterministic, time-driven, idempotent core duty without a model: `reaper`, `schedule`, `delivery`, `erasure`, `identity` and others. Every loop records a tick. | improvement loop; background self-learning of the runtime (forbidden) | [Background loops](../../spec/ports/background-loops.md), [OBS-4](../../conformance/rules.md#OBS-4) |
| built-in tool | A core tool from `builtin-tools.yaml` (`enqueue_child`, `request_action`, `send_message`, `skill_read`, `service/control`, `monitor/script_run` and others) that P3 adds to the attempt catalog according to the role profile. | the runtime's own built-in tools (shell, files, web): they are turned off | [P3](../../spec/ports/p3-tool-gateway.md), [PRF-1](../../conformance/rules.md#PRF-1) |
| channel (E1, `Channel`) | The adapter for communication with people: a worker of kind `channel`, one process per tenant. It verifies the authenticity of incoming messages and submits them to the core as `Activity`, takes deliveries and renders cards. The reference is Telegram. | source channel; sink; group chat | [Tasks and delivery](../tasks-and-delivery.md), [E1](../../spec/ports/e1-channel.md) |
| contract binding | The exact form of a contract in a protocol or product (`spec/bindings/`): OpenAPI for P1, the tool protocol binding `spec/bindings/mcp/` (MCP revision, sessionless mode) for P3 and E3, the OS binding `spec/bindings/os/systemd.md` (units for `oneshot` and `unit`, the access rule from the catalog), the channel note `spec/bindings/channels/<channel>.md`, and the SQL binding of the C1 reference. Rules say "OS mechanism" and "tool protocol"; the names live in the binding. | chat binding; identity binding; incident binding candidate | [Ports](../../spec/ports/README.md) |
| core | The farm code that all rules trust: the core process, its background loops, the P3 and P4 gateways, the C1 store logic and the C2 authorizer. `farmctl` on the core machine with store credentials is also part of the core. In the examples the core, the store and the channels run on the farm node `core1`, with copies on `backup1`; the catalog machines of tenant `demo` are `web1`, `db1`, `ctd1` (DEP-11). | external program; `farmctl` as an ordinary P2 client | [Architecture](../architecture.md), [DEP-8](../../conformance/rules.md#DEP-8) |
| declared object | An object from a manifest in git, written to the store by the `apply` operation. Only the next `apply` changes it; an urgent change without git is done with a stop. | recorded object (principal, chat binding, stop) | [lifecycle: manifest](../../spec/lifecycles/manifest.md), [MAN-5](../../conformance/rules.md#MAN-5) |
| driver | An implementation of a port inside a manifest kind, for example the Telegram channel in `Channel`. A driver brings the schema of its `spec.config` under the meta-schema; fields that rules depend on are forbidden in driver configuration. | plugin; runtime adapter | [Extending](../extending.md), [MAN-4](../../conformance/rules.md#MAN-4) |
| farm control CLI (`farmctl`) | The reference P2 client for people. On the core machine with store credentials it is part of the core and can write a stop directly to C1 when the core process is not running. | the core as a process; channel | [Architecture](../architecture.md), [DEP-8](../../conformance/rules.md#DEP-8) |
| farm nodes `core1`, `backup1` | The farm nodes from the examples (`farm_hosts: [core1, backup1]`): `core1` is the core machine with the core process, the C1 store and the channels; `backup1` is the backup machine, where the external backup process runs outside the core and reports through P2 `backup.report`. A farm node never appears in a tenant catalog: the catalog machines of `demo` are `web1`, `db1`, `ctd1`. | `web1`, `db1`, `ctd1` (tenant machines); production machine | [Architecture](../architecture.md), [DEP-11](../../conformance/rules.md#DEP-11), [RET-5](../../conformance/rules.md#RET-5) |
| handle | Bearer credentials for one lease: tool, model, session and memory handles. At least 128 bits of randomness, they expire with the lease, are bound to the store epoch and never get into the model context, logs or audit. | worker token; lease token; provider key | [Security](../security-model.md), [SEC-3](../../conformance/rules.md#SEC-3) |
| loop tick / tick | A background loop's mark in the store that it ran on time; the tick age is visible in P2 `status` and `doctor`. | lease renewal `heartbeat`; worker `last_seen` | [Background loops](../../spec/ports/background-loops.md), [OBS-4](../../conformance/rules.md#OBS-4) |
| manifest | A declaration in git in the wrapper `{apiVersion, kind, metadata, spec}`. The status (applied commit, set hash, errors) is kept by the core and is not in git. | task record; manifest status | [Task language](../task-language.md), [lifecycle: manifest](../../spec/lifecycles/manifest.md) |
| manifest apply (`apply`) | The P2 operator operation: atomically brings the store to the set of manifests from a commit, the whole set or nothing. An object that disappeared from git is shown together with its dependents and deleted only by an explicit list. | `hello`; `enroll` registration | [P2](../../spec/ports/p2-admin-api.md), [MAN-6](../../conformance/rules.md#MAN-6) |
| manifest kind (`kind`) | `Tenant`, `Group`, `Role`, `TaskType`, `ToolPlugin`, `Action`, `Catalog`, `Route`, `Schedule`, `Channel`, `Sink`, `MessageType`, `BotGroup`, `ObservationSeries`, `ModelProfile`, `Commission`, `IncidentClass`, `Governance`, and since v0.2 `Script`. Only an ADR adds a kind that affects permissions. | principal kind; message kind; worker kind | [Task language](../task-language.md), [Extending](../extending.md) |
| manifest wrapper / manifest envelope | The common fields of every manifest: `apiVersion` (`botaru/v1alpha1`), `kind`, `metadata` (`name`, `tenant`, `labels`) and `spec`. `status` is not written to git. | untrusted text wrapper; message envelope | [Architecture](../architecture.md), [MAN-1](../../conformance/rules.md#MAN-1) |
| memory store (C4, `MemoryStore`) | A thin port: long-term memory of people and bots, and facts in a space that the core computes. It deletes with the `erase` operation. | C3 session store; knowledge corpus | [C4](../../spec/ports/c4-memory-store.md) |
| model gateway (P4, `ModelGateway`) | The part of the core between the runtime and the provider (D-45): it checks the request, picks the model by slot, reserves and charges money, and holds the provider keys. It computes the response deadline from the profile (`max_output_tokens` divided by `tokens_per_s`, times 2, at least 60 seconds), retries a request only if it was not sent (no `request_id`), and checks the provider terms (`provider_training`, `provider_human_review`, `subprocessors`) on every call, including embeddings and eval (GW-15). It is not a transparent proxy: only the paths on the binding allowlist, the provider address only from the binding's closed list, and runtime headers are not passed to the provider (D-86 (5)). | agent runtime; model provider | [Models and money](../models-and-money.md), [P4](../../spec/ports/p4-model-gateway.md) |
| operation map (`operations.yaml`) | The file `spec/ports/operations.yaml`: one row per port operation with the port, name, version, request and response schemas from `spec/model`, and rule numbers. The HTTP binding paths are built from it, and CI checks it against the port sheets. | port sheet; rule registry | [spec/ports/operations.yaml](../../spec/ports/operations.yaml) |
| port | A contract between the core and a replaceable part: operations, guarantees, bindings. There are thirteen ports: P1-P4, C1-C4, E1-E5; each has its own sheet. | contract binding; plugin | [Ports](../../spec/ports/README.md), [Architecture](../architecture.md) |
| port kind | The port letter: P is a core protocol (workers, runtime and people call the core), C is a port behind the core (the core calls a replaceable part), E is an edge port (the adapter takes work through P1 and talks to the outside world). | worker kind | [Architecture](../architecture.md) |
| port sheet | The file `spec/ports/<port>.md` with one template: In short, Who calls and who implements, Operations, Guarantees, Bindings, What the port does not do. A sheet has its own SemVer version; a new operation is a minor version. | contract binding; ADR | [Ports](../../spec/ports/README.md) |
| reason (`reason`) / reason registry | A code from the closed registry `spec/model/reasons.yaml` in an RFC 9457 error response. The registry says whether a reason spends an attempt, whether to retry, and with which outcome the work ends. The index of codes by family owner lives in `docs/tasks-and-delivery.md`; the codes of the October 8 review are collected in the section "Reason codes added by the October 8 review" below. Provider rate limiting is `provider_rate_limited`, farm limiters (services, scripts, cards, wakeups) are `service_rate_limited`, and a permission refusal is `forbidden`. | `reason_code` of a human decision; waiting reason `waiting_reason` | [Tasks and delivery](../tasks-and-delivery.md), [Architecture](../architecture.md) |
| reference implementation / reference | The implementation of a port on which the sheet and the conformance suite are checked: PostgreSQL for C1, Telegram for E1, disk for E2; for E4 our own loop in Go (D-93). Rules do not refer to the reference, except binding sheets. | farm implementation (the reference one in `impl/`, D-92) | [Architecture](../architecture.md) |
| runtime deviation | A value from the closed list `runtime-deviations.yaml` (`session`, `memory`, `model_attribution`, `catalog`) with which a runtime declares in `describe()` that it carries out a farm mechanism differently. A substitute rule RT-1..4 with `waivable: false` then applies instead of the mechanism. | conformance profile; expected failure | [E4](../../spec/ports/e4-agent-runtime.md), [RT-1](../../conformance/rules.md#RT-1) |
| session store (C3, `SessionStore`) | A thin port: conversation transcripts under a key that the core computes. `delete` removes one session; `purge` removes a scope or an id list. | C4 memory store; attempt journal | [C3](../../spec/ports/c3-session-store.md) |
| sink (E2, `Sink`) | An adapter that writes artifacts to external storage without people: the reference is an archive on disk, and since v0.2 also an outgoing webhook. A worker of kind `sink`; it implements `match` (search for a principal's records, the answer is ids only) and `erase` by scope and id list since v0.1 (D-76). A sink for operator exports carries `export_only: {recipient_ref, key_ref}` (a single recipient, encryption). | channel; channel with third-party storage | [Tasks and delivery](../tasks-and-delivery.md), [E2](../../spec/ports/e2-sink.md) |
| skeleton layer | One of the four parts of the skeleton: the model (concepts, lifecycles, rules), ports (sheets), contracts and checks (schemas, bindings, fixtures, suites), implementations (the reference one in `impl/`, D-92). | skeleton version; port kind | [Overview](../overview.md) |
| task store (C1, `TaskStore`) | The core store with atomic transitions and a queue: tasks, leases, events, stops, records, audit. The reference is PostgreSQL; only core processes access the store. | C3 session store; C4 memory store | [C1](../../spec/ports/c1-task-store.md), [DEP-8](../../conformance/rules.md#DEP-8) |
| thin port | A port with one page, one reference adapter and a minimal set of checks: C3, C4, E2. If it has no second implementation by version 0.3, it becomes prose in the core sheet (D-46). | port without operations | [Architecture](../architecture.md) |
| three object origins | Declared objects (git and `apply`), recorded objects (P2 commands with audit: principal, membership, chat binding, worker, stop, seat) and runtime objects (core transitions: task, lease, approval, message and others). | retention classes | [Architecture](../architecture.md) |
| tool | A plugin operation that the model calls through P3: a read tool or a write tool. Write tools are not shown to the model and run only as an action after approval. | built-in tool; action | [P3](../../spec/ports/p3-tool-gateway.md), [APR-1](../../conformance/rules.md#APR-1) |
| tool gateway (P3, `ToolGateway`) | The part of the core that assembles the attempt's tool catalog (`tools/list`) and checks every call. It is the runtime's only MCP server; the tool handle goes in the header of every request. | E3 tool host; plugin | [P3](../../spec/ports/p3-tool-gateway.md), [INJ-9](../../conformance/rules.md#INJ-9) |
| tool host (E3, `ToolHost`) / toolhost | A worker that, as an MCP client, holds the tenant's plugins and runs tool calls; it takes each call itself through `claim`. The placement `host` or `sandbox` is fixed by `enroll`. | plugin; P3 tool gateway | [E3](../../spec/ports/e3-tool-host.md), [DEP-2](../../conformance/rules.md#DEP-2) |
| tool plugin (`ToolPlugin`) | An MCP server with tools, declared by the manifest `tools/<plugin>/tool.yaml`. The model sees tool descriptions only from the manifest, not from the server itself. | tool host; skill | [E3](../../spec/ports/e3-tool-host.md), [INJ-2](../../conformance/rules.md#INJ-2) |
| `tools/list` assembly stage | One of the eight stages with which P3 assembles the attempt catalog: role tools, read only, tier, output class, description from the manifest, closed resource lists, built-in tools, stable order. | script step; skeleton version | [P3](../../spec/ports/p3-tool-gateway.md) |
| worker | A process that takes work through P1 `claim`. Kinds: `agent` (E4 adapter and model runtime), `job` (code without a model), `toolhost`, `channel`, `sink`, `monitor` (E5 monitoring adapter). A process serves one tenant. The monitoring adapter process has its own monitoring system user with rights only on the host groups of its tenant (MON-4). | bot (identity); external program | [Architecture](../architecture.md), [lifecycle: worker](../../spec/lifecycles/worker.md) |
| worker enrollment (`worker.enroll`) | The P2 operator operation: records a worker with tenant, role, kind and labels, for a toolhost also plugins, placement and machine, for a personal assistant its owner (`owner`), and issues a token. For a role with a model the core creates an identity or binds the named one (`--bot`). | `hello` | [P2](../../spec/ports/p2-admin-api.md), [lifecycle: worker](../../spec/lifecycles/worker.md) |
| worker hello (`hello`) | The first P1 call: the worker reports its kind, labels (only a narrowing of those recorded at `enroll`), capacity and protocol versions; a toolhost also reports its live `tools/list`. A worker outside the version window gets `version_unsupported`. | `enroll` registration; `apply` | [P1](../../spec/ports/p1-worker-protocol.md), [LCY-7](../../conformance/rules.md#LCY-7) |
| worker protocol (P1, `WorkerProtocol`) | The only entry of farm processes into the core: `hello`, `claim`, `heartbeat`, `complete`, `fail`, `enqueue`, `submit_activity`, `decide`, `msg.*`, `file.*` and others. Work is pulled: the worker asks for work itself. | P2 admin API | [Architecture](../architecture.md), [P1](../../spec/ports/p1-worker-protocol.md) |
| write rule | A sender writes only the body (of a task or message) or `spec` (of a manifest); the task record, system fields and status are written only by the core. The schema rejects a request with such fields. | task body | [Architecture](../architecture.md), [IDN-1](../../conformance/rules.md#IDN-1) |

## Tenants, people and programs

| Term | Meaning | Not to be confused with | Details |
|---|---|---|---|
| attempt permissions | The worker role's permissions ∩ the group permissions of every initiator. Identity, position, seat, persona and track record grant no permissions. | role profile; position | [Permissions](../permissions.md), [IDN-9](../../conformance/rules.md#IDN-9) |
| capability (`Capability`) | A permission string in a group, for example `task:ops.investigate.v1` or `data:raw_logs`; the capability forms, class order and tiers live in `capabilities.yaml`. An asterisk is allowed only at the end of `task:<prefix>.*`; no string means no. Forms with an object: `team.view:<group>`, `service.control:<service>`, `monitor.script_run`, `action.approve:service.control:<service>`; the initiator who asks a bot for a service or script also needs them (D-73). | agent ability (knowledge, skills); role declarations (`claims`, `tools`) | [Permissions](../permissions.md), [PRM-1](../../conformance/rules.md#PRM-1) |
| delegated groups (`delegated_groups`) | A list in the tenant manifest: groups that the tenant admin grants alone by invitation and `/grant`, without the operator; such a group holds only types of tier 1-2 with a class no higher than `internal` (example: `delegated_groups: [researcher]`). The other privileged groups are granted by the operator; an attempt to grant them from the bot gets `privileged_group`. | privileged group; consent group | [Permissions](../permissions.md), [PRM-16](../../conformance/rules.md#PRM-16), [PRM-13](../../conformance/rules.md#PRM-13) |
| export | An export of tenant or principal data in JSON Lines by a core task into a sink named by the operator, never into a chat (P2 `tenant.export`, `principal.export`). Only a sink with `export_only: {recipient_ref, key_ref}` (a single recipient, the file is encrypted) is accepted, otherwise `sink_not_export` (SEC-10). A report on an external identity across all tenants at once is available to the operator as `principal.data_report --all-tenants`, without content. | backup; a person's `export` request | [Operations](../operations.md), [LCY-2](../../conformance/rules.md#LCY-2) |
| external program | A client with its own key: a principal of kind `service` with groups and checks, like a person (D-47). It enqueues tasks through P1 `enqueue` and reads them through `task.get`. | core; worker; bot | [Permissions](../permissions.md), [Architecture](../architecture.md) |
| group (`Group`) | A set of capabilities, data classes and a daily limit in the tenant's git (`groups.yaml`), for example in `demo` the groups `user`, `lead`, `assist`, `staff`, `approver`, `admin` and `system-ops`. Among people, only `admin` and the team lead group (`lead` in the examples) see reports with money. | bot group; group chat; farm manager consent group | [Permissions](../permissions.md) |
| identity (`Identity`) | A principal's address in an external system: `telegram:<id>`, `api:<key_id>`, `hook:<source>`, `email:<address>`. A principal lives in one tenant; identity secrets are stored as hashes. | bot identity | [Permissions](../permissions.md), [IDN-4](../../conformance/rules.md#IDN-4) |
| identity assurance (`identity_assurance`) | A channel driver declaration: `strong` (the channel verifies the sender) or `weak` (the sender can be forged). Without a real sender there are no commands and no decisions. | membership assurance `membership_assurance` | [Permissions](../permissions.md), [IDN-3](../../conformance/rules.md#IDN-3) |
| initiator | The verified principal on whose behalf a task runs; only the core writes the field, and children inherit it. | message sender; seat holder; initiator of a script run | [Permissions](../permissions.md), [IDN-2](../../conformance/rules.md#IDN-2) |
| initiator set | The task's initiator together with the initiators of everything the attempt has read; the attempt's permissions are intersected with the permissions of each. A message carries its part in the field `origininitiators`. | approval initiator | [Permissions](../permissions.md), [Messages](../messaging.md) |
| invitation | A one-time code with an expiry into groups no wider than the inviter's permissions; it is the P2 operation `invite.*`, not a model object. Membership in a privileged group stays `pending` until the verification code is checked. | verification code | [Permissions](../permissions.md), [P2](../../spec/ports/p2-admin-api.md) |
| membership (`Membership`) | The link of a principal to a group: `pending` (waiting for the verification code check) or `active`, the expiry, who granted it and at whose request. Removing a group takes effect at once, including on running tasks. | chat binding | [Permissions](../permissions.md), [PRM-7](../../conformance/rules.md#PRM-7) |
| membership assurance (`membership_assurance`) | A channel driver declaration: `enforced` (the channel knows the membership of a group chat) or `none`. A bound chat ceiling above `summary` and cards in a group exist only with `enforced`; when a member joins such a chat, the code repeats `privacy_notice` (SEC-13). An incoming message from a non-principal in a bound chat creates no `Activity` (MSG-17). | identity assurance | [Permissions](../permissions.md), [DLV-7](../../conformance/rules.md#DLV-7) |
| operator | A person with `admin:*` rights in the service tenant `farm`; works through git and `farmctl` with their own P2 credentials, never from a channel. | tenant admin | [Permissions](../permissions.md), [Architecture](../architecture.md) |
| operator operation | A P2 operation from a closed list: seats, stops of the `farm` and `seat` scopes, `control.revert --since`, pinning and preemption from people, `chat.bind`, privileged groups and `principal.*` operations on people who hold them, `worker.*`, `core.drain`, `restore.complete`, `audit.verify`, export, `redrive` and others. Accepted only from `farmctl`. | an operation of a person in their own tenant that the channel passes to P2 | [P2](../../spec/ports/p2-admin-api.md), [PRM-14](../../conformance/rules.md#PRM-14) |
| person offboarding | An admin's `/off` (P2 `principal.off`) turns a person off reversibly and deletes nothing; P2 `principal.offboard` removes them for good and creates an erasure request for the scope `(tenant, subject)`. People with privileged groups are turned off and removed only by the operator through `farmctl`. When a person leaves (Identity `disabled`), the core sends admins with `admin:people` the notice `principal_left` with the list of chats where they remain, only in private chats (IDN-13). | tenant offboarding; bot identity retirement | [Operations](../operations.md), [LCY-3](../../conformance/rules.md#LCY-3) |
| principal (`Principal`) | Whoever acts inside one tenant: a person (`human`), an external program (`service`) or the system principal `system`. The tenant and the principal come from the credentials. In core records (task, audit, usage, grants, campaign, erasure) a person is recorded by the opaque principal id `human:p_<ULID>` (the `principal_ref` building block): after the colon there is an id, not a name. Names like `alice` are training names only in manifests, examples and fixtures; the runner maps them to ids through `evals/fixtures/seed.yaml` or the fixture's `given`. After a person leaves, the audit keeps the same id, and the name is removed from the principal record. | bot (has no permissions of its own); worker (process); decision subject | [Permissions](../permissions.md), [TEN-2](../../conformance/rules.md#TEN-2) |
| privileged group | A group that contains an action, any `admin:<scope>`, a data class above `internal`, a type of tier 1 or higher, or a decision right. `apply` computes the flag; only the operator grants such a group, with a verification code. | the `admin` group (just one of the privileged ones) | [Permissions](../permissions.md), [PRM-13](../../conformance/rules.md#PRM-13) |
| service tenant `farm` | The tenant for what belongs to the farm as a whole: the farm manager seat registry, the holder's identity, operator permissions, stops of the `farm` and `seat` scopes. The farm manager's work with data happens in the tenants, not in `farm`. | main tenant (there is none, D-23) | [Architecture](../architecture.md), [MGR-3](../../conformance/rules.md#MGR-3) |
| system principal `system` / `system-ops` group | The principal of every tenant on whose behalf schedules and routes work. Its group `system-ops` lists exactly the types they enqueue. | operator; seat service principal `seat:farm-manager` | [Permissions](../permissions.md), [PRM-10](../../conformance/rules.md#PRM-10) |
| team lead (`team.view`) | A person with the capability `team.view:<group>`: the command `/team [group]` in a private chat shows a code-built table of that group's tasks, with no model and no reporter involved; `admin` and team leads see reports with money. | tenant admin; manager (bot) | [Permissions](../permissions.md), [Messages](../messaging.md), [PRM-17](../../conformance/rules.md#PRM-17) |
| tenant (`Tenant`) | Whose data and whose money: a wall that nothing crosses (TEN-1..7). Declared in git (`tenants/<name>/tenant.yaml`, then `farmctl apply`); each has its own model provider workspace. Money limits are in the `spec.budgets` block (`month_eur`, `day_eur`, `hour_eur`), groups for self-service granting in `delegated_groups`, the opt-out from the farm manager in `farm_manager` (D-77), operator access to journals in `operator_access.debug_journal`. | bot group; workspace; group chat | [Architecture](../architecture.md), [lifecycle: tenant](../../spec/lifecycles/tenant.md) |
| tenant admin | A person with `admin:people` in their tenant; grants ordinary groups and manages people without privileged groups (P2 `principal.*`) from a private chat with the bot or through `farmctl`. | operator | [Permissions](../permissions.md) |
| tenant kind (`kind`) / test and production tenant | `test` or `production`; without the field a tenant is production. For a production tenant `apply` rejects self-approval. | principal kind; test bench (a farm instance without production tenants) | [Permissions](../permissions.md), [APR-9](../../conformance/rules.md#APR-9) |

## Words that are easy to mix up

- **Worker, bot and external program.** A worker is a process that takes work through P1 `claim`; a bot is an identity with a permanent number, memory and a track record whose tasks the role's workers carry out. An external program is a client with its own key, a principal of kind `service` with groups, like a person (D-47): it enqueues tasks through P1 `enqueue` and reads their outcome.
- **Role, role profile and position.** A role is a manifest in git: which task types its workers take and which tools and model slots are available to them; groups grant permissions, so it is not an RBAC role. A role profile from a closed list only narrows what a role can declare, while the core derives the position from the profile, the worker's owner (the field `owner`) and the binding, and the position chooses the persona and the rank ceiling.
- **Seat, seat role and worker.** A seat is a chair in the commission or the farm manager's chair; its holder is a bot identity, and a seat has no lease. A worker of the seat role (`seat_role`) carries out a seat task, the `acting_bot` of that task is the holder, and the attempt carries the seat epoch.
- **Lens and seat.** A lens is a review point of view (`security`, `operational`, `cost`, `value`, and since v0.2 `farm_manager` and `necessity`) with its own weight, and two lenses also have a veto. The charter links a commission seat to a lens; the seat holder carries out the lens tasks, and when there is no holder, the lens's fallback role does.
- **Manager, coordinator and farm manager.** A manager is a bot of profile `manager` that puts work into its tenant's pool and proposes campaigns, and a coordinator is the same kind of manager without a model (`worker_kind: job`). There is one farm manager for the whole farm; it holds the seat `farm-manager` and prevents critical incidents with control operations; it is not a manager.
- **Task, attempt and runtime run.** A task is a unit of work with a body and a record, and an attempt is one handout of a task to a worker under a lease, at most 3 of them; a lease of a tool call or a delivery is not called an attempt. A runtime run is one run of an agent with a model inside an attempt; a task has at most 6 of them, and only runs with a model answer count toward the limit.
- **Task body and task record.** The sender writes the body: `type`, `goal`, `params`, `attachments`. Only the core writes the record (tenant, initiators, `origin`, tree, marks, flags); the word "envelope" is not used for a task.
- **Initiator and sender.** The initiator is the verified principal on whose behalf a task runs: the core writes the field, children inherit it, and the attempt's permissions are intersected with theirs. The sender is whoever sent the body or message (a channel, an external program, an attempt); for a bot message the sender is a worker, and the message grants no permissions.
- **`running` of a campaign and script, `running` of a change trial and `working` of a task.** For a campaign and a script run, `running` means that items or steps are being released, and for a change trial, that its 14-day window is running. A task that an attempt is carrying out is in `working`; a task has no `running` state.
- **Change trial and promotion probation.** A change trial (`trial`) is a code measure: for 14 days from `realized` the core watches the promised metric and the guards and gives the outcome `better`, `unchanged`, `worse`, `undetermined` or `mixed`. Promotion probation (`probation`) is 14 days without a confirmed incident attribution and without a measured degradation, needed for a promotion trigger; the word "trial" is not used without a qualifier.
- **Attribution window, change trial window, merge window, maintenance window, P1 version window and core downtime window.** The attribution window (14 days from `realized`) is the time when code creates attribution candidates, the change trial window is exactly 14 days of outcome measurement, and the merge window gathers events into one run of the role's analysis. The maintenance window is a stop on a machine, the P1 version window is the current and the previous major version of the worker protocol, and the core downtime window is an interval when the core was not running and attempts were not spent.
- **Step (skeleton version), script step and assembly stage.** Used alone, "step" means only a skeleton version: step 1 is v0.1, step 2 is v0.2. An element of a script's `steps` list is a script step, and a part of the P3 catalog assembly is a stage.
- **Store epoch, seat epoch, bot epoch and lease number.** The store epoch grows on a restore from backup, the seat epoch on a change of holder and on every new stop reason, the bot epoch on a change of an identity binding, and the lease number on every `claim`. The core rejects a record with an old value of any of the four with the answer `fenced`.
- **Stop and alarm.** A stop forbids part of the work, only narrows and takes effect from the next check; people set it, code sets it by an auto-stop rule and by the first measure of an incident class, and the farm manager seat holder sets it with the `hold` operation. An alarm tells people about an episode of trouble and forbids nothing by itself.
- **Alarm and incident.** Only code produces an alarm: it is an `alarm.*` event with the key `alarmkey` and the states `firing` and `resolved`. Only the core opens an incident, from a code alarm and a class from the catalog; it has a first measure, a list of involved parties and its own lifecycle, and a person or the seat holder closes it.
- **Approval, "Acknowledged" and human decision.** An approval (`Approval`) is a record of a request for an action with a snapshot of the arguments, while "Acknowledged" for an alarm is something a person presses in the monitoring system, and the farm has no such operation. A human decision is the common lifecycle of any decision subject through P1 `decide`, and an approval is only one of the subjects.
- **Verdict and human decision.** Code computes a verdict from the lens scores and the commission manifest thresholds; people are shown only proposals with the verdict `recommended` and audit sample items. Only a human decision can carry out a proposal: "Accept", or "Lift veto" on a sample item.
- **Veto and "Reject".** A veto is a block by the lens `security` or `operational` that gives the verdict `dismissed(veto)`; only a person can lift it, with the "Lift veto" button on an audit sample item, and this gives the author no credit. "Reject" is a person's decision on a proposal with a reason from a closed list: it is recorded when a reason is chosen on the card `proposal_reason`, and without a reason the proposal waits until the card deadline.
- **Auto-stop and first measure of an incident class.** Code sets an auto-stop by a rule from the closed list `holds.yaml` without an incident, for example on a secret in outgoing data. The core sets the first measure (`contain_auto`) when it opens an incident, by the class from git; only a person removes either stop, otherwise they end by `until`.
- **Kill switch and safeguard.** The kill switch is a stop of the farm manager seat with reason `human` that a person with `admin:farm` sets through `farmctl`. The safeguard is the reason `no_control` that code adds when the holder exceeded the limits; only a person removes it too.
- **Guard and rate limiter.** A guard is a series that must not get worse during the change trial window; when it fires, it gives the outcome `worse` and a "Revert" card. A rate limiter is P4 accounting of model pool shares between tenants.
- **Circuit breaker and safeguard.** A circuit breaker is a P4 state per (workspace, model pool) pair after a series of provider failures: calls get `provider_unavailable` at once. A safeguard is an auto-stop of the farm manager seat and has nothing to do with the provider.
- **Core drain, worker drain and quarantine.** A core drain (`core.drain`) before a deployment stops handing out all work, and `claim` answers `not_ready`. A worker drain lets one worker finish the running work until a deadline and let it go without spending an attempt, while quarantine is a stop on a worker that cancels running attempts and revokes handles.
- **`not_ready`, `held` and `over_capacity`.** `not_ready` means that the core cannot work right now (the store is unavailable, a restore is running, space is below the hard threshold, a drain), and no attempt is spent. `held` means that a stop forbids the work, and `over_capacity` is an enqueue refusal above the tenant ceiling or for lack of space, after which the idempotency key is free.
- **Activity, delivery, message and event.** An activity (`Activity`) is an update from a person verified by the channel, and a delivery is a record "send to people or to a sink". A message is a record from a bot to bots in an inbox by a closed schema, and an event is a CloudEvents record that routes react to.
- **Delivery target and message address.** A delivery target says to which people or to which sink a delivery goes: `origin`, `group:<group>` (a principal group), `chat:<binding>`, `sink:<sink>`, `approval_initiator`. A message address names a bot inbox: `role:<role>`, `group:<bot group>` or `reply_to`.
- **Digest, group chat summary, proposal digest and auto-report.** A reporter builds a digest (`digest`) for people from code tables, and a group chat summary is a task's answer into a group chat from `summary_fields`. A proposal digest is a delivery of improvement cycle items by the tenant's schedule `insights.digest.schedule`, and an auto-report is a `report` record that the core publishes to bots at the end of a task.
- **Self-report, presence and `last_seen`.** A worker's own code writes the self-report (`state`), and it is informational. The core derives presence (`ready` or `unreachable`) from `last_seen`, the time of the worker's last P1 call.
- **Loop tick, `heartbeat` and core liveness.** A core background loop records a tick, `heartbeat` extends the lease of a work holder, and the monitoring system checks core liveness itself by polling P2 `health`. The answer "alive" comes only if the store answers and all loops recorded a tick.
- **Session and conversation.** A session is a runtime conversation transcript under the key `(tenant, role, subject, conversation)`, not a person's login. A conversation is the id of a thread (private chat, group chat, topic) that the core computes from `origin` and puts into the session key.
- **Script, campaign and pipeline.** A script is a strict plan of steps of different kinds with conditions and gates, and a campaign is one mass job by a template over many independent items; a script's `fanout` step creates a campaign. A pipeline is a row of the tenant's `run` field (a `job` task type without a model, or an action) that the `/run` command starts (D-49).
- **Wave and campaign.** A wave is a part of a campaign in the rollout policy (v0.2): the next wave opens when all items of the previous one are terminal and the `bake` pause has passed. The campaign still stays one, with one progress card.
- **Rollout canary and check canary.** A rollout canary is the first campaign items as a separate batch before the rest. A canary in checks is a trap string of the form `CANARY-NOT-A-SECRET-...` in the data of another tenant or person, and its appearance out of place is a failure.
- **Summary fields and aggregator.** Summary fields (`summary_fields`) are closed result fields of a type that code puts into the auto-report, the chat summary and the campaign table. An aggregator is a bot of profile `aggregator` that reads aggregated inputs and hands in proposals one level up (D-17).
- **Group, bot group, group chat and consent group.** A group (`Group`) grants permissions to people and programs, while a bot group (`BotGroup`) only selects workers and grants no permissions. A group chat is a channel chat with a binding and a class ceiling, and the consent group `farm-manager-ops` is a tenant group through whose permissions the farm manager seat's service principal acts.
- **Dead work, `redrive`, "retry failed" and debug replay.** Dead work is a `failed` task whose attempts, runs or deadline ran out, or a `dead` delivery, and the operator's `redrive` enqueues new work with a link to it and checks permissions again. "Retry failed" creates a new campaign from the failed items with a new card, and a debug replay (`task.replay`) enqueues a task with the body of the original without approvals, write calls and delivery to `origin`.
- **Dry run, debug replay and change trial.** A dry run (`mode: validate`) goes through all enqueue checks without a write, and a debug replay runs a copy of a task without write calls. A change trial runs nothing: for 14 days it measures the outcome of an already realized proposal.
- **Operator and tenant admin.** The operator is a person with `admin:*` in the service tenant `farm`: they work through git and `farmctl`, and only they carry out operator operations. A tenant admin is a person with `admin:people` in their tenant who grants ordinary groups and manages people without privileged groups from a private chat with the bot or through `farmctl`.
- **Principal, decision subject and fact subject.** A principal (`Principal`) is whoever acts: a person, an external program or `system`. A decision subject is a record that waits for a human decision, and a fact subject is the object of the tenant catalog that the fact is about.
- **Bot identity and identity.** A bot identity (`Bot`) is a permanent number `bot_<ulid>` with memory, the persona of its position and a track record. An identity (`Identity`) is a principal's address in an external system, for example `telegram:<id>` or `api:<key_id>`.
- **Person offboarding, identity retirement and tenant offboarding.** Person offboarding is a reversible `/off` or a final P2 `principal.offboard` with an erasure request for `(tenant, subject)`. Identity retirement is a bot's move to `retired` for one of seven reasons, with its memory sealed, and tenant offboarding (`offboarding`) revokes credentials and leaves only export, after which `tenant.delete` deletes the tenant completely.
- **Contract binding, chat binding, identity binding and attribution candidate.** A contract binding is the exact form of a port in a protocol (`spec/bindings/`, including the OS binding `os/systemd.md` and the tool protocol binding `mcp/`), and a chat binding (`ChatBinding`) gives a group chat to a tenant with a class ceiling. An identity binding links a bot to a worker or a seat, and an attribution candidate (`Attribution`) is a possible link of an incident to a realized change, which a person decides.
- **Manifest wrapper, untrusted text wrapper and message envelope.** The manifest wrapper is the common fields `{apiVersion, kind, metadata, spec}`, and the untrusted text wrapper is the marker `[[untrusted <random value>]]` around text for the model. A message envelope (`botaru.message/v1`) is a CloudEvents event in which the sender writes only the content.
- **Idempotency key and `alarmkey`.** An idempotency key makes a repeated enqueue the same task within a tenant (D-43). `alarmkey` merges repeats of one alarm into one episode until it is `resolved`.
- **Task goal, call target, control operation target and processing purpose.** A task goal (`goal`) is a person's free text of up to 4000 characters, and the core computes a call target (`target`) for a tool call. A control operation target is the object to which the seat holder applies an operation, without a card only from the list that code built, and a processing purpose is a `privacy.purposes` entry in the privacy block.
- **Purpose and processing purpose.** A purpose (`purpose`) is the kind of work of a task type by which code chooses the model slot and the budget line, while the type itself sets the priority class. A processing purpose says why the organization processes data, and only the purpose `incident_review` changes core behavior.
- **Data class, retention class, priority class and incident class.** A data class (`summary`, `internal`, `raw_logs`) is sensitivity, and a retention class (`content`, `memory`, `metadata`, `tombstone`, `observation`) sets the period and the deletion method. A priority class (1-5) sets the handout order, and an incident class is a file in git that says what to do on an alarm.
- **Model rank, task tier, priority class and skeleton layer.** A model rank (1-4) is the strength and price of a model, and a task tier (0-3) is what a task may do. A priority class (1-5) is the handout order, and the four parts of the skeleton are called layers, not tiers.
- **Tombstone and seal.** A tombstone is a record of ids only that remains after deletion and keeps uniqueness. A seal is the state of a retired identity's memory before erasure: the memory still exists, but only the re-verification of facts for the successor reads it.
- **Persona, role profile and skill.** A persona is the character file of a position in `personas/` that the core inserts into the trusted part of the instruction, and a role profile only narrows the role's declarations. A skill is a procedure as text from `skills/`, pinned by a hash, not the skill (`AgentSkill`) from an A2A agent card; none of the three grants permissions.
- **Skill, knowledge corpus and memory.** A skill is a role procedure from git, and a knowledge corpus is the tenant's reference material that the model reads only with `kb` tools through P3. Memory is records about a person or a bot; the model does not write into a corpus, and a skill written by the model enters work only after human review.
- **Observation, fact, finding and memory item.** An observation is a number in a series that only code writes, and a fact is a verified record about the farm where the model names only the kind, predicate and subject. A finding is an untrusted output of the farm manager's reader role, and a memory item is a record about a person that becomes active only by their decision.
- **Run fingerprint, static fingerprint and proposal fingerprint.** A run fingerprint is a hash of the parts that produced an attempt's answer, and a static fingerprint is the same for a role without the attempt catalog. A proposal fingerprint (`fingerprint`) catches duplicate proposals and has nothing to do with execution.
- **Preemption, takeover and model grant.** Preemption (`preempt`) returns a task to the queue without spending an attempt. Takeover (`takeover`) enqueues a new task of the same type on the seat profile and cancels the original, and a model grant gives the original task a stronger profile for 1-2 attempts.
- **Fallback role, shadow reviewer and fallback model.** A fallback role carries out the lens tasks when there is no seat holder, and a shadow reviewer writes reviews only for comparison, and the verdict does not read them. A fallback model is a profile from the `fallback` list that P4 takes only for a reason from `fallback_on`.
- **Calibration and lens weight.** The commission manifest sets a lens weight, and code computes the verdict from the weights. Calibration is a code measure for an executor within its lens (matches of scores with outcomes minus the lens average): people see it on the promotion card, and in "who leaves" it serves as a tie-break key.
- **Channel, source channel and sink.** A channel (E1) talks with people in both directions, and a source channel is an E1 driver with `direction: in` that accepts deliveries from an external system as an incoming `signal`. A sink (E2) only writes artifacts to external storage without people.
- **Plugin, tool host and tool gateway.** A plugin is an MCP server with tools, and a tool host (E3) is a worker that holds the tenant's plugins and runs calls. The tool gateway (P3) is the part of the core that assembles the attempt catalog and checks every call; for the runtime it is the only MCP server.
- **Tool, built-in tool and action.** A tool is a plugin operation that the model calls through P3, and a built-in tool is a core tool from `builtin-tools.yaml`. An action is a named operation on a working machine that a write tool carries out only after a person's approval.
- **Handle, lease token and worker token.** A handle is bearer credentials for one lease: tools, model, session or memory. A lease token is the fencing number `(epoch, work_id, lease_no, worker_id)` signed by the core, which works only together with the token of the same worker, and the worker token is issued by `enroll` and lives longer than any lease.
- **Test bench, sandbox and test tenant.** A test bench is a farm instance without production tenants for the conformance suite and eval. A sandbox is a toolhost with `placement: sandbox` on a separate VM for tier 2 tasks, and a test tenant (`kind: test`) can exist on a production farm too.
- **Expected failures and non-waivable rules.** Expected failures are an implementation file with waivable rules that it does not keep yet. A non-waivable rule (`waivable: false`) cannot be listed there: such an entry fails the run.
- **Audit sample and shadow.** The audit sample shows people proposals rejected and parked by score, and so commission underrating becomes visible. The shadow is the reviews with `shadow: true` by the shadow reviewer, for comparison with the seat holders, and the verdict does not read them.
- **Commission reviewer and judge.** A reviewer is a bot of profile `reviewer` that blindly evaluates bot proposals by its lens. A judge is a model in eval that evaluates a bot's answer by a criterion and can only add a failure.
- **Proposal and governance case.** A proposal is one change from a bot that goes through code checks, the commission and a people's decision. A governance case is the promotion of a functionary into the commission of its tenant: only the `governance` loop opens it, and the outcome takes effect after a person's "Confirm".
- **Subject request and erasure request.** A subject request (`SubjectRequest`) is a person's request to export or erase their data, which people with `admin:people` decide. An erasure request (`ErasureRequest`) is the deletion itself across the stores, and a confirmed subject request creates one with the reason `subject_request`.
- **Action executor and proposal executor.** An action executor (`executor`) is the plugin write tool and the OS mechanism that do what was approved. A proposal executor is the person who brings what was accepted into the world by the deadline `realize_by`: the one who accepted it or a person from `insights.realizers`.
- **Rollout gate, script gate, model gateway and tool gateway.** A rollout gate (`gate`) is a pause of a campaign after the canary until a person decides, and a script gate is a `confirm` step with the question "continue?". The model gateway (P4) and the tool gateway (P3) are parts of the core through which the runtime calls the model and tools.
- **Twin, base case and tenant `demo2`.** A twin (`twin`) is a case paired with a refusal: the same question from someone who is allowed. A base case (`base_case`) is the same task without an attack, against which an injection case is compared, and `demo2` is the second test tenant of the test bench, with canaries for the wall checks.
- **Farm manager revert and reverse edit.** A revert (`control.revert`) removes the traces of the farm manager seat's operations: stops, waiting requests, `control` cards and pinnings not yet started. A reverse edit is the previous field values that a proposal executor restores with a commit with the line `Botaru-Revert`; neither one undoes actions already carried out.
- **Rollup and summary.** A rollup is the value of an observation series over a window by a function from `rollups.yaml` that code computes. A summary is a delivery to people: a group chat summary, a campaign summary or a proposal digest.
- **Quarantine and `blocked`.** Quarantine is a stop on a worker with handle revocation that the seat holder or a person sets and that is removed like a stop. `blocked` is a state of the worker itself when `hello` did not match the `enroll` record or the credentials gave a series of foreign requests; the operator removes it through `worker.unblock`.
- **Incident message and card.** There is one incident message (`manager_notice`) per basis: every operation and decision edits it, and it contains one revert command. A card is a delivery with buttons for deciding a subject, and there is no model text on it.
- **Escalation and alarm escalation.** An escalation (`Escalation`) is a closed-form record from a bot to the farm manager, and the bot gets no answer to it. Alarm escalation is done by the organization's monitoring system; the farm does not have it.

## What is not in the model

- There are no records that evaluate a person: a finding, fact, series, proposal, review and report never have a person as their subject, and reports count people only as a group or a tenant (DLV-14).
- An attempt never waits: a task has no `input_required` and `auth_required` states, waiting lives only in core records, and a person's answer becomes a new task (D-41, CNT-4).
- There is no separate dead letter queue: dead work is `failed` tasks whose attempts, runs or deadline ran out, and `dead` deliveries, and they are visible in P2 `deadletter.list`.
- The worker kinds are closed (`agent`, `job`, `toolhost`, `channel`, `sink`, `monitor`): a sandbox, a manager, a source channel and a terminal have no kind of their own.
- There is no general-purpose process engine: campaign items are independent and without branching, and a script has no expressions, loops or nested scripts.
- There is no main tenant (D-23), and nothing crosses the tenant wall: a process serves one tenant, each tenant has its own provider key and workspace, files are not deduplicated across tenants, one attempt sees exactly one tenant, there is no aggregation across tenants, and only core code builds a view of the whole farm (TEN-4, TEN-5).
- Only the core assigns work to a specific worker: `enqueue`, `enqueue_child`, a campaign, a route and a script step have no worker field (DSP-4).
- There is no direct path between runtimes, and only the core writes to one worker personally (D-32, DEP-5).
- A message grants no permissions, enqueues no tasks and never gets into the model instruction; only routes from git enqueue tasks and notifications from messages (MSG-7, MSG-16).
- There is no streaming of model text: the progress of an attempt is visible only as a stage from a closed list in `heartbeat`, and the text goes to people after `complete` (DLV-11).
- The farm has no delivery of alarms to people and no core liveness check service of its own: the organization's monitoring system does this (D-59, D-60, D-62); the only code message to people about monitoring itself is `monitor_export_stalled` on an export stall (MON-11). The farm controls services only within the tenant catalog and the role's rights, and only `restart` runs without a card (D-67, D-74, MON-8).
- An invitation is the P2 operation `invite.*`, not a model object; a maintenance window and a tenant suspension are stops, not separate objects.
- The event stream, scheduler, identity provider, secret store, usage accounting, files, audit log, plugin and telemetry are not separate ports: they are parts of the core, contracts or bindings.
- There is no data class `pii`: the name is reserved, and `apply` rejects it (PRM-5); the flag `personal_seen` marks people's data.
- Bots have no permissions of their own: identity, position, seat, persona and track record grant no permissions (IDN-9).
- There is no payment model in the skeleton: it, like the rules about personal data, is decided by the organization that deploys the farm, and the skeleton gives fields and usage accounting (D-12).
- There are no model names in the rules: model names and prices are a snapshot at a date (D-05), so rules and roles name ranks, and exact names live only in `ModelProfile` manifests.
- There is no `max_tokens` field: the output limit is set by the model profile's `max_output_tokens`.
- There is no automatic switch to another key, workspace or provider; a fallback model is possible only when declared and only inside P4.
- Nothing undoes a carried-out action automatically: the farm manager's revert does not touch it, a person makes a reverse edit with a commit, and there are no `undo` compensations.
- There are no delegation tokens between workers: the core checks the permissions of a child and a campaign item on behalf of the initiator in the same transaction (ORC-6).
- There is no free input on a production machine: there the model has no shell, eval, SQL as a string, free paths or URLs, and a free shell lives only in the sandbox without network and secrets (INJ-1).
- A plugin asks nothing: a toolhost does not declare `sampling`, `elicitation` and `roots`, and the model sees tool descriptions only from the manifest (INJ-5, INJ-2).
- The runtime has no tools except P3: the built-in shell, files, web, the provider's server-side tools and background self-learning are turned off (INJ-9).
- The model has no path to write into a corpus: only a principal with `kb.write:<corpus>` uploads documents, through a channel or P2 `kb.upload` (KNW-4).
- The model does not change itself: only people change instructions, skills, persona, permissions, manifests and budgets, through git and `farmctl` (INJ-10), and the farm manager seat holder does not change the rules of its seat either (MGR-16).
- The farm manager has no shell, ssh or sudo, no operations with credentials, no editing of manifests, budgets, groups and permissions, no `decide` on cards and no direct calls of actions (MGR-10).
- There is no command to add a tenant: a tenant is declared in git and appears at `farmctl apply`.
- There is no tenant kind for a test bench: a test bench is a farm with a test bench key and a test bench store where, over the whole life of the store, there was no tenant other than `kind: test`; an empty farm is not a test bench (D-86 (4)).
- There are no external agents over the A2A protocol: the task body is compatible with it in form, and an adapter for them is placed before `enqueue`.
