# E3 ToolHost

Sheet version: 0.3.0.

## In short

E3 is the tool execution adapter: a worker of kind `toolhost` that lives on the observed machine (`placement: host`) or on a separate sandbox VM (`placement: sandbox`) and runs MCP plugins. It takes through P1 the calls whose `target` matches its `enroll` record, calls the plugin over MCP, redacts and cuts the output and hands in the result. The model never talks to the toolhost: it sees only the P3 catalog, and tool descriptions and schemas come from the manifest. Where a plugin is placed depends on whether it has secrets, network and writes: this keeps the production machine without extra permissions. In addition, the action toolhost starts, stops and restarts the services that the tenant's catalog declared as managed (`service/control`, D-67).

## Who calls and who implements

- **Implemented by** the toolhost, a process with a worker token of one tenant; `enroll` fixes the tenant, the plugins, the placement and the machine (DEP-2, TEN-4).
- **Calls** the core through P1: `hello`, `claim(toolcall)`, `heartbeat`, `complete`, `fail`, `file.get`; a sandbox toolhost also `file.put` for result files.
- **Plugins** are external MCP servers; the toolhost is an MCP client for them.

## Guarantees

- MUST: on a production machine the model has no shell, free paths, URLs, hosts, commands and regular expressions; parameters of a `placement: host` plugin are of closed kinds only (INJ-1). Free input exists only for `placement: sandbox` on a separate VM without data, network and secrets (DEP-1).
- MUST: only an own plugin without secrets and without network access runs as a child process of the toolhost. A plugin with a secret, with network or a third-party plugin runs in its own container, described in the deployment in advance, with its own OS user and its own network. A write plugin lives in a separate toolhost, and the OS mechanism (`oneshot` or `unit`) allows the action only to its user (DEP-4). The deployment lint checks the user, network and secrets of each process by the deployment description (DEP-7, DEP-9, DEP-10). There is one action toolhost on a machine, and the machine belongs to exactly one tenant: the pair (machine, service) is in the catalog of one tenant, `apply` rejects a catalog with a machine of another tenant (D-75, TEN-4); the OS user of this toolhost is used by nobody else.
- MUST: neither the toolhost nor the plugin has credentials or a network path to the farm store: they talk to the core only through P1 (DEP-8).
- MUST: the bot and plugins are never root; a toolhost on a production machine does not run containers; only a sandbox toolhost manages containers and therefore does not share a machine with production data (DEP-3).
- MUST: the toolhost has no incoming port; a remote plugin accepts only an authenticated toolhost; the plugin's egress is held by the network means of its container and a closed list from the tenant's catalog; the plugin image is pinned by digest (DEP-6, INJ-6).
- MUST: a plugin that runs programs keeps `argv` as an array, an absolute path, parameters as whole elements from an `enum`, `--` before positional arguments, a cleaned environment, and does not run programs from the forbidden list (INJ-14).
- MUST: the toolhost measures the call lease period by its own monotonic clock from `lease_remaining_s` and stops working if it did not renew the lease; on `abandoned`, `lease_expired` and self-stop it sends the plugin an MCP cancellation and terminates its process after `kill_after` (default 10 s) (FEN-6). An external write carries the work id (FEN-7). The lease of a write call expired: the result is `exec_unknown`, no retry (APR-7).
- MUST: the trace context in `_meta` is passed to the plugin without baggage and does not affect decisions.
- MUST: a secret canary in the plugin output does not reach the runtime (INJ-4).
- MUST: a `via: host` service is started, stopped and restarted only by the narrow OS mechanism `unit` with the fields `unit_from` (the service name comes from `services[].unit` of the catalog), `verb_from` (the verb comes from `services[].control`) and `wait`. The access rule for it is generated by `apply` from the catalog's `services[]`: the OS user of this tenant's action toolhost is allowed exactly the `control` verbs on the exact service names. The deployment puts the rule on the machine (its location is set in the deployment description `spec/model/deploy-topology.schema.json`), and the deployment lint and `farmctl doctor` compare it with the catalog. Other services, other verbs and containers are not available to this user, and services of the core and of farm machines (`core1`) in a tenant's catalog fail the lint (MON-8, DEP-4, DEP-10, DEP-11). Which OS mechanism this is and what the rule looks like is said by the binding `spec/bindings/os/<os>.md` (reference `systemd.md`), not by the rule.
- MUST: `service/control` is executed once per permission number: without a card by the `grant_id` of a `service_grant` record (bot, role, task, service, verb, the task's reason code), if the service is in the role's allowed list and the verb is in `services[].no_card` (default only `restart`, D-74, D-68, APR-18); by `approval_id` if the verb is `start` or `stop` or the task saw untrusted text and the call went through a card (D-70, INJ-15). For a call on a person's command or from an external program, the initiator has their own capability `service.control:<service>` (D-73). One operation at a time per service (`exclusive: resource`); 2 minutes after a stop or restart the code checks the state and writes the result into the task journal (MON-8).
- MUST: the result of `service/control` and `monitor/script_run` for the model consists only of closed fields: the result code, the service state after the check and the `service_grant` number (or `approval_id`). The output of the unit or the script is not part of the call result: the core stores it as a task journal file with the untrusted text mark, and an attempt that reads it gets `untrusted_seen` (INJ-13, MON-10).
- MUST: the `monitor` plugin only reads the monitoring system: problems, item history and trends (`monitor/item_history` by a field from a closed list, for example `cpu_load`), the maintenance status, and only for hosts that the tenant's catalog bound to resources (`Catalog.spec.hosts[].monitor_host`). It has a secret and network, so it runs in its own container. The trust in the output is set by the manifest of each tool, and the code checks it (MON-6, D-82): `monitor/problems` (fields read by code: `triggerid`, class and item from the catalog's `monitor_triggers`, resource, severity, state, time), `monitor/maintenance` (whether the host is in maintenance now, and since when) and `monitor/item_history` (numbers only; a text or log item, detected by the value type in the API, gets `item_not_numeric`) declare `untrusted_output: false` and set no flag; `monitor/item_text` (values of text and log items) and `monitor/problem_comments` (comments on problems) declare `untrusted_output: true` and set `untrusted_seen` on the attempt with the source `monitor_item_text` or `monitor_comment` (INJ-13). The plugin returns trigger names, their tags and expanded problem texts from the API through no tool (INJ-16).

- The `conformance/suites/toolhost` suite with a fake plugin.

## What the port does not do

- It does not show the model the live descriptions and schemas of the plugin.
- It does not retry calls by itself and does not execute a write without an approved `approval_id` or the `grant_id` of a `service_grant` record.
- It does not serve two tenants: a machine belongs to one tenant, and the toolhost on it is enrolled in that tenant (TEN-4, D-75).
- It does not accept incoming connections.
- It does not touch services and containers that are not in the catalog's `services[]`, and does not write to the monitoring system: scripts, bot notes and code notes are executed by the E5 adapter (MON-7, MON-8, MON-10).
