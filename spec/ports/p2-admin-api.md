# P2 AdminAPI

How the core is built, not a contract: P2 serves our own `farmctl` and the channels on behalf of people, so this page describes the construction (C10, D-114). The request and response schemas of the rows `P2.*` in `spec/ports/operations.yaml` are implementation schemas that the Go core and `farmctl` use (`contract: false`), not a promise to foreign code; an OpenAPI description comes only with a second client.

## In short

P2 is everything people change and view: manifest apply, people and groups, workers, holds, erasure, proposals, seats, incidents and bot identities. The reference client is `farmctl`; commands of people in a channel go through P2 only on behalf of the verified person, only from a private chat and within the person's permissions (IDN-7, PRM-15). P2 listens separately from P1 and accepts no worker token; bots, external programs and `system` decide nothing through it. Every operation writes an audit record with the commit or the author of the command (AUD-1). Paths, credentials and commands on behalf of a person are in the HTTP binding `spec/bindings/http/admin.md`.

## Who calls

- The farm operator through `farmctl`: a `human` subject with `admin:*` permissions in the service tenant `farm`.
- The admin and the people of a tenant through `farmctl` or channel commands; card buttons call the same operations with the same checks. Only a `human` subject decides (cards, `seat.*`, `incident.dismiss`).
- The monitoring system calls only `health`, with its own key that is not a subject: no tenant, groups or permissions, and every other operation refuses it (MON-2, TEN-2). The core reads the key from the deployment configuration, not from the store, and serves `health` outside the request worker pool, so it answers even when the store does not; during a key change two values are valid.
- The external backup process calls only `backup.report`, and the usage reconciliation process only `spend.reconcile`, each with its report key.

## Operator operations

Operator operations are the closed list of PRM-14, kept as data: the P2 rows with `operator_only` in `spec/ports/operations.yaml` (`true` for the whole operation, or a string that names the case, for example a privileged group or a hold of scope `farm`). They go only through `farmctl`; with channel credentials P2 refuses them with `operator_only`, even on behalf of a person who has the permissions, and the channel answers with a ready text and calls nothing. A tenant appears only through `apply` from git (`tenants/<name>/tenant.yaml`); there is no operation to add one (MAN-5). Privileged groups, including decision permissions, are granted only by the operator: to a new person with `invite`, to an existing one with `grant --code`; the membership stays `pending` until the verification code is checked, and a production tenant needs a written request of another admin of the tenant (`--requested-by`, except for the first admin; PRM-13). An invitation and `/grant` in a channel grant only ordinary groups (`privileged_group`).

## Operations

- **Manifests and status.** `apply` brings the store to the manifest set of a commit atomically and idempotently, shows the plan with `--dry-run`, deletes a disappeared object only by an explicit list, prints the `privileged` flag of each group and refuses a set where an ordinary group became privileged (MAN-1, MAN-2, MAN-6, CAP-6). `status` shows the applied commit, errors, holds, `conforms_to` (MAN-8) and from v0.2 the `workers` block (STA-3). `doctor` checks loops, holds, workers, dead work, free space, open erasure requests, workspace ceilings, model profile retirement and the monitoring adapters. `health` is the liveness answer for the monitoring system: `alive` only if the store answers and every loop ticked in time, otherwise a code (`store_unavailable`, `loop_stale`, `not_ready`, `draining`), and only numbers (CAP-5, OBS-4, OBS-9, MON-11). `core.drain` stops dispatching before a rollout (LCY-6).
- **People and groups.** `principal.add`, `principal.off`, `principal.on`, `principal.set_identity`, `principal.offboard` (the final `offboarded` state with an erasure request and the `principal_left` notice; LCY-8, IDN-13), `invite.*` (`invite.create`, `invite.confirm`, `invite.revoke`), `grant` and `ungrant` (a group within the granter's own capabilities, PRM-7; removal cancels pending approvals, APR-6), `chat.bind` (a group chat with a class ceiling, `locale` and `model_text`; DLV-7, REP-7).
- **Workers and bots.** `worker.enroll`, `worker.drain`, `worker.revoke`, `worker.rotate`, `worker.unblock` (TEN-4, DEP-2, IDN-4); `bot.list`, `bot.show` (`--sealed` for the sealed memory of a retired identity), `bot.retire` (IDN-11); `secret.revoke` revokes a compromised credential at once and holds every scope that used it (SEC-6, v0.2).
- **Tasks and dead work.** `task.show`, `task.cancel`, `task.list`, `team.tasks`, `about` (code tables without model text; PRM-9, PRM-15); `task.redrive`, `delivery.redrive` and `deadletter.list` (DLV-4); `budget.set` only narrows a limit for a while, the limits live in git (MAN-5); `spend.reconcile` hands in the provider's daily sums (BUD-10); from v0.2 `dispatch.explain` and `dispatch.queue` (DSP-9), `task.journal` and `task.replay` for debugging (AUD-4, APR-8).
- **Holds.** `hold.set`, `hold.release`, `hold.list`: a hold by scope with effects and a deadline, visible in `status` and `doctor`, with an event and an audit record (HLD-1); it ends by `until` or by a person with `hold.release`, never by the core itself (HLD-2).
- **Audit, backup and restore.** `audit.query` (metadata only; AUD-7), `audit.verify` (the hash chain; AUD-6), `backup.report` (RET-5, RET-8), `restore.complete` (RET-6).
- **Erasure and a person's data.** `erasure.request`, `erasure.status`, `erasure.list`, `erasure.retry`, `erasure.match` and `principal.data_request`: early erasure goes only through an erasure request with a result for each store (RET-7, SEC-11, D-76); from v0.2 the extract (`principal.data_request` of kind `export`, only about oneself, SEC-10), `tenant.export` and `principal.export` only to an `export_only` sink (LCY-2), `tenant.privacy_report` (SEC-12), and `connection.register` and `connection.revoke` for the consent adapter (SEC-7).
- **Tenant lifecycle (v0.2).** `tenant.suspend`, `tenant.offboard`, `tenant.delete` (LCY-1).
- **Improvement cycle.** `proposal.list`, `proposal.show`, `proposal.link_commit` (PRP-19); decisions on proposals are card buttons through P1 `decide`, not P2 operations (APR-4). `commission.status` (COM-6, DIG-5), `obs.series` (OBV-3).
- **Campaigns and scripts.** `campaign.list`, `campaign.show`, `campaign.control`, `campaign.retry_failed` (ORC-1); `script.list`, `script.show`, `script.cancel` (SCR-11).
- **The farm manager and incidents.** `seat.assign`, `seat.vacate`, `seat.resume` (IDN-10, GOV-22); a hold of scope `seat` and `control.revert` (the kill switch and the revert of the seat's operations; MGR-15); `control.list` and `control.apply` (MGR-9); `incident.list`, `incident.show`, `incident.ack`, `incident.close`, `incident.dismiss` (MGR-8, GOV-13), from v0.3 `incident.cause` (MGR-8, GOV-38); `manager.direct` (MGR-4), `manager.cost`, `manager.reads` (MGR-28); `service.control` on behalf of a person with their own `service.control:<service>` (D-73, MON-8); from v0.2 `model_grant.list`, `model_grant.issue`, `model_grant.revoke` (MGR-17), `escalation.list`, `escalation.show` (MGR-5), `governance.list`, `governance.show`, `governance.cancel` (GOV-12), `attribution.list`, `attribution.create` (GOV-13).
- **Messages and knowledge (v0.2).** `msg.list`, `msg.show`, `inbox.status` (MSG-18); `kb.upload` (KNW-4).

## What P2 does not do

- It does not change the world bypassing git: roles, task types, plugins, actions, limits and group permissions change only by a commit and `apply`.
- It gives bots and external programs no decision operation, and it executes no action: an approval goes through P1 `decide`, and the core executes the action (APR-7).
- It does not open promotion cases or change a seat holder at a bot's request.
- Answers for people show the full refusal reason, unlike answers for the model.
