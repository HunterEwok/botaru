# P2 AdminAPI

Sheet version: 0.1.0.

## In short

P2 is everything that people change and view: manifest apply, people and groups, workers, holds, erasure, proposals, seats, incidents and bot identities. The reference client is `farmctl`; commands of people in a channel go through P2 only on behalf of the verified person, only from a private chat and within the person's permissions. The port listens separately from P1, worker tokens are not accepted here, and bots, external programs and `system` decide nothing through P2. Every operation is written to the audit with the commit number or the author of the command. Operator operations are the closed list PRM-14: they go only through `farmctl` and are never available from a channel.

## Who calls and who implements

- **Implemented by** the core. Binding: the HTTP v1 envelope `spec/bindings/http/admin.md` (paths `/v1/p2/<operation>`, credentials, commands on behalf of a person) and the map `spec/ports/operations.yaml` (rows `P2.*`) with the request and response schemas of each operation; OpenAPI will appear together with the second client.
- **Called by:**
  - the farm operator through `farmctl` (a `human` subject with `admin:*` permissions in the service tenant `farm`);
  - the admin and the people of a tenant through `farmctl` or through channel commands; the channel then acts only on behalf of the verified person and within the person's permissions, and accepts commands only in a private chat (IDN-7, PRM-7, PRM-15);
  - card buttons call the same operations with the same checks.
- **Not called by:** workers (their tokens are refused), bots, the subjects `service` and `system`.
- **The monitoring system** calls only `health` with its separate key. The `health` key is not a subject: it has no tenant, groups or permissions, it opens only this operation, and any other operation with it is refused (MON-2, TEN-2). The core takes the key value from the deployment configuration, not from C1, and the `health` handler lives outside the pool of request workers: so the operation answers even when the store is unavailable. During a key change two values are valid (`health_keys: [current, next]`).
- **The external backup process** calls only `backup.report` with its report key, as the usage reconciliation process calls `spend.reconcile`.
- **Operator operations** are the closed list PRM-14. In the tables below their "Who calls" column says "operator, `farmctl` only"; P2 refuses a call with channel credentials with the reason `operator_only`, and the channel answers with a ready text. A tenant appears only through `apply` from git (`tenants/<name>/tenant.yaml`); there is no operation to add a tenant (MAN-5).
- **Privileged groups** (PRM-13), including those with decision permissions (accept a proposal, remove a hold, confirm a promotion or an incident link, run a script), are granted only by the operator through `farmctl`: to a new person with `invite`, to an existing one with `grant --code`. Until the verification code is checked the membership is `pending`; for a production tenant a written request from an admin of this tenant who is another person is needed (`--requested-by`; the first admin of a tenant does not need `--requested-by`, PRM-13). An invitation and `/grant` in a channel grant only ordinary groups; an attempt to grant a privileged one gets `privileged_group`.

## Guarantees

- MUST: P2 listens separately from P1; worker tokens are not accepted on P2 (IDN-7).
- MUST: the `health` key is accepted only by the `health` operation and gives neither a subject nor a tenant; the monitoring system that holds the key does not run on the core machine and gets no other core credentials (MON-2, TEN-2).
- MUST: channel credentials on P2 act only on behalf of the verified person and within the person's permissions; operator operations from the closed list are always refused with the reason `operator_only` with such credentials, even on behalf of a person with the required permissions (IDN-7, PRM-14).
- MUST: only a subject of kind `human` may decide (decisions on cards (P1 `decide`), operation buttons on cards, `seat.*`, `incident.dismiss`); such operations from bots, `service` and `system` are refused.
- MUST: `service.control` from a person requires their own capability `service.control:<service>`, as for an ordinary action; an external program (`service`) gets this capability only by an explicit group row (D-73). Only `restart` from `services[].no_card` (default `[restart]`) goes without a card; `start` and `stop` go through an approval card (D-74).
- MUST: only a group whose capabilities are within the capabilities of the granter can be granted (PRM-7); privileged groups and decision permissions are granted only by the operator through `farmctl`, with the membership `pending` until the verification code is checked (PRM-13).
- MUST: every operation writes an audit record with the commit number or the author of the command (AUD-1).
- MUST: `apply` is atomic and idempotent: a repeat of the same set changes nothing; an object that disappeared from git is not deleted silently (MAN-2).
- MUST: one fact has one source: budget limits live in git, and `budget.set` only narrows them temporarily (MAN-5).
- MUST: a hold is visible in `status` and `doctor` and writes an event and an audit record (HLD-1). A hold ends by `until` or is removed by a person with `hold.release` on its scope; the core does not remove a hold by itself, and the holder of the farm manager seat removes only its own holds (HLD-2).
- MUST: early erasure, including manual erasure, goes only through an erasure request (RET-7).
- SHOULD: answers for people show the full refusal reason, unlike answers for the model.

## Bindings

- Object schemas: `spec/model/` and `spec/manifests/`; reasons: `spec/model/reasons.yaml`; capabilities: `spec/model/capabilities.yaml`.
- The registry of human decisions: for each card one file says who decides, the deadline, the outcome on silence and how to cancel.
- Checks: the `conformance/suites/core-blackbox` suite (P2 section), fixtures `authorize/` and `authorize/holds/`.

## What the port does not do

- It does not change the world bypassing git: roles, task types, plugins, actions, limits and group permissions change only by a commit and `apply`; there are no behavior flags at run time.
- It does not give bots and external programs a single decision operation.
- It does not execute actions: approval of an action goes through `decide` in P1 and the core executes it (APR-7).
- It does not accept operator operations from a channel, even on behalf of a person with such permissions.
- It does not open promotion cases or change the seat holder at a bot's request.
