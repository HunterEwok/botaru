# E1 Channel

Sheet version: 0.3.0.

## In short

E1 is the adapter of a communication channel with people: a worker of kind `channel`, one process per tenant. On input it checks the authenticity of external system updates and the real sender, builds an incoming `Activity` and hands it to the core, and passes button presses on as decisions on behalf of the verified person. On output it takes deliveries through P1, renders them by the channel capabilities without link previews and markup, and reports with a receipt. The channel driver declares how reliably it knows the sender and the chat membership, and how it tells a person that they are talking to a bot. The reference channel is Telegram; other channels are added as a new driver without editing the core.

## Who calls and who implements

- **Implemented by** the channel adapter (a driver under the meta-schema `spec/manifests/drivers/`), a process with a worker token of its tenant (TEN-4). The channel credentials are explicit and separate: the worker token opens P1; on P2 the channel uses the P2 secret of its driver (one per driver in a tenant: the core issues it in the `worker.enroll` answer of the channel process, field `p2_token`, the deployment stores it, C1 holds only the hash; D-87 (3)), and the person and chat of each call come from the `Botaru-On-Behalf` and `Botaru-Chat` headers with the checks of `spec/bindings/http/README.md`; the external system secret (for example the bot token) is also only by name from the deployment (SEC-1, IDN-7).
- **Calls** the core through P1: `hello`, `submit_activity`, `decide`, `card.details`, `card.remind`, `campaign.control`, `script.control`, `file.put`, `file.get`, `claim(delivery)`, `complete`, `fail`; commands of people and operation buttons go to P2 on behalf of the verified person; text commands only from the private chat, which is checked by the person's identity without a chat binding, operation buttons from the chat of the card delivery (PRM-15).
- **Driver declarations:** `identity_assurance` (`strong` or `weak`), `membership_assurance` (`enforced` or `none`), the identity kind (for example `email:<address>`), the capabilities `max_text`, `buttons`, `files`, `edit`; `ai_disclosure` (`native` if the external system itself shows the bot, or `first_contact`) and `provenance` (`metadata` or `visible_label`), how the channel passes on the data origin mark `dataorigin` (DLV-12, DLV-13). A driver without `ai_disclosure` fails `apply`.
- **Chat binding** (`ChatBinding`, an operator record of P2 `chat.bind`) carries the class ceiling, `assistant: true` for a personal assistant binding (private chats only, DSP-10) and the list of chat members as the channel knows it: the channel updates it when a member joins or leaves, and by it the core sends `principal_left` to the admins when a person leaves (IDN-13) and keeps deliveries `withheld` when there is an unknown member (DLV-7).

## Guarantees

- MUST: an activity where the channel cannot name the real sender, and input of a channel with `identity_assurance: weak`, do not execute privileged commands and do not approve actions; an unknown identity does not create a task (IDN-3).
- MUST: the identity is looked up only among the subjects of the channel's tenant (TEN-4); an activity from a non-subject in a bound chat creates no `Activity`, file or session record: the channel saves nothing of it and passes nothing to the core except the event `activity.ignored(not_subject)`, and the code answers by repeating the `ai_notice` and `privacy_notice` notices no more than once per `notice_repeat` period (MSG-17, DLV-7).
- MUST: one update submitted twice gives one task; the external system offset moves only after the core answers (DLV-5).
- MUST: the channel builds the card of any decision only from the subject record by a code template; there is no model text in the card (APR-3). In a channel without buttons the card shows a text command with the id and `nonce`, and it is checked the same way as a press (APR-4).
- MUST: to each card the channel adds the code bottom line "why you, until when, what happens if you stay silent" from the decision registry row (APR-12).
- MUST: outgoing messages go without link previews and without markup, links outside the tenant's list are cut out; a found secret stops the sending, the admins get an event without content (INJ-11).
- MUST: the delivery address comes only from `origin`, a route name or `deliver_to`; a mark above the group chat ceiling: the full answer in a private message, only a ready text in the chat (DLV-6). Only a summary by the type's `summary_fields` goes to a group chat, the rest to the person who asked in a private message (DLV-15).
- MUST: a ceiling above `summary` and cards in a group only under `membership_assurance: enforced`; an unknown member appeared: deliveries to the chat are `withheld` (DLV-7).
- MUST: model text goes with the provenance mark the way `provenance` declared; under `ai_disclosure: first_contact` model text for a recipient waits until the code text `ai_notice` has been delivered to them (DLV-12, DLV-13).
- MUST: the channel measures the delivery lease period by its own monotonic clock from `lease_remaining_s` and stops sending if it did not renew the lease; a repeated delivery without an idempotency key is allowed, and `card_update` edits an already sent message (FEN-6, FEN-7).
- MUST: there is no streaming output of model text (DLV-11).
- MUST: the channel does not deliver alarms to people by routes, and there are no buttons to acknowledge them. In an installation with the `monitor` profile people get farm alarms, including those about a missing manager and about an unhandled incident, only through the monitoring system (MON-1, MON-12); in an installation without it the channel delivers only the code text `alarm_notice`, which the core puts itself (MON-13, D-88). The channel delivers cards, summaries and code messages about incidents and the manager as ordinary deliveries; the only code message about the monitoring system itself is `monitor_export_stalled` (MON-11).
- MUST: the driver does not configure link previews, markup and receiving messages "on behalf of the chat": such fields are forbidden by the driver meta-schema (MAN-4).

## Bindings

- `spec/bindings/channels/<channel>.md`: how channel fields map onto `Activity` and `Delivery`, how authenticity and chat membership are checked (reference `telegram.md`); for a source channel also the incoming format, the authentication methods and a ready field mapping (reference `webhook.md`). Monitoring system problems do not go through a source channel, but through the E5 adapter (MON-5).
- `spec/model/activity.schema.json`, `delivery.schema.json`; the driver meta-schema in `spec/manifests/drivers/`.
- The channel check suite `conformance/suites/channel`: IDN-3, IDN-7, APR-3, DLV-5..7, INJ-11, MSG-17; an activity from a non-subject in a chat with `membership_assurance: none` gives no `Activity` and no `file.put`.

## What the port does not do

- It does not download URLs from messages: it saves attachments itself and passes `file_ref` (INJ-8).
- It does not choose the task type by the meaning of the text: code chooses the type (IDN-6).
- It does not build cards from model text and passes nothing by a button except the id and `nonce`.
- It does not evaluate people and does not write judgments about them.
- It does not execute operator operations on anyone's behalf.
- It does not deliver alarms and does not accept their acknowledgements: the monitoring system does this (MON-1).
