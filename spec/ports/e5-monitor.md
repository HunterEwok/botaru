# E5 Monitor

Sheet version: 0.1.0.

## In short

Port E5 is part of the `monitor` conformance profile (D-88): an installation that has a monitoring system implements it. An installation without it delivers alarms to people as the code text `alarm_notice` (MON-13), and the deployment watchdog polls core liveness (MON-2).

E5 is the adapter of the organization's external monitoring system: a worker of kind `monitor`, an edge process like a channel. Watching machines, services, disks and load and delivering alarms to people belong to the monitoring system; the farm does not repeat them and adds what the monitoring system does not see: tasks, bots, money, campaigns, secrets, the manager and the commission (D-59). The adapter sends to the monitoring system the episodes of farm alarms and the head of the audit chain signed by the core, maintains the farm hosts and template in its host group, receives from the monitoring system problems on catalog hosts and passes them to the core as external events, and on a core delivery runs its scripts on the catalog hosts of its tenant (D-67, D-69). The monitoring system itself checks core liveness by polling P2 `health`; the farm has no separate liveness check process (D-60). The adapter takes work by pull through P1, the core does not go outside. Everything the adapter read from the monitoring system (names of scripts, triggers, texts) stays a vocabulary for code: script names and trigger classes get into the model context only from the tenant's catalog (`monitor_scripts_allowed`, `monitor_triggers`), and code compares the API answer with the catalog. The reference implementation is Zabbix (D-66); the rules and the other documents say "monitoring system".

## Who calls and who implements

- **Implemented by** the monitoring adapter, a process with a worker token of its tenant: one process per tenant and a separate process in the service tenant `farm` (TEN-4). A tenant process exports only the alarms and the audit head of its tenant and receives problems and runs scripts only for hosts that its tenant's catalog bound to resources (`Catalog.spec.hosts[].monitor_host`). The `farm` process exports the alarms about the farm itself (tag `scope: farm`) and the head of the `farm` chain, and it alone maintains the farm hosts and template.
- **Calls** the core through P1: `hello`, `claim(delivery)`, `heartbeat`, `complete`, `fail`, `release`; `submit_activity` (an activity of kind `signal` from a `service` subject with the identity `hook:monitor`).
- **Calls** the monitoring system through its API as its own user with narrow permissions (D-61, MON-4): each adapter process has its own monitoring system user, a tenant process with permissions only on the host groups that this tenant's catalog named, the `farm` process on the host group and the template group of the farm; there is no user shared by two processes, and `doctor` checks through the API that the user of the `demo` adapter does not see `demo2` hosts and farm hosts. The adapter has no credentials of the store, the model provider and the channels (DEP-8).
- **Deployment.** In the deployment description (`spec/model/deploy-topology.schema.json`) the top-level key `monitoring: {url, address}` names the monitoring system, and the lint checks that `address` is not a farm host (MON-2). The list of farm hosts (`farm_hosts`, in the example `[core1, backup1]`: the core machine and the backup machine) lives there too: `apply` rejects a tenant catalog where the `monitor_host` or the `machine` of a resource matches a farm host or a host already bound to another tenant (D-75), and `doctor` checks that the adapter user has no script permission on the farm host group (DEP-11). The adapter is a `kind: monitor` process with the OS user `botaru-mon`, the network `monitor-out` (only to the monitoring system and to P1) and the secrets `worker-token-monitor` and `monitor-api-token` (DEP-10).
- **The monitoring system** calls the adapter only with a problem webhook and calls the core only with the P2 operation `health` with its key, which opens this one operation (MON-2). It does not run on the core machine, and it has no other core credentials.
- **People** get farm alarms, press "Acknowledged", escalate, are on call and silence notifications only in the monitoring system (D-62, MON-1). The only exception: if the export to the monitoring system has failed for longer than 15 minutes, code sends the tenant admins and the operator the code message `monitor_export_stalled` in the channel (text from the message catalog, without the model), no more than once in 6 hours (MON-11). Bots with the role permission start, stop and restart services on catalog machines themselves, including through monitoring system scripts via the adapter, and run scripts by the `monitor_scripts` permission (D-67, D-68, MON-8, MON-10); people see every such action as a code note on the problem, in the farm audit and in the task journal.

## Data shapes

Alarm episodes, the audit head and the adapter tick go to the monitoring system only as numbers, `enum` values and ids from the tenant's catalog: ids of people, texts of the model and of people, file names and tool arguments are never part of them (MON-1, OBS-1). The farm writes text into the monitoring system only as notes on problems: a code note by the template `service_control_done` from v0.1 (MON-8) and a bot note from v0.2 (MON-7). The monitoring system is a recipient of tenant data of class `third_party_storage` (`recipients[]` of the privacy block: `monitoring`): a bot note is not above class `summary`, passes the redaction of addresses, mail and secrets like tool output (INJ-4), carries no ids and names of people, and its text is part of the TEN-5 canary.

## Guarantees

- MUST: only the monitoring system delivers farm alarms to people. Each change of an alarm episode gives exactly one E5 delivery with tags and no E1 delivery; repeats, "Acknowledged", escalation, on-call duty and silencing live in the monitoring system (MON-1).
- MUST: the export of alarms and of the audit head carries only numbers, `enum` values, tags and catalog ids; no ids of people and no texts (MON-1, OBS-1).
- MUST: the monitoring system checks core liveness by polling P2 `health`. The answer is "alive" only when the store answers and all background loops ticked; a stopped `reaper` loop and an unavailable store give "not alive". The monitoring system does not run on the core machine, and it has no credentials of the core, the store, the channels and the model provider, except the `health` key; the deployment lint checks this (MON-2).
- MUST: no data from the adapter for longer than the threshold gives a problem in the monitoring system (MON-2).
- MUST: the head of the audit chain of each tenant and of `farm` is written at least once a day into the history of the monitoring system with a retention period not shorter than the audit period; the value carries `epoch`, `seq`, `hash`, `key_id` and the core signature, `audit.verify` checks the signature and the monotonicity of `seq` within an epoch (a rollback of `seq` only with a growth of `epoch` and a restore record, RET-6), so neither the adapter nor an administrator of the monitoring system can rewrite the witness (MON-3, AUD-6).
- MUST: `monitor_alarm` and `monitor_audit_head` deliveries are retried with a pause of up to 10 minutes while the episode is open or the head is not uploaded; episode changes go out in `seq` order; after the connection is restored the core exports the open episodes again; the age of the last successful export is visible in `health`, `status` and `doctor` (MON-11).
- MUST: each adapter process has its own monitoring system user. The user of the `farm` process reads and writes only hosts and templates in the farm group; the user of a tenant process sees only the host groups that this tenant's catalog named, and runs scripts only there; it has no permissions on farm hosts and hosts of another tenant (D-69, DEP-11). None of them can acknowledge, close or silence problems, change their severity, notification actions and maintenance windows. `farmctl doctor` checks the role and permissions of each user through the API and fails the check if the permissions are wider, including if the `demo` user can see a `demo2` host or has access to at least one script on a farm host (MON-4).
- MUST: a problem on a host that the tenant's catalog did not bind to a resource does not go to the farm. Only closed fields go into the event; the class and the item come from the catalog's `monitor_triggers` row by `triggerid`, and the trigger name, its tags and texts do not go into it. Only a `job` raises a farm alarm for a problem, after a re-check by code; the problem itself does not become `alarm.*`; a trigger outside the catalog raises nothing above `warn` and opens no incident (MON-5, ING-4, INJ-7).
- MUST: a repeated webhook about the same `eventid` and state gives one event (MON-5, IDM-4).
- MUST: a note is added only to a problem on a host of its tenant, with the mark `[botaru <bot_id>]`; there are no more than 10 bot notes per hour per tenant, code notes `service_control_done` do not count toward this limit; a bot note is not above class `summary`, after INJ-4 redaction, without ids and names of people; the adapter calls only adding a message (MON-7, MON-8, TEN-5).
- MUST: the adapter runs a script only on a `monitor_script` delivery from the core, only on a host that its tenant's catalog bound to a resource, only a `scriptid` from the latest list for this host and with input only from the `choices` list of the catalog row that matches the list in the script itself. The model sees the script name only from the catalog's `monitor_scripts_allowed`; the name from the API does not get into the model context (INJ-1). The adapter executes each delivery at most once and returns the result to the core through P1; the model sees the script output only as a task journal file with the untrusted text mark, and in the call result only closed fields (MON-10, INJ-13).
- MUST: the adapter executes an action with a `via: monitor` service by the same path, with the script that the catalog named for the verb; the core checks the allowed list, the limiters and the holds before creating the delivery (MON-8, APR-18, INJ-15).
- MUST: the core sets a hold by a maintenance window with the author `contain_auto`, the source `system:monitor` and the `until` of the adapter's poll, and moves `until` forward while the polls report the window active; only a person removes it, otherwise it ends by `until`, at most two poll intervals after the window. The adapter does not compute the monitoring system's time periods (D-103). Its effect `pause_action` does not cancel pending approvals but pauses them; only a host with `maintenance_hold: true` cancels them (MON-9, HLD-2, HLD-3).
- MUST: the adapter measures the delivery lease period by its own monotonic clock from `lease_remaining_s` and stops writing if it did not renew the lease; a value write carries the delivery id, so a repeat does not create a second episode (FEN-6, FEN-7).

## Bindings

- `spec/bindings/monitor/zabbix.md`: the reference binding (section below), item values, tags, trigger expressions, webhook parameters.
- `deploy/monitor/`: farm hosts, the farm template, the role and the user for each adapter process as data in git; `spec/model/monitor-map.yaml`: the closed table "class -> farm alarm" (the catalog's `monitor_triggers` row gives a problem its class).
- Schemas `spec/model/event-data/alarm.schema.json`, `spec/bindings/events/catalog.yaml` (`ext.monitor.problem.v1`, `ext.monitor.scripts.v1`, `ext.monitor.maintenance.v1`), the `health` response schema.
- The check suite `conformance/suites/monitor` with a mock monitoring system: one write per episode transition, no E1 delivery; a repeated webhook gives one event; a host outside the catalog is dropped; a note calls nothing except adding a message; a script on a host outside the catalog and a script outside the list are refused; a script name with an injection from the mock API does not appear in any request to the mock provider; a repeated `monitor_script` delivery does not run the script a second time; a `monitor_alarm` delivery while the system is unavailable is retried and goes out after recovery in `seq` order; a signed head with a substituted `hash` fails `audit.verify`; `doctor` fails if the adapter user has access to a script on a farm host or the `demo` user can see a `demo2` host.

## Reference binding: Zabbix 7.0 and later

| Duty | How it maps onto Zabbix |
|---|---|
| Hosts and template | `host.create`, `host.update` and `template.*` only in the farm host group and the farm template group; hosts and template from `deploy/monitor/` (for example the host `botaru-core`) |
| Alarm export | `history.push` into trapper items (Zabbix trapper type, text) of the farm host, one per severity: `botaru.alarm[info]`, `botaru.alarm[warn]`, `botaru.alarm[page]`. The value is a string of `key=value` pairs from the episode fields |
| Template triggers | One trigger per item with the severity Information, Warning, High; the problem expression `find(/botaru-core/botaru.alarm[page],,"like","state=firing")=1`, the recovery expression the same with `state=resolved`; the event generation mode "Multiple", an OK event closes the problems with a matching value of the `key` tag |
| Problem tags | The trigger tags `tenant`, `alarm`, `subject`, `severity`, `scope`, `origin`, `key` take their values from the item value with the macro `{{ITEM.VALUE}.regsub(...)}`; by these tags people configure notification actions, escalation and silencing; an action usually skips alarms with `origin: monitor`, because the original problem already wakes people |
| Audit head | `history.push` into the text trapper `botaru.audit.head[<tenant>]` (the value `epoch=<n> seq=<n> hash=<hex> sig=<base64> key=<id>` as the core composed it); the retention period of the item history is not shorter than the audit period; `doctor` reads `item.get` (item history) and the `hk_history_global` setting and warns if the period is shorter than 90 days |
| Adapter tick | `history.push` into the numeric trapper `botaru.adapter.alive[<tenant>]` once a minute; the trigger `nodata(/botaru-core/botaru.adapter.alive[demo],{$BOTARU.ADAPTER.WINDOW})=1` with severity High |
| Core liveness | An item of type HTTP agent `botaru.health` on the host `botaru-core` (machine `core1`): the address of P2 `health`, the key in a header from the secret macro `{$BOTARU.HEALTH.KEY}`, interval 1 minute; during a key change two macros `{$BOTARU.HEALTH.KEY}` and `{$BOTARU.HEALTH.KEY.NEXT}`, the core accepts both values; dependent items by JSONPath (`alive`, `reason`, `drain_until_s`, `monitor_export_age_s`, free store space, tick ages, health indicators); the triggers `max(/botaru-core/botaru.health.alive,{$BOTARU.HEALTH.WINDOW})=0 and last(/botaru-core/botaru.health.drain_until_s)=0` and `nodata(/botaru-core/botaru.health.alive,{$BOTARU.HEALTH.WINDOW})=1` with severity High; a separate Warning trigger on `botaru.health.monitor_export_age_s` above 900 |
| Problem input | A media type of type "Webhook" to the address of the tenant adapter: parameters `{EVENT.ID}`, `{TRIGGER.ID}`, `{HOST.HOST}`, `{EVENT.NSEVERITY}`, `{EVENT.VALUE}`; the adapter does not read tags and the trigger name, the catalog gives the class by `{TRIGGER.ID}`; the adapter token in a media type parameter, TLS only. People of the organization configure the action with a condition on catalog hosts and with a recovery operation |
| Re-check | `problem.get` and `event.get` by `eventids`: the problem is open, the host is the same, the `triggerid` is the same; the number by `history.get` of the `item` from the catalog row |
| Reading by bots (E3) | The `monitor` plugin: `monitor/problems`, `monitor/maintenance` and `monitor/item_history` (history and trends of a numeric item by a field from a closed list, for example `cpu_load`) with trusted output, `monitor/item_text` (text and log items) and `monitor/problem_comments` with untrusted output (MON-6, D-82), on top of `problem.get`, `event.get`, `history.get`, `trend.get`, `maintenance.get` only for the catalog hosts of its tenant |
| Script list | `script.getscriptsbyhosts` for the catalog hosts every 10 minutes; the event goes out only when the hash of the answer changes; the list holds the `scriptid` of scripts of the scope "Manual host action" (`scope` 2), the adapter drops the `name` field. A script with manual input (`manualinput` 1) goes into the list only if the input validation is a list (`manualinput_validator_type` 1), and then the `choices` are taken from `manualinput_validator` and the core compares them with the catalog row; a script with string input validation does not go into the list |
| Script run | `script.execute` with the `scriptid` and `hostid` of a catalog host, `manualinput` only from the script's list; the answer `response` (`success`, `failed`) and `value` (output) give the result of the delivery; the Zabbix answer has no separate exit code field, so `exit_code` is empty. The monitoring system itself writes the run into its audit log |
| Notes (code notes from v0.1, bot notes from v0.2) | `event.acknowledge` only with the `action` value 4 ("add message"); the adapter never sets other bits (close, acknowledge, change severity, suppress, unsuppress and others) |
| Maintenance windows (v0.2) | polling `host.get` with `maintenance_status` and `maintenanceid` for the catalog hosts every `maintenance_poll_s`; the adapter does not evaluate `timeperiods` and cannot create or change windows |
| `match` and `erase` (v0.1) | `match`: `event.get` with `select_acknowledges` for the catalog hosts, a string search only in messages with the mark `[botaru`; the answer is a list of `eventid` and message numbers. `erase`: for the scope `(tenant, subject)` the answer is `not_applicable`; Zabbix 7.0 offers no API to delete an acknowledgement message, so `erase` by a list of ids answers `failed`, the result goes to a person as a separate line and does not keep the request open, and a Zabbix administrator removes the message by hand; this is acceptable because a bot note carries no data of people (MON-7, TEN-5, RET-7) |
| Users and roles | Each adapter process has its own Zabbix user in its own user group (`botaru-mon-farm`, `botaru-mon-demo`, `botaru-mon-demo2`), files in `deploy/monitor/<tenant>/`. The `farm` user: type Admin (needed for hosts and templates of its group), read and write permissions only on the farm host group and the farm template group. A tenant user: type User, read permissions only on the host groups that this tenant's catalog named, it does not see farm hosts and other tenants. For all: API access with a list of allowed methods from this table; in the role actions, running scripts and adding comments to problems are allowed, and acknowledging, closing, changing severity, suppressing problems and changing maintenance windows are forbidden. People set which scripts are available in the scripts themselves: the host group of a script (`groupid`) is the host group of one tenant, the user group of a script (`usrgrpid`) is the user group of this tenant; a script for all hosts or on the farm host group makes the permissions wider. For each user `doctor` calls `host.get` and `script.getscriptsbyhosts` on the hosts of the farm and of other tenants and fails the check if the answer is not empty |

## What the port does not do

- It does not deliver alarms to people in farm channels and keeps no repeats, acknowledgements, escalations and silencing of its own.
- It does not acknowledge, close or silence problems and does not change their severity. It does not run scripts without a `monitor_script` delivery from the core, on hosts outside its tenant's catalog and on farm hosts.
- It does not change notification actions, maintenance windows, hosts and templates outside its group.
- It does not pass to the farm script names, trigger names, tags, descriptions and other texts of the monitoring system, nor to the monitoring system data of people; the farm's text there is only notes on problems of class no higher than `summary` after redaction (MON-7, MON-8, TEN-5).
- It does not build or sign the audit head: the core sets the signature, the adapter only carries the value.
- It does not serve two tenants with one process (TEN-4).
