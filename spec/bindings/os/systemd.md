# OS binding: systemd

## In short

This binding implements the two OS mechanisms through which the farm changes something on a production machine: `oneshot` for actions from `Action` manifests and `unit` for starting, stopping and restarting services declared by the tenant's catalog (DEP-4, MON-8). Sheets and rules say "OS mechanism", "access rule" and "exact service name"; this file says that on a machine with systemd this is a oneshot unit with a path unit, `systemctl` with the verbs `start`, `stop`, `restart`, and a polkit rule that `apply` generates from the catalog. Another OS or another init system is another file in this folder with the same contract; the core and the toolhost do not depend on the choice.

## What it implements

| Mechanism | Sheet and operation | Who executes | Since | Rules |
|---|---|---|---|---|
| `oneshot` | E3 write call of an `Action` with the executor `os_mechanism: {kind: oneshot, unit, started_by, wait: false}` | the tenant's action toolhost on the resource machine | v0.1 | DEP-4, DEP-9, APR-7 |
| `unit` | E3 `service/control {service, verb}` for a `via: host` service with the executor `os_mechanism: {kind: unit, unit_from, verb_from, wait}` | the same action toolhost | v0.1 | DEP-4, MON-8, APR-18 |

## The `oneshot` mechanism

- The action toolhost puts the run request as a file into the tenant's queue `/var/lib/botaru/<tenant>/queue/`, writable only by the OS user of this tenant's action toolhost (`os_users` of the deployment description, DEP-10). The run request holds only the closed fields of the call and the `approval_id` or `grant_id` number; it holds no shell strings.
- The `started_by` path unit (in the example `botaru-demo-actions.path`) belongs to root and, when a run request appears, starts the oneshot unit of the request parser `unit` (`botaru-demo-actions.service`, `Type=oneshot`, `User=root`, `ProtectSystem=strict`, `NoNewPrivileges=yes`). The request parser checks the run request against the action schema, rejects everything that does not match the manifest and queues the run; `wait` is always `false`, the result of the write call is "accepted for run" with the run id, and the end of the work is reported by an event of the `job` worker (DEP-4).
- Units, queues and paths are separate for each tenant and contain its name: in the shared action manifest the tenant's place holds `{tenant}`, and `apply` substitutes the name (DEP-4, TEN-6).

## The `unit` mechanism

- The action toolhost calls `systemctl <verb> <unit>` without a shell, with `argv` as an array; `unit` is the exact unit name from `Catalog.spec.hosts[].services[].unit` (for example `nginx.service` on `web1`), `verb` is one of `start`, `stop`, `restart` from `services[].control`. The core computes both values from the catalog by the `service` and `verb` arguments; from the model only closed values from the `enum` reach the call (MON-8, INJ-1).
- With `wait: true` the toolhost waits for `systemctl is-active` to reach the required state for no longer than the tool's `timeout_s` and hands in the result as closed fields: the result code, the unit state (`active`, `inactive`, `failed`), the `grant_id` or `approval_id` number. The output of `systemctl` and `journalctl` is not part of the result: the core stores it as a task journal file with the untrusted text mark (INJ-13).
- An action without a card exists only for the `restart` verb from `services[].no_card` (default `[restart]`); `start` and `stop` go through an approval card like an ordinary action (D-74). The OS rule does not know this difference: it allows the toolhost user all `control` verbs of the service, and the core checks the card or the `service_grant` record before creating the write call (APR-18).

## The polkit rule that `apply` generates

The access rule is a polkit file that `apply` builds from the `services[]` of the tenant's catalog for each machine with `via: host`, and the deployment puts it on the machine. The location of the file is set in the deployment description (`spec/model/deploy-topology.schema.json`, in the example `/etc/polkit-1/rules.d/60-botaru-demo.rules` on `web1`); nobody writes or edits the rule by hand (DEP-4). An example for the `demo` catalog, where the service `nginx` with `unit: nginx.service` and `control: [start, stop, restart]` is declared on `web1`, and the OS user of the `demo` action toolhost on `web1` is `botaru-act-demo`:

```js
// generated by farmctl apply from tenants/demo/catalog.yaml; do not edit
polkit.addRule(function(action, subject) {
  if (action.id !== "org.freedesktop.systemd1.manage-units") return polkit.Result.NOT_HANDLED;
  if (subject.user !== "botaru-act-demo") return polkit.Result.NOT_HANDLED;
  var unit = action.lookup("unit");
  var verb = action.lookup("verb");
  if (unit === "nginx.service" && (verb === "start" || verb === "stop" || verb === "restart"))
    return polkit.Result.YES;
  return polkit.Result.NO;
});
```

- The rule holds only exact unit names and verbs from the catalog: it never holds patterns, wildcards, verbs other than the three, or units of farm services (core, workers, toolhost, monitoring adapter); such a catalog already fails the lint at `apply` (DEP-4, DEP-11).
- A machine belongs to exactly one tenant: the pair (machine, service) is in the catalog of one tenant, and the machine holds one rule of that tenant; `apply` rejects a catalog that names a machine already bound to another tenant (D-75, TEN-4).
- The user `botaru-act-demo` is used for nothing else: it is not shared with read plugins, it is not in groups with access to containers and `sudo`, and there are no other polkit rules for it (DEP-9).
- The deployment lint compares the generated rule with the catalog, `farmctl doctor` reads the rule on the machine through the action toolhost (file hash) and fails the check on a mismatch (DEP-10).

## Checks

- `conformance/suites/toolhost`: a mock machine with systemd where the rule is generated from the `demo` catalog; `systemctl restart nginx.service` from `botaru-act-demo` passes, `systemctl restart postgresql.service` and `systemctl restart nginx.service` from another user get a polkit refusal; the core does not create `start` without `approval_id` (fixtures MON-8, APR-18, DEP-4).
- Deployment lint: a `demo` action toolhost on `core1` fails (DEP-11); two tenants with one machine in their catalogs fail (D-75).
